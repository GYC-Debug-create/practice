| Java 基础 | J-01 | 抽象类和接口怎么选？ | 原题 | S | 方案 | ①JDK 8 接口有了 default 方法后，两者还剩什么区别？②为什么 Java 类只能单继承，却能实现多个接口？ | **结论：表达"是什么"（is-a）且要共享状态和代码用抽象类；表达"能做什么"（能力、规范）用接口。**<br>抽象类：可以有成员变量、构造器、任意访问修饰符的方法；只能单继承。<br>接口：字段默认 public static final；JDK 8 加 default / static 方法，JDK 9 加 private 方法；可多实现，没有实例状态。<br>选法：对外定义契约优先用接口（面向接口编程，便于扩展和 mock）；多个子类有公共骨架代码用抽象类（模板方法）。<br>常见组合：接口定规范 + 抽象类给骨架实现，如 List → AbstractList → ArrayList。 |
| Java 基础 | J-02 | 静态代码块、实例代码块、构造方法的执行顺序？ | 原题 | S | 原理 | ①有父类时整体顺序是什么？②静态代码块执行几次、在什么时候执行？ | **结论：静态先于实例，父类先于子类，代码块先于构造方法。**<br>有继承时：父类静态块 → 子类静态块 → 父类实例块 → 父类构造方法 → 子类实例块 → 子类构造方法。<br>静态块在类初始化阶段（`<clinit>`）执行，整个生命周期只执行一次；实例块每次 new 都执行。<br>实例块和实例变量赋值会被编译器插入到每个构造方法的 `super()` 之后，所以先于构造方法体执行。<br>同一级别的静态变量赋值与静态块，按源码书写顺序执行。 |
| Java 基础 | J-03 | Java 的 IO 模型有哪些？高并发短连接下 BIO 有什么问题？ | 原题 | S | 原理 | ①NIO 的 Selector 在 Linux 上底层靠什么？②Netty 为什么选 NIO 而不是 AIO？ | **结论：BIO 同步阻塞、NIO 同步非阻塞（IO 多路复用）、AIO 异步非阻塞；BIO 一个连接占一个线程，高并发短连接下线程开销会压垮服务。**<br>BIO：accept / read 都阻塞。NIO：Channel + Buffer + Selector，一个线程轮询多个连接的就绪事件。AIO：IO 完成后由系统回调通知。<br>BIO 短连接的问题：连接频繁建立断开 → 线程频繁创建销毁；每个线程栈默认 1MB，线程一多内存和上下文切换开销暴涨；改用线程池又受池大小限制，连接排队超时。<br>本质：线程数和连接数一一绑定，而线程大部分时间在阻塞等待或创建销毁，CPU 浪费在调度上。<br>NIO 让少量线程处理大量连接，Netty、Tomcat 的 NIO Connector 都基于它。 |

| Java 基础 | J-05 | 类在什么时候会被初始化？访问一个类的静态常量会执行它的静态代码块吗？ | 同点变体 | S | 原理 | ①通过子类访问父类的静态字段，子类静态块执行吗？②`new A[10]` 会初始化 A 吗？ | **结论：只有"主动使用"才触发类初始化并执行静态块；访问编译期常量不会触发。**<br>主动使用：new、读写静态字段（编译期常量除外）、调用静态方法、Class.forName 反射、初始化子类时先初始化父类、main 方法所在的类。<br>被动引用不触发：`static final` 编译期常量在编译时已放进调用方的常量池；通过子类引用父类静态字段只初始化父类；`new A[10]` 不初始化 A。<br>`static final` 但值要运行时计算（如 `= new Random().nextInt()`）时会触发初始化。 |
| Java 基础 | J-06 | select、poll、epoll 有什么区别？Java NIO 在 Linux 上用的是哪个？ | 同点变体 | S | 原理 | ①epoll 的 LT 和 ET 模式有什么区别？ | **结论：epoll 只关注就绪的连接，不用每次全量拷贝和遍历，连接数大时性能远好于 select / poll；Java NIO 在 Linux 上默认用 epoll。**<br>select：fd 集合是位图，默认上限 1024；每次调用都把全部 fd 拷进内核并线性扫描。<br>poll：用 pollfd 数组，没有 1024 上限，但仍是全量拷贝 + 线性扫描。<br>epoll：epoll_ctl 注册一次，内核用红黑树管理 fd；就绪的 fd 放进就绪链表，epoll_wait 只返回就绪的那些。<br>LT（水平触发，默认）：只要可读就反复通知；ET（边缘触发）：状态变化时只通知一次，必须一次读完。 |
| Java 基础 | J-07 | == 和 equals 的区别？为什么重写 equals 必须重写 hashCode？ | 领域高频 | A | 原理 | ①hashCode 相同，equals 一定相同吗？ | **结论：== 比较基本类型的值或引用的地址；equals 比较对象内容（Object 的默认实现等同 ==，需要重写）。**<br>String、Integer 等类都重写了 equals，比较的是内容。<br>约定：equals 相等的两个对象，hashCode 必须相等；hashCode 相等，equals 不一定相等（哈希冲突）。<br>只重写 equals 不重写 hashCode：两个"相等"的对象放进 HashMap / HashSet 会落到不同的桶，导致重复存储、get 不到。 |
| Java 基础 | J-08 | String、StringBuilder、StringBuffer 的区别？String 为什么不可变？ | 领域高频 | A | 原理 | ①`String s = new String("abc")` 创建了几个对象？②JDK 9 里 String 的底层有什么变化？ | **结论：String 不可变；StringBuilder 可变、线程不安全、速度快；StringBuffer 可变、方法加了 synchronized、线程安全。**<br>不可变的原因：类被 final 修饰不能继承；内部数组是 private final，且没有对外暴露修改它的方法。<br>好处：可以缓存 hash 值、支持字符串常量池复用、天然线程安全、适合做 HashMap 的 key。<br>JDK 9 起底层由 char[] 改为 byte[] + coder（纯 Latin-1 字符串每个字符只占 1 字节），节省内存。<br>循环里拼接字符串用 StringBuilder，用 `+` 会反复创建对象。 |
| Java 基础 | J-09 | HashMap 的底层原理？JDK 7 和 JDK 8 有什么区别？ | 领域高频 | A | 原理 | ①容量为什么是 2 的幂？②链表转红黑树的条件是什么？ | **结论：HashMap 是数组 + 链表（JDK 8 起加了红黑树），用 key 的 hash 定位桶，冲突时挂链表。**<br>put：`hash = h ^ (h >>> 16)` 扰动 → `(n - 1) & hash` 定位桶 → 空桶直接放；否则遍历比较 key，相同则覆盖，不同则插入。<br>JDK 7 头插法，多线程扩容会形成环形链表；JDK 8 改尾插法，链表长度超过 8 且数组长度 ≥ 64 时转红黑树（不足 64 先扩容），节点数 ≤ 6 时退回链表。<br>扩容：默认容量 16、负载因子 0.75，元素数超过阈值就翻倍；JDK 8 扩容时元素要么留在原位置，要么移到"原位置 + 旧容量"。<br>容量取 2 的幂：让 `(n - 1) & hash` 等价于取模，且分布均匀。 |
| Java 基础 | J-10 | HashMap 为什么线程不安全？ConcurrentHashMap 怎么保证线程安全？ | 领域高频 | A | 原理 | ①ConcurrentHashMap 的 key 和 value 为什么不能为 null？②size() 是怎么统计的？ | **结论：HashMap 的 put 和扩容没有任何同步；ConcurrentHashMap 在 JDK 7 用分段锁，JDK 8 用 CAS + synchronized 锁桶的头节点。**<br>HashMap 并发问题：JDK 7 扩容头插法形成环形链表，get 时死循环；JDK 7 / 8 都会出现数据覆盖丢失、size 不准。<br>JDK 7 的 CHM：Segment 数组（Segment 继承 ReentrantLock），默认 16 段，最多 16 个线程同时写。<br>JDK 8 的 CHM：取消 Segment，空桶用 CAS 放入，非空桶用 synchronized 锁住头节点，锁粒度细到单个桶；支持多线程协助扩容。<br>不允许 null：并发下 get 返回 null 时，无法区分是"key 不存在"还是"value 就是 null"。 |
| Java 基础 | J-11 | ArrayList 和 LinkedList 的区别？ArrayList 怎么扩容？ | 领域高频 | B | 原理 | ①ArrayList 线程安全吗？用什么替代？ | **结论：ArrayList 底层是动态数组，随机访问 O(1)；LinkedList 是双向链表，随机访问 O(n)；绝大多数场景用 ArrayList。**<br>插入删除：ArrayList 在中间位置要移动后面的元素；LinkedList 只改指针，但要先遍历找到位置，实际不一定更快。<br>内存：LinkedList 每个节点多存前后两个指针，且节点分散，对 CPU 缓存不友好。<br>扩容：JDK 8 无参构造时是空数组，第一次 add 扩到 10；之后满了按 1.5 倍（`old + (old >> 1)`）扩容并用 Arrays.copyOf 复制。<br>两者都线程不安全；并发场景用 CopyOnWriteArrayList 或 Collections.synchronizedList。 |
| Java 基础 | J-12 | 重载和重写的区别？ | 领域高频 | B | 定义 | ①只有返回值不同能构成重载吗？ | **结论：重载是同一个类里方法名相同、参数不同，编译期决定调用哪个；重写是子类覆盖父类方法，运行期按实际对象类型决定（多态）。**<br>重载：参数类型、个数或顺序不同；和返回值、修饰符无关，只有返回值不同不算重载。<br>重写：方法名和参数列表相同；返回值相同或是其子类；访问权限不能更严格；抛出的受检异常不能更宽。<br>private、static、final 方法不能被重写；构造方法不能重写，但能重载。 |
| Java 基础 | J-13 | Java 的异常体系是怎样的？受检异常和非受检异常有什么区别？ | 领域高频 | B | 定义 | ①try 里有 return，finally 还会执行吗？ | **结论：Throwable 下分 Error（JVM 严重错误，程序不处理）和 Exception；Exception 又分受检异常和运行时异常。**<br>Error：OutOfMemoryError、StackOverflowError。<br>受检异常（Checked）：IOException、SQLException 等，编译器强制 try-catch 或 throws 声明。<br>非受检异常：RuntimeException 及其子类，如 NullPointerException、IndexOutOfBoundsException，不强制处理。<br>try 里有 return 时 finally 照样执行（在返回值计算之后、方法真正返回之前）；finally 里写 return 会覆盖 try 的返回值，不要这样写。 |
| Java 基础 | J-14 | Java 是值传递还是引用传递？ | 领域高频 | B | 原理 | ①在方法里给对象参数重新赋值，外面的变量会变吗？ | **结论：Java 只有值传递；传对象时，传的是"引用的副本"。**<br>基本类型：传值的拷贝，方法内修改不影响外部。<br>引用类型：传地址的拷贝，方法内通过它修改对象的属性，外部能看到。<br>方法内把参数指向一个新对象，只改了副本，外部引用不变——这正说明它不是引用传递。 |
| Java 基础 | J-15 | 反射是什么？有哪些应用场景？ | 领域高频 | B | 原理 | ①反射为什么比直接调用慢？ | **结论：反射是在运行时获取类的信息，并操作其字段、方法、构造器的能力，入口是 Class 对象。**<br>获取 Class 的三种方式：`类名.class`、`对象.getClass()`、`Class.forName("全限定名")`。<br>场景：Spring IoC 创建 Bean 和依赖注入、动态代理、MyBatis 结果映射、注解处理、JDBC 加载驱动。<br>缺点：绕过编译期检查；能通过 setAccessible 破坏封装；性能比直接调用差（方法查找、参数装箱、访问检查，且难以被 JIT 内联）。 |
| Java 基础 | J-16 | 泛型是什么？什么是类型擦除？ | 领域高频 | B | 原理 | ①`List<String>` 和 `List<Integer>` 的 getClass() 相等吗？②`? extends` 和 `? super` 有什么区别？ | **结论：泛型提供编译期类型检查；Java 泛型是伪泛型，编译后类型参数会被擦除成上界（默认 Object）。**<br>擦除后，运行时 `List<String>` 和 `List<Integer>` 是同一个 Class。<br>编译器在取值的地方自动插入强制类型转换，并生成桥接方法保证多态正确。<br>限制：不能 `new T()`；不能用基本类型做类型参数；不能对泛型类型做 instanceof。<br>PECS 原则：`? extends T` 适合只读（生产者），`? super T` 适合只写（消费者）。 |
| Java 基础 | J-17 | 自动装箱和拆箱是什么？Integer 缓存池是怎么回事？ | 领域高频 | B | 原理 | ①`Integer a = 128, b = 128;` 那么 `a == b` 的结果是什么？ | **结论：装箱是基本类型自动转成包装类（调用 valueOf），拆箱是反过来（调用 xxxValue）。**<br>Integer.valueOf 对 -128 到 127 之间的值返回缓存对象，范围外每次 new 新对象。<br>所以 `Integer a = 127, b = 127` 时 `a == b` 为 true，换成 128 就是 false；包装类比较一律用 equals。<br>缓存上限可用 `-XX:AutoBoxCacheMax` 调大；Byte、Short、Long、Character（0 到 127）也有缓存，Float、Double 没有。<br>拆箱时对象为 null 会抛 NullPointerException。 |

| JVM | V-01 | 对象在分代内存中是怎么晋升到老年代的？ | 原题 | S | 原理 | ①动态年龄判定是怎么算的？②大对象为什么直接进老年代？ | **结论：对象先在 Eden 分配，每熬过一次 Minor GC 年龄 +1，达到阈值进入老年代；另外有动态年龄、大对象、空间担保三种提前晋升。**<br>年龄阈值：`-XX:MaxTenuringThreshold`，默认 15（使用 CMS 时默认 6）。<br>动态年龄：从年龄 1 开始累加 Survivor 中各年龄对象的大小，累加到某个年龄时超过 Survivor 的一半（TargetSurvivorRatio=50），该年龄及以上的对象直接晋升。<br>大对象：超过 `-XX:PretenureSizeThreshold` 直接在老年代分配（只对 Serial / ParNew 生效；G1 放进 Humongous 区），避免在两个 Survivor 间反复复制。<br>空间担保：Minor GC 后 Survivor 放不下的存活对象，直接进入老年代。 |
| JVM | V-02 | JVM 是怎么记录对象年龄的？ | 原题 | S | 原理 | ①为什么年龄阈值最大只能设 15？②对象头里还存了什么？ | **结论：年龄记录在对象头的 Mark Word 里，占 4 个 bit，所以最大值是 15。**<br>每次 Minor GC 时对象从 Eden / From 复制到 To 区，年龄 +1。<br>Mark Word（64 位 JVM 占 8 字节）还存哈希码、锁标志位、偏向线程 ID 等，存放内容随锁状态变化。<br>把 MaxTenuringThreshold 设成 16 以上，JVM 启动直接报错，原因就是 4 bit 存不下。 |
| JVM | V-03 | 标记-清除、复制、标记-整理算法的原理和优劣？复制算法在存活率高时为什么效率低？ | 原题 | S | 本质原因 | ①新生代和老年代分别用哪种？②CMS 用的是哪种，带来什么后果？ | **结论：标记-清除快但有碎片；复制无碎片但浪费空间、开销随存活对象数增长；标记-整理无碎片也不浪费空间，但移动对象慢。**<br>标记-清除：标记存活对象，回收其余；产生内存碎片，大对象找不到连续空间时会提前触发 GC。<br>复制：内存分两块只用一块，GC 时把存活对象复制到另一块；分配时用指针碰撞，速度快，但可用空间少一块。<br>标记-整理：把存活对象向一端移动，再清理边界外的内存；移动对象要更新所有引用，需要 STW。<br>存活率高时复制慢的本质：复制的工作量和存活对象数量成正比（每个都要拷贝 + 改引用），存活越多拷得越多，还得预留足够大的空间兜底；所以它只适合"朝生夕死"的新生代。 |
| JVM | V-04 | 为什么新生代用复制算法，老年代用标记-清除或标记-整理？Eden 和 Survivor 为什么是 8:1:1？ | 同点变体 | S | 本质原因 | ①Survivor 为什么要两个？ | **结论：按存活率选算法——新生代存活率低适合复制；老年代存活率高，也没有额外空间做担保，只能用标记-清除 / 整理。**<br>新生代绝大多数对象朝生夕死，每次只复制少量存活对象，代价很低。<br>8:1:1：每次只浪费 10% 的空间（一块 Survivor），而不是复制算法原始方案的 50%。<br>两个 Survivor：保证每次 GC 后总有一块是空的，存活对象在两块之间来回复制，不产生碎片；Survivor 不够时靠老年代做分配担保。 |

| 前端 JS | FE-17 | 箭头函数和普通函数有什么区别？ | 领域高频 | B | 定义 | ①对象的方法能用箭头函数写吗？ | **结论：箭头函数没有自己的 this、arguments、prototype，不能作为构造函数。**<br>this 继承定义时外层作用域的 this，且不能被 call / apply / bind 改变。<br>没有 arguments，用剩余参数 `...args` 代替。<br>不能 new，也不能做 Generator 函数。<br>对象方法用箭头函数时，this 不会指向这个对象，所以对象方法、需要动态 this 的回调要用普通函数。 |
| 前端 JS | FE-18 | 什么是跨域？有哪些解决方案？ | 领域高频 | B | 方案 | ①CORS 的预检请求什么时候触发？②开发环境的代理为什么能绕过跨域？ | **结论：浏览器的同源策略限制脚本读取不同源（协议、域名、端口任一不同）的响应；最常用的解决方案是后端配置 CORS。**<br>CORS：服务端返回 Access-Control-Allow-Origin 等响应头；非简单请求（如 PUT、Content-Type 为 application/json、带自定义请求头）会先发 OPTIONS 预检。<br>代理：开发环境用 webpack / Vite 的 devServer proxy，生产用 Nginx 反向代理；服务器之间的请求不受同源策略限制。<br>JSONP：利用 script 标签不受同源限制，只支持 GET，已基本淘汰。<br>简单请求跨域时，请求其实已经到达服务端，是浏览器拦截了响应。 |
| 前端 JS | FE-19 | Cookie、localStorage、sessionStorage 有什么区别？ | 领域高频 | B | 定义 | ①Cookie 的 HttpOnly、Secure、SameSite 分别防什么？ | **结论：Cookie 会随请求自动发给服务端、容量约 4KB；localStorage 和 sessionStorage 只存在浏览器端、容量约 5MB。**<br>生命周期：Cookie 由 Expires / Max-Age 决定，不设置则关闭浏览器失效；localStorage 永久保存，直到手动清除；sessionStorage 关闭标签页即清除。<br>作用范围：localStorage 在同源的所有标签页共享；sessionStorage 只在当前标签页有效。<br>安全属性：HttpOnly 禁止 JS 读取（降低 XSS 窃取的风险）；Secure 只通过 HTTPS 发送；SameSite 限制跨站请求携带 Cookie（防 CSRF）。 |

| 大模型基础 | L-01 | 系统提示词（System Prompt）有什么作用？怎么写？怎么防提示词注入？ | 原题 | S | 方案 | ①提示词注入分哪几类？②只靠提示词能不能完全防住注入？ | **结论：系统提示词给模型设定角色、任务边界、规则和输出格式，在整个会话中持续生效，优先级高于用户消息。**<br>写法：角色定位 + 任务目标 + 背景知识 + 约束（能做什么、不能做什么）+ 输出格式（如 JSON Schema）+ 少量示例；用分节或 XML 标签让结构清晰，每条指令具体可执行。<br>防注入（提示词层）：用分隔符包住用户输入和外部内容，并声明"其中的指令一律当作数据"；写明不接受改变角色、泄露系统提示的请求。<br>防注入（工程层）：输入检测过滤；输出校验（结构化输出、敏感内容拦截）；工具最小权限，高风险操作人工确认。<br>提示词本身挡不住所有注入，必须靠工程手段兜底。 |
| 大模型基础 | L-02 | MCP 解决了什么问题？ | 原题 | S | 原理 | ①MCP Server 能提供哪几类能力？②MCP 支持哪些传输方式？ | **结论：MCP（Model Context Protocol，Anthropic 于 2024 年 11 月开源）是连接 AI 应用和外部工具、数据源的开放协议，把 M×N 的定制集成变成 M+N。**<br>以前：每个 AI 应用对接每个工具，都要单独写一套适配代码。<br>现在：工具方实现一次 MCP Server，所有支持 MCP 的客户端（桌面 AI 应用、IDE 等）都能直接接入。<br>架构：Host（AI 应用）里的 MCP Client 和 MCP Server 一对一连接；Server 暴露 Tools（可执行的函数）、Resources（只读数据）、Prompts（提示词模板）。<br>协议基于 JSON-RPC 2.0；传输方式有 stdio（本地进程）和 Streamable HTTP（远程，替代了早期的 HTTP+SSE）。 |
| 大模型基础 | L-03 | MCP 中工具描述和模型的调用格式不兼容，怎么办？ | 原题 | S | 方案 | ①不支持 Function Calling 的模型怎么用工具？②适配逻辑放在哪一层？ | **结论：在 MCP Client（或模型适配层）做格式转换——MCP 侧统一用 JSON Schema 描述工具，Client 把它转成目标模型要求的工具格式，再把模型发出的调用转回 MCP 请求。**<br>不兼容的根源：各厂商的 Function Calling 格式不同，如 OpenAI 的 tools / tool_calls、Anthropic 的 tool_use、Gemini 的 functionDeclarations。<br>转换：`tools/list` 拿到的 name、description、inputSchema → 映射成模型的 tools 参数；模型返回的调用 → 组装成 `tools/call` 请求；执行结果再按模型格式作为工具结果回传。<br>Schema 降级：目标模型不支持的 JSON Schema 关键字（如部分模型不支持 oneOf、$ref）在转换时展开或简化。<br>模型不支持原生 Function Calling：把工具描述写进提示词，约定 JSON 输出格式，解析后做 Schema 校验，失败带着错误信息重试；LangChain、LiteLLM 等框架提供现成的多模型适配。 |
| 大模型基础 | L-04 | Function Calling 是怎么让模型调用外部 API 的？模型在其中扮演什么角色？ | 原题 | S | 原理 | ①模型会直接执行函数吗？②一次回答要调用多个函数怎么办？ | **结论：模型只负责"决定调哪个函数、生成参数"，真正执行 API 的是应用代码；模型是决策者和参数生成者，不是执行者。**<br>① 开发者把函数名、描述、参数的 JSON Schema 随请求一起发给模型。<br>② 模型判断需要调用时，返回结构化的调用意图（函数名 + JSON 参数），而不是普通文本。<br>③ 应用解析后执行真实的 API（鉴权、超时、错误处理都在应用侧），把结果作为工具消息回传给模型。<br>④ 模型根据结果生成最终回答，或继续发起下一次调用（多轮调用、并行调用）。 |
| 大模型基础 | L-05 | 用户问题有歧义、同时匹配多个工具时，模型怎么决策？ | 原题 | S | 原理 | ①怎么让工具选择更稳定？②tool_choice 参数有什么用？ | **结论：模型根据工具名称、描述、参数说明和用户意图的语义匹配程度来选，本质是基于上下文的概率生成，不是规则匹配；结果有三种：选一个、并行调用多个、先向用户澄清。**<br>决策依据：工具描述写得越清楚（适用场景、不适用场景、和相似工具的区别），选得越准。<br>工程手段：系统提示里规定"意图不明确或缺少必填参数时先追问，不许编造参数"；工具之间职责不重叠。<br>tool_choice 控制：auto（模型自己决定）、必须调用（OpenAI 为 required，Anthropic 为 any）、指定某个工具、none（不调用）。<br>工具很多时，先做意图分类 / 路由，只把相关的子集暴露给模型。 |
| 大模型基础 | L-06 | 什么是提示词注入？直接注入和间接注入有什么区别？ | 同点变体 | S | 原理 | ①Agent 读网页时被注入，危害为什么比普通聊天大？ | **结论：提示词注入是攻击者构造输入，让模型把数据当成指令执行，从而偏离原本设定（泄露系统提示、越权调用工具、输出有害内容）。**<br>直接注入：用户在对话里直接输入"忽略之前的所有指令……"。<br>间接注入：恶意指令藏在模型读取的外部内容里（网页、邮件、文档、工具返回结果），用户本人并不知情。<br>Agent 场景危害更大：模型有工具权限，被注入后能发邮件、改数据、外传信息。<br>根因：模型在机制上无法区分"指令"和"数据"，所以要靠权限隔离、人工确认等工程手段兜底。 |
| 大模型基础 | L-07 | MCP 和 Function Calling 是什么关系？ | 同点变体 | S | 原理 | ①有了 MCP 还需要 Function Calling 吗？ | **结论：Function Calling 是模型的能力（输出结构化的调用意图），MCP 是工具接入的协议标准（工具怎么被发现、描述、调用、返回结果）；两者互补，不是替代关系。**<br>Function Calling 解决"模型怎么表达要调用工具"，格式由各模型厂商定义。<br>MCP 解决"工具怎么用统一方式接入应用"，和具体模型无关。<br>配合方式：MCP Client 从 Server 拿到工具列表 → 转成模型的 Function Calling 格式 → 模型决定调用 → Client 发 `tools/call` 给 Server 执行。 |
| 大模型基础 | L-08 | MCP 的 Client 和 Server 是怎么通信的？ | 同点变体 | S | 原理 | ①Server 新增了工具，客户端怎么感知？ | **结论：基于 JSON-RPC 2.0，流程是初始化握手 → 能力协商 → 发现能力 → 调用。**<br>初始化：Client 发 initialize（协议版本、自身能力）→ Server 返回自己的能力 → Client 发 initialized 通知。<br>发现：`tools/list`、`resources/list`、`prompts/list` 获取可用能力及其描述、参数 Schema。<br>调用：`tools/call` 传入工具名和参数，Server 执行后返回结果（文本、图片等内容块；失败时用 isError 标记）。<br>变更通知：Server 的工具列表变化时发 `notifications/tools/list_changed`，Client 重新拉取列表。 |
| 大模型基础 | L-09 | 模型调用工具时生成了错误的参数或编造参数，怎么处理？ | 同点变体 | S | 方案 | ①错误信息要不要回传给模型？ | **结论：在"生成前约束、执行前校验、失败后反馈"三处把关，不能直接信任模型生成的参数。**<br>生成前：JSON Schema 写清类型、枚举值、必填项、格式和示例；开启严格结构化输出（如 OpenAI 的 strict 模式）。<br>执行前：应用侧做 Schema 校验和业务校验（ID 是否存在、当前用户有没有权限）。<br>失败后：把具体的错误信息作为工具结果回传，让模型自我修正，并限制重试次数。<br>缺少必填信息时让模型追问用户；高风险操作执行前人工确认。 |
| 大模型基础 | L-10 | 常用的提示词技巧有哪些？Few-shot、思维链分别是什么？ | 同点变体 | S | 原理 | ①Few-shot 的示例怎么选？ | **结论：核心是把任务说清楚、给出示例、引导推理、约束输出格式。**<br>Zero-shot / Few-shot：不给示例直接做 / 给几组"输入 → 输出"示例让模型模仿格式和风格；示例要覆盖典型情况且格式统一。<br>思维链（CoT）：让模型先写出推理步骤再给答案，提升数学、逻辑等多步问题的准确率；推理模型已把这个过程内置。<br>其他：角色设定、把复杂任务拆成多步串联（Prompt Chaining）、用分隔符区分指令和数据、指定输出格式、写明反例和边界条件。 |
| 大模型基础 | L-11 | 大模型的幻觉是什么？怎么缓解？ | 领域高频 | A | 方案 | ①大模型为什么会产生幻觉？ | **结论：幻觉是模型生成看似合理、但与事实不符或没有依据的内容；根源是模型按概率生成下一个 token，目标是"通顺"而不是"真实"。**<br>原因：训练数据有错误或过时；有知识截止日期；问题超出知识范围时仍会硬给答案；解码有随机性。<br>缓解：RAG 检索真实资料作为依据，并要求标注引用；提示词里允许模型回答"不知道"；降低 temperature。<br>校验：调用工具查实时数据；输出后做事实核验，或用另一个模型交叉检查；关键场景人工审核。 |
| 大模型基础 | L-12 | RAG 是什么？完整流程是怎样的？ | 领域高频 | A | 原理 | ①文档切块大小怎么定？②检索不准怎么优化？ | **结论：RAG（检索增强生成）先从外部知识库检索相关内容，再和问题一起交给模型生成答案，解决知识过时、私有知识和幻觉问题。**<br>离线：文档加载 → 切块（按段落或固定长度，相邻块有重叠）→ Embedding 向量化 → 存入向量数据库。<br>在线：问题向量化 → 相似度检索 Top-K → 重排序（Rerank）→ 拼进提示词 → 模型生成答案并标注来源。<br>优化：混合检索（向量 + BM25 关键词）、查询改写、调整切块大小、元数据过滤、Rerank 模型。<br>对比微调：RAG 更新知识只要改知识库，成本低、可溯源。 |
| 大模型基础 | L-13 | Temperature 和 Top-p 参数有什么作用？ | 领域高频 | A | 原理 | ①写代码和写文案分别怎么设？ | **结论：两者都控制输出的随机性：temperature 调整概率分布的平滑程度，top-p 限定参与采样的候选 token 范围。**<br>Temperature：越低分布越尖锐、输出越确定（接近 0 时基本每次都选概率最高的）；越高越随机、越有创造性。<br>Top-p（核采样）：只在累计概率达到 p 的最小候选集合里采样，p 越小候选越少。<br>一般只调其中一个。代码生成、信息抽取、结构化输出用低温度；创意写作用较高温度。 |
| 大模型基础 | L-14 | Token 是什么？上下文窗口是什么？ | 领域高频 | B | 定义 | ①同样的内容，中文和英文的 token 数为什么不一样？ | **结论：Token 是模型处理文本的最小单位，由分词器（如 BPE）切分得到；上下文窗口是模型一次能处理的输入 + 输出 token 总数上限。**<br>常见英文单词约 1 个 token；一个汉字占 1 到 2 个 token 不等，取决于具体模型的分词器。<br>计费、速度、窗口上限都按 token 计算。<br>超出窗口的内容会被截断或直接报错，所以长对话需要摘要、检索等上下文管理手段。 |
| 大模型基础 | L-15 | Transformer 和自注意力机制的基本原理是什么？ | 领域高频 | B | 原理 | ①为什么要用多头注意力？②位置编码有什么用？ | **结论：Transformer 用自注意力让序列中每个 token 直接和其他所有 token 计算相关性，可以并行计算，解决了 RNN 只能串行、长距离依赖弱的问题。**<br>自注意力：每个 token 生成 Q、K、V 三个向量，Q 和所有 K 做点积再除以 √d，经 softmax 得到权重，对 V 加权求和。<br>多头注意力：多组 Q / K / V 并行计算，从不同子空间捕捉不同的关系。<br>位置编码：注意力本身不感知顺序，要额外加入位置信息。<br>GPT 类大模型只用 Decoder 部分，用因果掩码保证每个 token 只能看到前面的内容，自回归地逐个生成。 |
| 大模型基础 | L-16 | Embedding 是什么？向量数据库有什么用？ | 领域高频 | B | 原理 | ①向量相似度怎么计算？ | **结论：Embedding 把文本映射成高维向量，语义相近的文本向量距离也近；向量数据库专门存储向量并做高效的相似度检索。**<br>相似度：余弦相似度、点积、欧氏距离。<br>检索：数据量大时用近似最近邻（ANN）索引，如 HNSW、IVF，用少量精度换速度。<br>常见选型：Milvus、Chroma、FAISS（库）、pgvector（PostgreSQL 扩展）、Elasticsearch 的向量检索。<br>用途：RAG 检索、语义搜索、推荐、Agent 长期记忆。 |
| 大模型基础 | L-17 | 提示词工程、RAG、微调分别适合什么场景？ | 领域高频 | B | 方案 | ①微调能让模型学会新知识吗？ | **结论：先提示词，再 RAG，最后才考虑微调——成本和门槛依次升高。**<br>提示词工程：几乎零成本，适合调整输出格式、风格、任务说明。<br>RAG：适合需要外部知识、私有数据、知识频繁更新、要求能溯源的场景。<br>微调：适合固定输出风格、特定领域的任务格式、让小模型学会某类任务；不适合频繁变化的知识，成本高，还有遗忘已有能力的风险。<br>实际项目里常组合使用。 |
| 大模型基础 | L-18 | 大模型的流式输出是怎么实现的？ | 领域高频 | B | 原理 | ①前端怎么接收流式数据？②SSE 和 WebSocket 有什么区别？ | **结论：模型逐个 token 生成，服务端每生成一段就推给客户端，常用 SSE（Server-Sent Events）实现，目的是缩短首字等待时间。**<br>SSE：基于 HTTP 长连接，响应头 `Content-Type: text/event-stream`，服务端按 `data: ...` 加空行的格式持续推送，单向（服务端 → 客户端）。<br>前端：EventSource 只支持 GET；调大模型接口一般用 fetch + `response.body.getReader()` 逐块读取并解析，可以发 POST。<br>后端（Spring）：返回 SseEmitter，或 WebFlux 的 `Flux<ServerSentEvent>`。<br>WebSocket 是全双工，适合双向实时交互；只需要单向推送时用 SSE 更简单。 |

| Web 安全 | S-01 | XSS 是什么？分几种？ | 原题 | S | 原理 | ①三种类型各举一个例子？②DOM 型和反射型的区别在哪？ | **结论：XSS（跨站脚本攻击）是攻击者把恶意脚本注入到网页中，在其他用户的浏览器里以该站点的身份执行；分存储型、反射型、DOM 型三种。**<br>存储型：脚本被存进数据库（评论、昵称），所有访问该页面的人都会中招，危害最大。<br>反射型：脚本放在 URL 参数里，服务端原样拼进响应返回，需要诱导用户点击恶意链接。<br>DOM 型：前端 JS 把 URL、输入框等不可信数据直接写进 innerHTML、document.write、eval，全程不经过服务端。<br>危害：窃取 Cookie / Token、冒充用户操作、篡改页面、钓鱼。 |
| Web 安全 | S-02 | 富文本编辑器需要保留部分 HTML 标签时，怎么防 XSS？ | 原题 | S | 方案 | ①只在前端过滤行不行？②a 标签的 href 怎么处理？ | **结论：不能整体转义（会破坏格式），要用白名单过滤：只保留允许的标签和属性，其余全部删掉，而且必须在服务端做。**<br>做法：把 HTML 解析成 DOM 树后逐个节点检查，不要用正则替换字符串。<br>标签白名单：p、b、i、img、a、ul、li 等；属性白名单按标签单独配置，如 img 只留 src / alt，a 只留 href / title。<br>删除所有 on* 事件属性；URL 类属性只允许 http / https 协议，拦截 `javascript:`、`data:`；style 属性要么删掉，要么只允许安全的 CSS 属性。<br>工具：前端 DOMPurify，后端 jsoup 的 Safelist、OWASP Java HTML Sanitizer；再加 CSP 兜底。 |
| Web 安全 | S-03 | 为什么白名单比黑名单可靠？ | 原题 | S | 本质原因 | ①举一个绕过黑名单的例子？ | **结论：本质是集合的开放与封闭——黑名单要枚举所有"坏的"，而攻击写法是无限的开放集合，漏一个就被绕过；白名单只放行已知"好的"，是有限的封闭集合，未知的一律拒绝。**<br>绕过黑名单的方式层出不穷：大小写（`<ScRipt>`）、编码（HTML 实体、URL 编码）、新标签新事件（`<svg onload>`、`<img onerror>`）、浏览器的容错解析、嵌套拼接（`<scr<script>ipt>` 过滤一次后又拼成 `<script>`）。<br>浏览器出现新特性时，黑名单默认放行，白名单默认拦截。<br>这对应安全设计的"默认拒绝"（fail-safe defaults）原则；代价是白名单要维护一份业务需要的标签清单。 |
| Web 安全 | S-04 | SQL 注入是什么？怎么防？ | 原题 | S | 方案 | ①预编译为什么能防注入？②ORDER BY 动态排序怎么防？ | **结论：SQL 注入是用户输入被拼接进 SQL 语句并被当成代码执行；根本防御是参数化查询（预编译）。**<br>例：后端拼接 `"select * from user where name = '" + name + "'"`，输入 `' or '1'='1` 能绕过登录，输入 `'; drop table user; -- ` 能删表。<br>防御：PreparedStatement 参数化查询；MyBatis 用 #{} 不用 ${}；用 ORM 框架的参数绑定。<br>必须拼接的位置（表名、排序字段）用白名单校验；输入做类型和格式校验。<br>纵深防御：数据库账号最小权限；不把数据库报错信息返回给前端；部署 WAF。 |
| Web 安全 | S-05 | 防御 XSS 的通用手段有哪些？ | 同点变体 | S | 方案 | ①Vue 的 v-html 为什么危险？ | **结论：核心是"输出编码"——不可信数据输出到页面时按所在上下文转义，再叠加 CSP、HttpOnly 等纵深防御。**<br>输出编码：HTML 内容中转义 `< > & " '`；属性、JS、URL 上下文用各自的编码规则。<br>框架默认转义：Vue 的 `{{ }}`、React 的 JSX 都会自动转义；慎用 v-html、dangerouslySetInnerHTML、innerHTML。<br>纵深防御：Cookie 设置 HttpOnly；配置 CSP 限制脚本来源；输入校验（长度、格式）。<br>富文本场景用白名单过滤。 |
| Web 安全 | S-06 | CSP 是什么？怎么防 XSS？ | 同点变体 | S | 原理 | ①禁止内联脚本后，必须用的内联脚本怎么办？ | **结论：CSP（内容安全策略）通过响应头告诉浏览器哪些来源的脚本、样式、图片可以加载执行，注入的脚本即使出现在页面里也不会运行。**<br>配置：响应头 `Content-Security-Policy: script-src 'self' https://cdn.example.com`，或用 meta 标签。<br>启用 script-src 后默认禁止内联脚本和 eval，直接挡住大部分注入的 `<script>` 和 onerror 事件。<br>必须用内联脚本时，用 nonce（每次请求生成的随机值）或 hash 放行指定的脚本。<br>上线前可先用 Content-Security-Policy-Report-Only 只上报不拦截，观察后再正式启用。 |
| Web 安全 | S-07 | Cookie 设置了 HttpOnly，能完全防住 XSS 吗？ | 同点变体 | S | 本质原因 | ①Token 存 localStorage 和存 Cookie 哪个更安全？ | **结论：不能。HttpOnly 只阻止 JS 读取 Cookie，防的是"XSS 之后偷 Cookie"，阻止不了脚本被注入和执行。**<br>脚本照样能在页面里以用户身份发请求（浏览器会自动带上 Cookie）、读取页面上的数据、篡改页面钓鱼、记录键盘输入。<br>所以 HttpOnly 只是降低危害的手段，防 XSS 还是要靠输出编码、白名单过滤和 CSP。 |
| Web 安全 | S-08 | 预编译为什么能防 SQL 注入？ | 同点变体 | S | 本质原因 | ①占位符能代替表名吗？ | **结论：本质是"代码和数据分离"——SQL 的结构先编译固定，参数之后只作为值传入，不会再被当成 SQL 语法解析。**<br>过程：带 `?` 的 SQL 模板先交给数据库解析、编译成执行计划，此时语法结构已经确定。<br>执行时传入的参数只填充占位符，即使内容是 `' or 1=1`，也只是一个普通的字符串值。<br>MySQL 驱动默认（`useServerPrepStmts=false`）是在客户端对参数转义后再拼接发送，效果同样是参数只被当作值处理。<br>限制：占位符只能代替值，不能代替表名、列名、ORDER BY 字段、SQL 关键字，这些位置要用白名单。 |
| Web 安全 | S-09 | ORDER BY 动态排序、LIKE 模糊查询怎么写才能防注入？ | 同点变体 | S | 方案 | ①ORDER BY 为什么不能用 #{}？ | **结论：ORDER BY 字段走白名单映射，LIKE 用 #{} 配合拼接函数，不让用户输入直接进入 SQL 结构。**<br>ORDER BY：#{} 会给值加上引号，变成按常量排序、不起作用，只能用 ${}；所以前端只传排序标识，后端用 Map 或枚举映射成固定列名，不在白名单内就用默认排序。<br>LIKE：写 `like concat('%', #{kw}, '%')`，或在 Java 里拼好 `"%" + kw + "%"` 再用 #{} 传入；不要写 `'%${kw}%'`。<br>IN 查询：用 `<foreach>` 生成多个 #{}，不要拼接字符串。 |
| Web 安全 | S-10 | CSRF 是什么？怎么防？ | 领域高频 | A | 原理 | ①SameSite 的 Strict 和 Lax 有什么区别？②Token 放在请求头里为什么能防 CSRF？ | **结论：CSRF（跨站请求伪造）是攻击者诱导已登录的用户访问恶意页面，利用浏览器自动携带 Cookie 的特性，以用户身份发起请求。**<br>例：恶意页面里放 `<img src="https://bank.example/transfer?to=hacker&amount=1000">`，用户打开页面就发出了转账请求。<br>防御：CSRF Token（服务端下发随机值，请求时放在表单或请求头里校验，攻击者拿不到）；Cookie 设置 SameSite=Lax / Strict；校验 Referer / Origin 请求头；关键操作二次验证。<br>JWT 放在 Authorization 请求头而不是 Cookie 里时，浏览器不会自动携带，天然不受 CSRF 影响。<br>Chrome 80 起，没有声明 SameSite 的 Cookie 默认按 Lax 处理。 |
| Web 安全 | S-11 | XSS 和 CSRF 有什么区别？ | 领域高频 | A | 原理 | ①网站有 XSS 漏洞时，CSRF Token 还有用吗？ | **结论：XSS 是在目标站点里执行攻击者的脚本，CSRF 是借用户的登录态从别的站点发请求；XSS 能读到页面数据，CSRF 拿不到响应，只能"盲发"请求。**<br>发生位置：XSS 在受害网站内部执行；CSRF 从第三方站点发起。<br>依赖条件：XSS 依赖网站存在注入漏洞；CSRF 依赖浏览器自动带 Cookie，且服务端只靠 Cookie 认证。<br>防御：XSS 靠输出编码、白名单过滤、CSP；CSRF 靠 Token、SameSite、校验来源。<br>有 XSS 时 CSRF Token 会失效，因为脚本在同源页面里能直接读到 Token。 |
| Web 安全 | S-12 | 什么是越权漏洞？怎么防？ | 领域高频 | A | 方案 | ①只在前端隐藏按钮能防越权吗？ | **结论：越权是用户访问或操作了自己没有权限的资源，分水平越权（同级用户互相访问数据）和垂直越权（普通用户执行管理员操作）。**<br>水平越权例子：接口 `/order?id=1001` 改成 1002 就能看到别人的订单。<br>防御：每个接口都在服务端校验"当前登录用户是否拥有这个资源"，查询时带上 user_id 条件，不信任前端传来的用户 ID。<br>垂直越权：用 RBAC 权限框架（Spring Security、Sa-Token、Shiro）在接口层统一做角色校验。<br>前端隐藏按钮只是用户体验，不是安全措施。 |
| Web 安全 | S-13 | 用户密码怎么存储才安全？ | 领域高频 | B | 方案 | ①为什么不能用 MD5？②盐需要保密吗？ | **结论：用加盐的慢哈希算法存储，如 BCrypt、Argon2、PBKDF2；绝不能明文或用可逆加密存储。**<br>单纯的 MD5 / SHA：计算太快，能被彩虹表和 GPU 暴力破解。<br>加盐：每个用户一个随机盐，相同密码的哈希值也不同，彩虹表失效；盐可以和哈希值存在一起，不需要保密。<br>慢哈希：BCrypt 有可调的工作因子，故意让单次计算变慢，提高暴力破解的成本；Spring Security 的 BCryptPasswordEncoder 可以直接用。<br>传输过程用 HTTPS 保护。 |
| Web 安全 | S-14 | 文件上传漏洞怎么防？ | 领域高频 | B | 方案 | ①只校验文件扩展名够不够？ | **结论：核心是"上传的文件不能被当成代码执行"，从校验、存储、访问三个环节防御。**<br>校验：扩展名白名单 + 文件头魔数校验 + 大小限制；不信任前端校验和请求里的 Content-Type。<br>存储：重命名为随机文件名；存到非 Web 目录或对象存储，上传目录禁止执行脚本。<br>访问：用独立域名或下载接口返回，设置 `Content-Disposition: attachment`，防止浏览器直接解析 HTML / SVG。<br>图片可以二次渲染压缩，去掉嵌入的恶意代码。 |

| MySQL | M-10 | 事务的 ACID 是什么？InnoDB 分别靠什么实现？ | 领域高频 | A | 原理 | ①为什么说一致性是目的，其他三个是手段？ | **结论：原子性靠 undo log，持久性靠 redo log，隔离性靠锁和 MVCC，一致性是前三者共同保证的目标。**<br>原子性（A）：要么全部成功，要么全部回滚；undo log 记录反向操作，用于回滚。<br>一致性（C）：事务前后数据都满足约束和业务规则。<br>隔离性（I）：并发事务互不干扰；读靠 MVCC，写靠行锁。<br>持久性（D）：提交后数据不丢；redo log 采用 WAL（先写日志再写数据页），宕机后用 redo log 恢复。 |

| MySQL | M-14 | InnoDB 有哪些行锁？RR 下怎么防止幻读？ | 领域高频 | B | 原理 | ①什么情况下行锁的效果等同于锁全表？ | **结论：行锁有记录锁、间隙锁、临键锁（Next-Key Lock = 记录锁 + 间隙锁）；RR 下当前读用临键锁同时锁住记录和间隙，阻止其他事务插入。**<br>记录锁：锁单条索引记录。间隙锁：锁两条记录之间的间隙，只在 RR 下存在，作用是防插入。<br>加锁的对象是索引：where 条件没走索引时会扫描全表，给扫到的所有记录加锁，效果等同锁表。<br>唯一索引上的等值查询命中记录时，临键锁退化为记录锁。<br>`select ... for update`、update、delete 是当前读，要加锁；普通 select 是快照读，不加锁。 |

| Agent | A-09 | Agent 调用工具失败时怎么处理？ | 同点变体 | S | 方案 | ①哪些错误适合重试，哪些不适合？ | **结论：按错误类型分别处理：临时错误重试，参数错误让模型修正，不可恢复的错误换方案或上报。**<br>临时错误（超时、限流 429、5xx）：指数退避重试，设置最大次数。<br>参数错误（4xx、校验失败）：把具体的错误信息作为工具结果返回给模型，让它修正参数。<br>权限不足、资源不存在：不重试，换工具或换路径，或者告知用户。<br>全程记录调用日志，失败次数计入终止条件。 |

| Agent | A-11 | 什么是 ReAct 模式？ | 领域高频 | A | 原理 | ①ReAct 和 Plan-and-Execute 有什么区别？ | **结论：ReAct（Reasoning + Acting）让模型交替进行"思考 → 行动 → 观察"，根据每一步的观察结果决定下一步。**<br>Thought：分析当前情况，决定下一步做什么。Action：调用某个工具。Observation：拿到工具返回的结果。<br>不断循环，直到模型判断可以给出最终答案。<br>优点：推理过程可见；能根据中间结果动态调整，减少凭空编造。<br>缺点：每一步都要调用模型，步骤多时慢、成本高，也容易陷入循环，需要终止条件。 |
| Agent | A-12 | Agent 和 Workflow（工作流）有什么区别？怎么选？ | 领域高频 | A | 方案 | ①Dify、Coze 里的工作流属于哪一种？ | **结论：Workflow 的执行路径由开发者预先编排好，Agent 的执行路径由模型在运行时自主决定。**<br>Workflow：步骤固定、结果可预测、易调试、成本可控，适合流程明确的任务（如审批、固定格式的报告生成）。<br>Agent：灵活，能处理开放性问题，但结果不稳定、成本高、难调试。<br>选择：能用工作流解决的优先用工作流；路径无法提前确定时才用 Agent；实际项目常组合使用，在工作流的某个节点里放一个 Agent。 |
| Agent | A-13 | Agent 怎么做任务规划？有哪些常见模式？ | 领域高频 | B | 原理 | ①计划执行到一半发现走不通，怎么办？ | **结论：常见模式有 ReAct（边想边做）、Plan-and-Execute（先规划再执行）、Reflexion（执行后反思改进）。**<br>Plan-and-Execute：先由规划器生成完整的步骤列表，执行器逐步执行，出问题时重新规划；适合步骤多的复杂任务。<br>Reflexion / 自我反思：执行完后让模型评估结果、总结失败原因，带着反思重新尝试。<br>任务拆解：把大目标拆成可验证的子任务，每个子任务都有明确的完成标准。 |
| Agent | A-14 | 多 Agent 协作有哪些模式？ | 领域高频 | B | 原理 | ①多 Agent 比单 Agent 好在哪？代价是什么？ | **结论：常见的有主从（Supervisor）模式、流水线模式、对等协作 / 辩论模式。**<br>主从：主 Agent 拆分任务、分派给专职的子 Agent，再汇总结果；最常用。<br>流水线：各 Agent 按固定顺序处理，前一个的输出是后一个的输入（如需求 → 编码 → 测试）。<br>辩论 / 评审：多个 Agent 各自给方案或互相审查，提升结果质量。<br>好处是上下文隔离、职责专一；代价是通信开销大、token 成本明显增加、协调出错时难排查。 |
| Agent | A-15 | 怎么评估一个 Agent 的效果？ | 领域高频 | B | 方案 | ①没有标准答案的任务怎么评？ | **结论：从结果、过程、成本三个维度，用固定的测试集持续评估。**<br>结果：任务成功率、答案准确率；有标准答案的自动比对，开放性任务用 LLM-as-Judge 加人工抽检。<br>过程：工具调用是否正确、用了多少步、有没有无效循环、有没有越权操作。<br>成本：平均 token 消耗、耗时、费用。<br>每次改提示词或换模型后跑一遍回归测试集，防止效果退化。 |
| Agent | A-16 | Agent 执行高风险操作（删数据、转账、发邮件）时怎么控制风险？ | 领域高频 | B | 方案 | ①加了人工确认，会不会让 Agent 失去意义？ | **结论：最小权限 + 人工确认 + 隔离环境 + 可审计，不把安全寄托在模型的自觉上。**<br>最小权限：只给完成任务必需的工具和权限，读写分离，写操作限定范围。<br>人工确认（Human-in-the-loop）：不可逆的操作执行前，把具体内容展示给用户确认。<br>隔离：代码执行放进沙箱 / 容器；防提示词注入，外部内容不能触发高风险操作。<br>审计：记录每次工具调用的参数和结果，支持追溯和回滚。 |
| Agent | A-17 | 工具很多（几十上百个）时，怎么让 Agent 选对工具？ | 领域高频 | B | 方案 | ①工具描述怎么写？ | **结论：不要把所有工具一次性塞给模型，先缩小范围，再让模型选。**<br>路由：先做意图分类，按类别只暴露相关的工具子集；或者用向量检索，按问题召回 Top-K 个工具描述。<br>分层：把相关的工具交给专门的子 Agent，主 Agent 只负责选子 Agent。<br>描述质量：名称语义清晰；描述写明用途、适用和不适用的场景、参数含义和示例；相似的工具写清楚区别。 |

| Redis | RD-04 | 缓存穿透、缓存击穿、缓存雪崩分别是什么？怎么解决？ | 领域高频 | B | 方案 | ①布隆过滤器有什么缺点？ | **结论：穿透是查不存在的数据，击穿是热点 key 过期，雪崩是大量 key 同时过期或 Redis 宕机。**<br>穿透：请求的数据缓存和数据库里都没有，每次都打到数据库；解决：缓存空值（设置较短过期时间）、布隆过滤器拦截、参数校验。<br>击穿：某个热点 key 过期的瞬间，大量请求打到数据库；解决：互斥锁，只让一个线程重建缓存；热点 key 逻辑过期（不设 TTL，后台异步更新）。<br>雪崩：解决：过期时间加随机值打散；Redis 集群保证高可用；限流降级；多级缓存。<br>布隆过滤器有误判（判断存在时实际不一定存在），而且不支持删除元素。 |
| Redis | RD-05 | 怎么保证缓存和数据库的一致性？ | 领域高频 | B | 方案 | ①为什么是删缓存而不是更新缓存？②延迟双删的延迟时间怎么定？ | **结论：常用"先更新数据库，再删除缓存"（Cache Aside），配合过期时间兜底，追求最终一致性。**<br>删而不更新：并发写时更新缓存会写入旧值；而且很多缓存值需要计算，删掉等下次读时再加载更省。<br>不先删缓存：删完缓存到更新数据库之间，读请求会把旧值重新写回缓存。<br>删除失败的补偿：重试；用消息队列重试删除；订阅 binlog（Canal）异步删除缓存。<br>延迟双删：先删缓存 → 更新数据库 → 延迟几百毫秒再删一次，处理并发读把旧值写回缓存的情况。 |
| Redis | RD-06 | Redis 的过期删除策略和内存淘汰策略是什么？ | 领域高频 | B | 原理 | ①LRU 和 LFU 有什么区别？ | **结论：过期删除用"惰性删除 + 定期删除"；内存满了按 maxmemory-policy 淘汰。**<br>惰性删除：访问 key 时才检查是否过期，过期就删。定期删除：每秒若干次，随机抽查一批设置了过期时间的 key，删除其中已过期的。<br>8 种淘汰策略：noeviction（默认，内存满时写入报错）；allkeys-lru / allkeys-lfu / allkeys-random；volatile-lru / volatile-lfu / volatile-random / volatile-ttl（只在设置了过期时间的 key 中淘汰）。<br>LRU 淘汰最久没被访问的，LFU（4.0 起）淘汰访问频率最低的；Redis 用的都是基于随机采样的近似算法。 |
| Redis | RD-07 | 怎么用 Redis 实现分布式锁？ | 领域高频 | B | 方案 | ①锁过期了业务还没执行完怎么办？②Redisson 的看门狗是什么？ | **结论：`SET lock_key 唯一值 NX PX 30000` 加锁，释放时用 Lua 脚本"先判断是自己的锁，再删除"。**<br>NX 保证互斥，PX 设置过期时间，防止持有者宕机导致死锁；加锁和设置过期必须是一条原子命令。<br>唯一值（UUID + 线程 ID）防止误删别人的锁；判断和删除放在 Lua 脚本里保证原子性。<br>锁续期：Redisson 的看门狗在没有指定 leaseTime 时，默认锁 30 秒过期、每 10 秒自动续期，持有者宕机后不再续期。<br>Redisson 还支持可重入（用 Hash 记录重入次数）；主从切换会导致锁丢失，强一致场景考虑 RedLock 或 ZooKeeper。 |
| Redis | RD-08 | Redis 的主从复制、哨兵、集群分别解决什么问题？ | 领域高频 | B | 原理 | ①Cluster 为什么是 16384 个槽？ | **结论：主从解决读扩展和数据备份，哨兵解决主节点故障时的自动切换，集群解决数据量和写压力的水平扩展。**<br>主从：第一次全量同步（发送 RDB），之后增量同步写命令；从节点默认只读。<br>哨兵：监控主从节点，主节点下线时多个哨兵投票选出新的主节点，并通知客户端。<br>Cluster：用 CRC16(key) % 16384 把数据分到槽，槽分配给多个主节点；每个主节点配从节点做故障转移；客户端访问错了节点会收到 MOVED 重定向。 |
| Redis | RD-09 | ZSet 的底层是什么结构？为什么用跳表而不是红黑树？ | 领域高频 | B | 原理 | ①跳表的查询时间复杂度是多少？ | **结论：元素少时用 listpack（7.0 之前是 ziplist），元素多时用"跳表 + 哈希表"。**<br>切换条件：元素个数超过 128，或单个元素超过 64 字节（都可以配置）。<br>跳表：多层有序链表，上层是下层的"索引"，查询、插入、删除平均 O(log n)；哈希表负责按成员 O(1) 查分数。<br>选跳表的原因：范围查询（ZRANGE）找到起点后沿底层链表遍历即可，比红黑树简单；实现和调试更简单；插入时只改局部指针，不需要旋转。 |
| Redis | RD-10 | 什么是大 Key、热 Key？怎么处理？ | 领域高频 | B | 方案 | ①怎么发现大 Key？ | **结论：大 Key 是 value 过大的 key，热 Key 是访问量过于集中的 key，两者都会让单个节点成为瓶颈。**<br>大 Key 的危害：读写时阻塞单线程；占满网络带宽；删除时阻塞（用 UNLINK 异步删除）；集群数据倾斜。<br>发现：`redis-cli --bigkeys`、`MEMORY USAGE key`、离线分析 RDB 文件。<br>处理：大 Key 拆成多个小 key、压缩 value；热 Key 用本地缓存（Caffeine）分担，或给 key 加随机后缀拆成多份分散到不同节点，或做读写分离。 |

| Java 并发 | CC-03 | synchronized 的原理是什么？锁升级的过程是怎样的？ | 领域高频 | B | 原理 | ①现在的 JDK 里还有偏向锁吗？ | **结论：synchronized 基于对象头的 Mark Word 和 Monitor 实现；JDK 6 起引入锁升级：无锁 → 偏向锁 → 轻量级锁 → 重量级锁。**<br>字节码：同步代码块用 monitorenter / monitorexit；同步方法用 ACC_SYNCHRONIZED 标志。<br>偏向锁：只有一个线程访问时，Mark Word 记录这个线程 ID，之后它再进入无需 CAS。轻量级锁：多个线程交替访问时，用 CAS 把 Mark Word 替换为指向栈中锁记录的指针，失败就自旋。重量级锁：竞争激烈时膨胀为 Monitor，线程阻塞挂起。<br>JDK 15 起偏向锁默认禁用并被标记废弃（JEP 374）。 |

| Java 并发 | CC-06 | AQS 是什么？原理是怎样的？ | 领域高频 | B | 原理 | ①ReentrantLock 是怎么基于 AQS 实现可重入的？ | **结论：AQS（AbstractQueuedSynchronizer）是构建锁和同步器的框架，核心是一个 volatile int state 加一个 FIFO 双向等待队列（CLH 队列的变体）。**<br>state：表示同步状态，用 CAS 修改；在 ReentrantLock 中表示重入次数，在 Semaphore 中表示剩余许可数。<br>获取失败的线程被包装成节点加入队尾，通过 LockSupport.park 挂起；释放时唤醒后继节点。<br>子类只需实现 tryAcquire / tryRelease（独占模式）或 tryAcquireShared / tryReleaseShared（共享模式）。<br>基于 AQS 实现的有：ReentrantLock、ReentrantReadWriteLock、Semaphore、CountDownLatch。 |
| Java 并发 | CC-07 | CAS 是什么？ABA 问题怎么解决？ | 领域高频 | B | 原理 | ①CAS 还有什么缺点？ | **结论：CAS（比较并交换）是 CPU 提供的原子指令：内存值等于期望值时才更新为新值，否则失败重试；它是乐观锁的实现方式。**<br>Java 中通过 Unsafe 类调用，AtomicInteger 等原子类都基于 CAS + 自旋。<br>ABA 问题：值从 A 改成 B 又改回 A，CAS 认为没有变化；用 AtomicStampedReference 加版本号解决。<br>其他缺点：竞争激烈时自旋浪费 CPU（高并发计数用 LongAdder 分段累加）；只能保证单个变量的原子操作。 |
| Java 并发 | CC-08 | 线程池有哪些核心参数？任务提交后的执行流程是怎样的？ | 领域高频 | B | 原理 | ①为什么不建议用 Executors 创建线程池？②核心线程数怎么设置？ | **结论：7 个参数：核心线程数、最大线程数、空闲线程存活时间、时间单位、任务队列、线程工厂、拒绝策略。**<br>流程：线程数小于核心数就新建线程 → 否则放进队列 → 队列满了且线程数小于最大数，就新建非核心线程 → 都满了执行拒绝策略。<br>拒绝策略：AbortPolicy（默认，抛异常）、CallerRunsPolicy（由提交任务的线程自己执行）、DiscardPolicy、DiscardOldestPolicy。<br>不用 Executors：FixedThreadPool 和 SingleThreadExecutor 的队列是无界的，会 OOM；CachedThreadPool 的最大线程数没有上限，会创建大量线程。<br>线程数参考：CPU 密集型 N+1，IO 密集型 2N 左右（N 为核数），最终以压测为准。 |
| Java 并发 | CC-09 | ThreadLocal 的原理是什么？为什么会内存泄漏？ | 领域高频 | B | 原理 | ①在线程池里使用 ThreadLocal 有什么坑？ | **结论：每个 Thread 内部有一个 ThreadLocalMap，以 ThreadLocal 对象为 key、存的值为 value，所以每个线程拿到的都是自己的那一份。**<br>泄漏原因：Entry 的 key 是弱引用，ThreadLocal 外部的强引用没了以后 key 被回收成 null，但 value 是强引用，只要线程不结束就回收不掉。<br>线程池里的线程长期存活，泄漏会一直存在，还会让下一个任务读到上一个任务留下的数据。<br>解决：用完在 finally 里调用 remove()。<br>场景：保存当前登录用户信息、数据库连接、SimpleDateFormat 等非线程安全对象。 |
| Java 并发 | CC-10 | 死锁产生的条件是什么？怎么避免和排查？ | 领域高频 | B | 方案 | ①线上怎么确认发生了死锁？ | **结论：互斥、占有并等待、不可抢占、循环等待四个条件同时满足才会死锁，破坏其中任意一个就能避免。**<br>避免：所有线程按相同的顺序加锁（破坏循环等待）；用 tryLock 设置超时（破坏不可抢占）；一次性申请所有资源（破坏占有并等待）。<br>排查：`jps` 找到进程 → `jstack <pid>`，输出末尾会提示 "Found one Java-level deadlock"，并列出互相等待的线程和锁；也可以用 jconsole，或 Arthas 的 `thread -b`。 |

| 设计模式 | DP-09 | 责任链模式是什么？在哪里用到？ | 领域高频 | B | 原理 | ①FilterChain 是怎么把多个过滤器串起来的？ | **结论：把多个处理者连成一条链，请求沿着链传递，每个处理者决定自己处理还是交给下一个，让请求的发送者和处理者解耦。**<br>应用：Servlet 的 FilterChain（调用 chain.doFilter 交给下一个）；Spring MVC 的拦截器链；Spring Security 的过滤器链；Netty 的 ChannelPipeline。<br>业务场景：审批流（组长 → 经理 → 总监）；下单前的多重校验（参数 → 库存 → 风控）。<br>新增一个处理环节，只需加一个处理者并调整链的顺序。 |

### 10.7 计算机网络

| 领域 | 编号 | 题目 | 类型（原题 / 同点变体 / 领域高频） | 优先级（S / A / B） | 要懂到哪一层（定义 / 原理 / 方案 / 本质原因） | 可能的追问（1~2 个） | 答案要点（≤ 5 行，先一句话结论） |
|---|---|---|---|---|---|---|---|
| 计算机网络 | NET-01 | TCP 三次握手的过程是怎样的？为什么是三次而不是两次？ | 领域高频 | B | 原理 | ①第三次握手的 ACK 丢了会怎样？②什么是 SYN 洪水攻击？ | **结论：三次握手让双方都确认自己和对方的收发能力正常，并同步双方的初始序列号；两次握手无法阻止历史连接请求造成错误连接。**<br>过程：客户端发 SYN（seq=x）→ 服务端回 SYN+ACK（seq=y, ack=x+1）→ 客户端发 ACK（ack=y+1）；状态依次为 SYN_SENT → SYN_RCVD → ESTABLISHED。<br>不是两次的原因：旧的 SYN 延迟到达时，两次握手下服务端一回复就建立了连接，白白浪费资源；三次握手时客户端能识别出这是历史连接，发 RST 终止。<br>初始序列号随机生成，双方都需要确认对方的序列号。 |
| 计算机网络 | NET-02 | TCP 四次挥手的过程是怎样的？TIME_WAIT 为什么要等 2MSL？ | 领域高频 | B | 原理 | ①服务器上出现大量 TIME_WAIT 怎么办？ | **结论：TCP 是全双工的，两个方向要分别关闭，所以是四次；TIME_WAIT 等 2MSL 是为了保证最后一个 ACK 能送达，并让旧连接的报文在网络中消失。**<br>过程：主动方发 FIN → 被动方回 ACK（此时被动方还能继续发数据）→ 被动方发 FIN → 主动方回 ACK，进入 TIME_WAIT。<br>2MSL：如果最后的 ACK 丢了，被动方重发的 FIN 能在 2MSL 内到达并被重新确认；同时让本连接残留的报文过期，避免被新连接误收。<br>大量 TIME_WAIT：出现在主动关闭的一方，短连接频繁时常见；改用长连接或连接池，开启 tcp_tw_reuse（作为客户端发起连接时复用）。 |
| 计算机网络 | NET-03 | TCP 和 UDP 有什么区别？ | 领域高频 | B | 定义 | ①怎么基于 UDP 实现可靠传输？ | **结论：TCP 面向连接、可靠、面向字节流；UDP 无连接、不可靠、面向报文，开销小、实时性好。**<br>TCP：三次握手建立连接，有确认、重传、流量控制、拥塞控制；首部至少 20 字节；只支持一对一。<br>UDP：首部 8 字节；不保证送达和顺序；支持一对多、广播。<br>场景：TCP 用于 HTTP/1.1、HTTP/2、文件传输、邮件；UDP 用于音视频通话、直播、DNS、游戏；HTTP/3 的 QUIC 基于 UDP，在应用层实现可靠传输。 |
| 计算机网络 | NET-04 | TCP 是怎么保证可靠传输的？ | 领域高频 | B | 原理 | ①流量控制和拥塞控制有什么区别？ | **结论：靠序列号与确认应答、超时重传、滑动窗口流量控制、拥塞控制共同保证。**<br>序列号和 ACK：保证数据有序、不重复，接收方确认已收到的字节。<br>重传：超时重传；收到 3 个重复 ACK 时触发快速重传。<br>流量控制：接收方通过窗口大小告诉发送方自己还能收多少，防止接收方处理不过来。<br>拥塞控制：防止把网络打满，四个算法：慢启动、拥塞避免、快重传、快恢复。 |
| 计算机网络 | NET-05 | HTTP/1.0、1.1、2、3 有什么区别？ | 领域高频 | B | 原理 | ①什么是队头阻塞？HTTP/2 解决了吗？ | **结论：1.1 引入长连接，2 引入二进制分帧和多路复用，3 改用基于 UDP 的 QUIC，解决了 TCP 层的队头阻塞。**<br>HTTP/1.0：每个请求新建一个 TCP 连接。HTTP/1.1：默认长连接（keep-alive）；管道化基本没被使用，同一连接上的请求要排队（应用层队头阻塞）。<br>HTTP/2：二进制分帧，一个连接上多个请求交错并发（多路复用）；HPACK 头部压缩；服务器推送。但 TCP 丢包时所有流都要等重传（TCP 层队头阻塞）。<br>HTTP/3：基于 QUIC（UDP），流之间相互独立，丢包只影响单个流；内置 TLS 1.3，建连更快，支持连接迁移。 |
| 计算机网络 | NET-06 | HTTPS 是怎么保证安全的？TLS 握手的过程是怎样的？ | 领域高频 | B | 原理 | ①为什么不全程用非对称加密？②怎么防止中间人攻击？ | **结论：HTTPS = HTTP + TLS，用非对称加密交换密钥、对称加密传输数据、数字证书验证服务端身份。**<br>TLS 1.2（ECDHE）：ClientHello（随机数、支持的加密套件）→ ServerHello + 证书 + 服务端 DH 参数 → 客户端校验证书并发送客户端 DH 参数 → 双方算出相同的会话密钥 → 之后用对称加密通信；共 2 个 RTT。<br>TLS 1.3：精简为 1 个 RTT，只保留具备前向安全性的密钥交换算法。<br>证书：CA 用私钥对服务端公钥和域名签名，浏览器用内置的 CA 公钥验签，防止中间人冒充。<br>不全程用非对称加密：计算太慢，对称加密的性能高得多。 |
| 计算机网络 | NET-07 | 从浏览器输入 URL 到页面显示，中间发生了什么？ | 领域高频 | B | 原理 | ①浏览器渲染中的重排和重绘有什么区别？ | **结论：URL 解析 → DNS 解析 → 建立 TCP（和 TLS）连接 → 发送 HTTP 请求 → 服务器处理并响应 → 浏览器解析渲染 → 连接复用或关闭。**<br>DNS：浏览器缓存 → 操作系统缓存 / hosts → 本地 DNS 服务器 → 根域名服务器 → 顶级域服务器 → 权威域名服务器。<br>服务端：经过 CDN / 负载均衡（Nginx）→ 应用服务器 → 数据库 / 缓存。<br>渲染：解析 HTML 生成 DOM 树、解析 CSS 生成 CSSOM → 合成渲染树 → 布局（Layout）→ 绘制（Paint）→ 合成显示；遇到同步 script 会阻塞 HTML 解析。<br>重排是几何属性变化、重新计算布局；重绘只改外观；重排一定会触发重绘。 |
| 计算机网络 | NET-08 | GET 和 POST 有什么区别？ | 领域高频 | B | 定义 | ①GET 请求能带请求体吗？ | **结论：语义上 GET 用于获取资源，是安全且幂等的；POST 用于提交数据，不幂等。**<br>参数：GET 的参数通常放在 URL 里，长度受浏览器和服务器限制；POST 的参数放在请求体里。<br>缓存：GET 能被浏览器缓存、收藏为书签；POST 默认不缓存。<br>安全性：POST 的参数不显示在 URL 中，但明文传输时两者一样不安全，要靠 HTTPS。<br>规范上 GET 可以带请求体，但语义未定义，很多服务器和代理会忽略它，实际开发中不要这样用。 |
| 计算机网络 | NET-09 | 常见的 HTTP 状态码有哪些？ | 领域高频 | B | 定义 | ①502 和 504 有什么区别？ | **结论：1xx 信息、2xx 成功、3xx 重定向、4xx 客户端错误、5xx 服务端错误。**<br>2xx：200 成功、204 无内容、206 部分内容（断点续传）。<br>3xx：301 永久重定向、302 临时重定向、304 资源未修改（协商缓存命中）。<br>4xx：400 请求参数错误、401 未认证、403 没有权限、404 资源不存在、405 方法不允许、429 请求过多。<br>5xx：500 服务器内部错误、502 网关收到上游的无效响应（如后端服务挂了）、503 服务不可用、504 网关等待上游响应超时。 |
| 计算机网络 | NET-10 | 浏览器的 HTTP 缓存机制是怎样的？强缓存和协商缓存有什么区别？ | 领域高频 | B | 原理 | ①打包后的 JS 文件名为什么要带 hash？ | **结论：先判断强缓存，命中就不发请求；没命中再走协商缓存，由服务器判断资源有没有变化，没变就返回 304。**<br>强缓存：Cache-Control: max-age（HTTP/1.1，优先级高）、Expires（HTTP/1.0，绝对时间）；命中时状态码为 200（from memory / disk cache）。<br>协商缓存：Last-Modified / If-Modified-Since（精度到秒）；ETag / If-None-Match（内容指纹，更精确，优先级更高）。<br>no-cache 是每次都走协商缓存，no-store 才是完全不缓存。<br>前端实践：HTML 用协商缓存；带内容 hash 的 JS / CSS 设置长期强缓存，内容一变文件名就变。 |
