## 一、Java 基础

| 优先级 | 题目 | 共识 | 要懂到哪一层 | 可能的追问 | 答案要点 |
|---|---|---|---|---|---|
| **S** | 抽象类和接口怎么选 | 3/3 | 方案 | ①JDK 8 接口有了 default 方法后，两者还剩什么区别？②为什么 Java 类只能单继承，却能实现多个接口？ | **结论：表达"是什么"（is-a）且要共享状态和代码用抽象类；表达"能做什么"（能力、规范）用接口。**<br>抽象类：可以有成员变量、构造器、任意访问修饰符的方法；只能单继承。<br>接口：字段默认 public static final；JDK 8 加 default / static 方法，JDK 9 加 private 方法；可多实现，没有实例状态。<br>选法：对外定义契约优先用接口（面向接口编程，便于扩展和 mock）；多个子类有公共骨架代码用抽象类（模板方法）。<br>常见组合：接口定规范 + 抽象类给骨架实现，如 List → AbstractList → ArrayList。 |
| **S** | 静态代码块、实例代码块、构造方法的执行顺序 | 3/3 | 原理 | ①有父类时整体顺序是什么？②静态代码块执行几次、在什么时候执行？<br>①通过子类访问父类的静态字段，子类静态块执行吗？②`new A[10]` 会初始化 A 吗？ | ▸ **静态代码块、实例代码块、构造方法的执行顺序？**<br>**结论：静态先于实例，父类先于子类，代码块先于构造方法。**<br>有继承时：父类静态块 → 子类静态块 → 父类实例块 → 父类构造方法 → 子类实例块 → 子类构造方法。<br>静态块在类初始化阶段（`<clinit>`）执行，整个生命周期只执行一次；实例块每次 new 都执行。<br>实例块和实例变量赋值会被编译器插入到每个构造方法的 `super()` 之后，所以先于构造方法体执行。<br>同一级别的静态变量赋值与静态块，按源码书写顺序执行。<br>▸ **类在什么时候会被初始化？访问一个类的静态常量会执行它的静态代码块吗？**<br>**结论：只有"主动使用"才触发类初始化并执行静态块；访问编译期常量不会触发。**<br>主动使用：new、读写静态字段（编译期常量除外）、调用静态方法、Class.forName 反射、初始化子类时先初始化父类、main 方法所在的类。<br>被动引用不触发：`static final` 编译期常量在编译时已放进调用方的常量池；通过子类引用父类静态字段只初始化父类；`new A[10]` 不初始化 A。<br>`static final` 但值要运行时计算（如 `= new Random().nextInt()`）时会触发初始化。 |
| **S** | Java IO 模型有哪些；高并发短连接下 BIO 的问题 | 3/3 | 原理 | ①NIO 的 Selector 在 Linux 上底层靠什么？②Netty 为什么选 NIO 而不是 AIO？ | **结论：BIO 同步阻塞、NIO 同步非阻塞（IO 多路复用）、AIO 异步非阻塞；BIO 一个连接占一个线程，高并发短连接下线程开销会压垮服务。**<br>BIO：accept / read 都阻塞。NIO：Channel + Buffer + Selector，一个线程轮询多个连接的就绪事件。AIO：IO 完成后由系统回调通知。<br>BIO 短连接的问题：连接频繁建立断开 → 线程频繁创建销毁；每个线程栈默认 1MB，线程一多内存和上下文切换开销暴涨；改用线程池又受池大小限制，连接排队超时。<br>本质：线程数和连接数一一绑定，而线程大部分时间在阻塞等待或创建销毁，CPU 浪费在调度上。<br>NIO 让少量线程处理大量连接，Netty、Tomcat 的 NIO Connector 都基于它。 |
| **A** | == 和 equals 的区别；为什么重写 equals 要重写 hashCode | 3/3 | 原理 | ①hashCode 相同，equals 一定相同吗？ | **结论：== 比较基本类型的值或引用的地址；equals 比较对象内容（Object 的默认实现等同 ==，需要重写）。**<br>String、Integer 等类都重写了 equals，比较的是内容。<br>约定：equals 相等的两个对象，hashCode 必须相等；hashCode 相等，equals 不一定相等（哈希冲突）。<br>只重写 equals 不重写 hashCode：两个"相等"的对象放进 HashMap / HashSet 会落到不同的桶，导致重复存储、get 不到。 |
| **A** | HashMap 底层结构和 put 流程（JDK 7 / 8 区别） | 3/3 | 原理 | ①容量为什么是 2 的幂？②链表转红黑树的条件是什么？ | **结论：HashMap 是数组 + 链表（JDK 8 起加了红黑树），用 key 的 hash 定位桶，冲突时挂链表。**<br>put：`hash = h ^ (h >>> 16)` 扰动 → `(n - 1) & hash` 定位桶 → 空桶直接放；否则遍历比较 key，相同则覆盖，不同则插入。<br>JDK 7 头插法，多线程扩容会形成环形链表；JDK 8 改尾插法，链表长度超过 8 且数组长度 ≥ 64 时转红黑树（不足 64 先扩容），节点数 ≤ 6 时退回链表。<br>扩容：默认容量 16、负载因子 0.75，元素数超过阈值就翻倍；JDK 8 扩容时元素要么留在原位置，要么移到"原位置 + 旧容量"。<br>容量取 2 的幂：让 `(n - 1) & hash` 等价于取模，且分布均匀。 |
| **A** | HashMap 为什么线程不安全；ConcurrentHashMap 怎么保证安全 | 2/3 | 原理 | ①ConcurrentHashMap 的 key 和 value 为什么不能为 null？②size() 是怎么统计的？ | **结论：HashMap 的 put 和扩容没有任何同步；ConcurrentHashMap 在 JDK 7 用分段锁，JDK 8 用 CAS + synchronized 锁桶的头节点。**<br>HashMap 并发问题：JDK 7 扩容头插法形成环形链表，get 时死循环；JDK 7 / 8 都会出现数据覆盖丢失、size 不准。<br>JDK 7 的 CHM：Segment 数组（Segment 继承 ReentrantLock），默认 16 段，最多 16 个线程同时写。<br>JDK 8 的 CHM：取消 Segment，空桶用 CAS 放入，非空桶用 synchronized 锁住头节点，锁粒度细到单个桶；支持多线程协助扩容。<br>不允许 null：并发下 get 返回 null 时，无法区分是"key 不存在"还是"value 就是 null"。 |
| **A** | ArrayList 和 LinkedList 怎么选；ArrayList 怎么扩容 | 3/3 | 原理 | ①ArrayList 线程安全吗？用什么替代？ | **结论：ArrayList 底层是动态数组，随机访问 O(1)；LinkedList 是双向链表，随机访问 O(n)；绝大多数场景用 ArrayList。**<br>插入删除：ArrayList 在中间位置要移动后面的元素；LinkedList 只改指针，但要先遍历找到位置，实际不一定更快。<br>内存：LinkedList 每个节点多存前后两个指针，且节点分散，对 CPU 缓存不友好。<br>扩容：JDK 8 无参构造时是空数组，第一次 add 扩到 10；之后满了按 1.5 倍（`old + (old >> 1)`）扩容并用 Arrays.copyOf 复制。<br>两者都线程不安全；并发场景用 CopyOnWriteArrayList 或 Collections.synchronizedList。 |
| **A** | String、StringBuilder、StringBuffer 的区别 | 2/3 | 原理 | ①`String s = new String("abc")` 创建了几个对象？②JDK 9 里 String 的底层有什么变化？ | **结论：String 不可变；StringBuilder 可变、线程不安全、速度快；StringBuffer 可变、方法加了 synchronized、线程安全。**<br>不可变的原因：类被 final 修饰不能继承；内部数组是 private final，且没有对外暴露修改它的方法。<br>好处：可以缓存 hash 值、支持字符串常量池复用、天然线程安全、适合做 HashMap 的 key。<br>JDK 9 起底层由 char[] 改为 byte[] + coder（纯 Latin-1 字符串每个字符只占 1 字节），节省内存。<br>循环里拼接字符串用 StringBuilder，用 `+` 会反复创建对象。 |
| **A** | Java 异常体系；受检和非受检异常 | 3/3 | 定义 | ①try 里有 return，finally 还会执行吗？ | **结论：Throwable 下分 Error（JVM 严重错误，程序不处理）和 Exception；Exception 又分受检异常和运行时异常。**<br>Error：OutOfMemoryError、StackOverflowError。<br>受检异常（Checked）：IOException、SQLException 等，编译器强制 try-catch 或 throws 声明。<br>非受检异常：RuntimeException 及其子类，如 NullPointerException、IndexOutOfBoundsException，不强制处理。<br>try 里有 return 时 finally 照样执行（在返回值计算之后、方法真正返回之前）；finally 里写 return 会覆盖 try 的返回值，不要这样写。 |
| **B** | 重载和重写的区别 | 2/3 | 定义 | ①只有返回值不同能构成重载吗？ | **结论：重载是同一个类里方法名相同、参数不同，编译期决定调用哪个；重写是子类覆盖父类方法，运行期按实际对象类型决定（多态）。**<br>重载：参数类型、个数或顺序不同；和返回值、修饰符无关，只有返回值不同不算重载。<br>重写：方法名和参数列表相同；返回值相同或是其子类；访问权限不能更严格；抛出的受检异常不能更宽。<br>private、static、final 方法不能被重写；构造方法不能重写，但能重载。 |
| **B** | 泛型和类型擦除 | 2/3 | 原理 | ①`List<String>` 和 `List<Integer>` 的 getClass() 相等吗？②`? extends` 和 `? super` 有什么区别？ | **结论：泛型提供编译期类型检查；Java 泛型是伪泛型，编译后类型参数会被擦除成上界（默认 Object）。**<br>擦除后，运行时 `List<String>` 和 `List<Integer>` 是同一个 Class。<br>编译器在取值的地方自动插入强制类型转换，并生成桥接方法保证多态正确。<br>限制：不能 `new T()`；不能用基本类型做类型参数；不能对泛型类型做 instanceof。<br>PECS 原则：`? extends T` 适合只读（生产者），`? super T` 适合只写（消费者）。 |
| **B** | final 的作用（final / finally / finalize） | 2/3 | 原理 | `final` 修饰集合还能增删吗？引用对象属性能改吗？ | 结论：`final` 限制变量再次赋值、方法被重写或类被继承。<br>`final` 引用不能指向新对象，但对象内部可变属性仍可修改。<br>`final` 集合仍可增删元素；要禁止修改需使用不可变集合或防御性拷贝。 |
| **B** | 反射和动态代理 | 2/3 | 原理 | ①反射为什么比直接调用慢？ | **结论：反射是在运行时获取类的信息，并操作其字段、方法、构造器的能力，入口是 Class 对象。**<br>获取 Class 的三种方式：`类名.class`、`对象.getClass()`、`Class.forName("全限定名")`。<br>场景：Spring IoC 创建 Bean 和依赖注入、动态代理、MyBatis 结果映射、注解处理、JDBC 加载驱动。<br>缺点：绕过编译期检查；能通过 setAccessible 破坏封装；性能比直接调用差（方法查找、参数装箱、访问检查，且难以被 JIT 内联）。 |
| **B** | try-with-resources 怎么保证资源释放 | 1/3 | 原理 | 多个资源按什么顺序关闭？`close` 抛异常怎么办？ | 结论：实现 `AutoCloseable` 的资源会在 `try` 结束时自动关闭。<br>资源按声明顺序的逆序关闭；关闭异常会作为主异常的 suppressed exception 保存。<br>Java 7 起支持该语法，仍需处理主异常和资源关闭异常。 |
| **B** | Java 序列化 | 1/3 | 方案 | `serialVersionUID` 有什么作用？哪些字段不序列化？ | 结论：序列化是把对象状态转换为字节流，反序列化再恢复对象。<br>Java 原生序列化通常实现 `Serializable`，显式声明 `serialVersionUID` 控制兼容性。<br>`transient` 字段默认不参与原生序列化，生产接口优先使用明确的 JSON 或二进制协议。 |
| **B** | Java 是值传递还是引用传递 | 1/3 | 原理 | ①在方法里给对象参数重新赋值，外面的变量会变吗？ | **结论：Java 只有值传递；传对象时，传的是"引用的副本"。**<br>基本类型：传值的拷贝，方法内修改不影响外部。<br>引用类型：传地址的拷贝，方法内通过它修改对象的属性，外部能看到。<br>方法内把参数指向一个新对象，只改了副本，外部引用不变——这正说明它不是引用传递。 |
| **B** | 自动装箱拆箱、Integer 缓存池 | 1/3 | 原理 | ①`Integer a = 128, b = 128;` 那么 `a == b` 的结果是什么？ | **结论：装箱是基本类型自动转成包装类（调用 valueOf），拆箱是反过来（调用 xxxValue）。**<br>Integer.valueOf 对 -128 到 127 之间的值返回缓存对象，范围外每次 new 新对象。<br>所以 `Integer a = 127, b = 127` 时 `a == b` 为 true，换成 128 就是 false；包装类比较一律用 equals。<br>缓存上限可用 `-XX:AutoBoxCacheMax` 调大；Byte、Short、Long、Character（0 到 127）也有缓存，Float、Double 没有。<br>拆箱时对象为 null 会抛 NullPointerException。 |
| **B** | select、poll、epoll 的区别 | 1/3 | 原理 | ①epoll 的 LT 和 ET 模式有什么区别？ | **结论：epoll 只关注就绪的连接，不用每次全量拷贝和遍历，连接数大时性能远好于 select / poll；Java NIO 在 Linux 上默认用 epoll。**<br>select：fd 集合是位图，默认上限 1024；每次调用都把全部 fd 拷进内核并线性扫描。<br>poll：用 pollfd 数组，没有 1024 上限，但仍是全量拷贝 + 线性扫描。<br>epoll：epoll_ctl 注册一次，内核用红黑树管理 fd；就绪的 fd 放进就绪链表，epoll_wait 只返回就绪的那些。<br>LT（水平触发，默认）：只要可读就反复通知；ET（边缘触发）：状态变化时只通知一次，必须一次读完。 |
| **B** | 阻塞 / 非阻塞、同步 / 异步 IO 的含义 | 1/3 | 定义 | NIO 是异步 IO 吗？Selector 解决了什么？ | 结论：阻塞描述线程是否等待，异步描述结果是否由系统主动通知。<br>NIO 是同步非阻塞，线程仍需主动轮询就绪事件；AIO 才是异步。<br>`Selector` 把多个通道的就绪事件集中交给少量线程处理。 |
| **B** | 接口 default 方法；同名 default 方法冲突 | 1/3 | 原理 | ①父类的方法和接口 default 方法冲突时听谁的？ | **结论：default 方法（JDK 8）让接口能新增方法而不破坏已有实现类，解决的是接口演进的兼容问题。**<br>典型例子：JDK 8 给 Collection 加了 stream()、forEach()，老的实现类一行不用改。<br>两个接口的 default 方法同名同参：实现类必须重写，可以用 `A.super.method()` 指定调用其中一个。<br>类优先原则：父类中的方法优先于接口 default 方法；子接口的 default 方法优先于父接口的。 |
| **B** | Java 创建对象经历哪些步骤 | 1/3 | 原理 | 类加载和对象分配谁先发生？对象头里有什么？ | 结论：先检查类是否加载，再分配内存、初始化零值、设置对象头并执行初始化代码。<br>类未加载时会先完成加载、链接和初始化。<br>对象头包含标记字段、类型指针等，数组还包含长度信息。 |
| **B** | 类加载过程 | 1/3 | 原理 | 双亲委派解决什么问题？如何打破？ | 结论：类加载包括加载、验证、准备、解析和初始化。<br>双亲委派优先让父加载器尝试加载，避免核心类被自定义类覆盖。<br>线程上下文类加载器、OSGi 和应用服务器可按隔离需求打破委派。 |

| **S** | 对象在分代内存中的晋升规则 | 3/3 | 原理 | ①动态年龄判定是怎么算的？②大对象为什么直接进老年代？ | **结论：对象先在 Eden 分配，每熬过一次 Minor GC 年龄 +1，达到阈值进入老年代；另外有动态年龄、大对象、空间担保三种提前晋升。**<br>年龄阈值：`-XX:MaxTenuringThreshold`，默认 15（使用 CMS 时默认 6）。<br>动态年龄：从年龄 1 开始累加 Survivor 中各年龄对象的大小，累加到某个年龄时超过 Survivor 的一半（TargetSurvivorRatio=50），该年龄及以上的对象直接晋升。<br>大对象：超过 `-XX:PretenureSizeThreshold` 直接在老年代分配（只对 Serial / ParNew 生效；G1 放进 Humongous 区），避免在两个 Survivor 间反复复制。<br>空间担保：Minor GC 后 Survivor 放不下的存活对象，直接进入老年代。 |
| **S** | JVM 怎么记录对象年龄 | 3/3 | 原理 | ①为什么年龄阈值最大只能设 15？②对象头里还存了什么？ | **结论：年龄记录在对象头的 Mark Word 里，占 4 个 bit，所以最大值是 15。**<br>每次 Minor GC 时对象从 Eden / From 复制到 To 区，年龄 +1。<br>Mark Word（64 位 JVM 占 8 字节）还存哈希码、锁标志位、偏向线程 ID 等，存放内容随锁状态变化。<br>把 MaxTenuringThreshold 设成 16 以上，JVM 启动直接报错，原因就是 4 bit 存不下。 |
| **S** | 标记-清除 / 复制 / 标记-整理的原理和优劣；复制算法存活率高时为什么效率低 | 3/3 | 本质原因 | ①新生代和老年代分别用哪种？②CMS 用的是哪种，带来什么后果？<br>①Survivor 为什么要两个？ | ▸ **标记-清除、复制、标记-整理算法的原理和优劣？复制算法在存活率高时为什么效率低？**<br>**结论：标记-清除快但有碎片；复制无碎片但浪费空间、开销随存活对象数增长；标记-整理无碎片也不浪费空间，但移动对象慢。**<br>标记-清除：标记存活对象，回收其余；产生内存碎片，大对象找不到连续空间时会提前触发 GC。<br>复制：内存分两块只用一块，GC 时把存活对象复制到另一块；分配时用指针碰撞，速度快，但可用空间少一块。<br>标记-整理：把存活对象向一端移动，再清理边界外的内存；移动对象要更新所有引用，需要 STW。<br>存活率高时复制慢的本质：复制的工作量和存活对象数量成正比（每个都要拷贝 + 改引用），存活越多拷得越多，还得预留足够大的空间兜底；所以它只适合"朝生夕死"的新生代。<br>▸ **为什么新生代用复制算法，老年代用标记-清除或标记-整理？Eden 和 Survivor 为什么是 8:1:1？**<br>**结论：按存活率选算法——新生代存活率低适合复制；老年代存活率高，也没有额外空间做担保，只能用标记-清除 / 整理。**<br>新生代绝大多数对象朝生夕死，每次只复制少量存活对象，代价很低。<br>8:1:1：每次只浪费 10% 的空间（一块 Survivor），而不是复制算法原始方案的 50%。<br>两个 Survivor：保证每次 GC 后总有一块是空的，存活对象在两块之间来回复制，不产生碎片；Survivor 不够时靠老年代做分配担保。 |
| **S** | 为什么新生代用复制、老年代用清除或整理；Eden 和 Survivor 的比例 | 1/3 | 方案 | 老年代为什么少用复制？ | 结论：复制适合新生代低存活率；标记整理适合老年代；标记清除适合对碎片不敏感或特定阶段。老年代存活率高，复制需要搬运大量对象并准备等大空间。 |
| **A** | Minor GC、Major GC、Full GC 的区别和触发时机 | 3/3 | 原理 | ①空间分配担保具体怎么判断？ | **结论：Eden 满了触发 Minor GC；老年代或元空间不够用时触发 Full GC。**<br>Full GC 的触发条件：老年代空间不足；空间分配担保失败（Minor GC 前发现老年代最大连续空间小于历次晋升的平均大小）；元空间不足（JDK 8+，之前是永久代）；调用 System.gc()（只是建议）；CMS 出现 concurrent mode failure。<br>Minor GC 只回收新生代，停顿短；Full GC 回收整个堆和方法区，停顿长，线上要尽量避免。 |
| **A** | JVM 运行时内存区域；JDK 7 / 8 的变化 | 3/3 | 原理 | ①为什么用元空间替代永久代？②哪些区域会 OOM？ | **结论：线程私有的有程序计数器、虚拟机栈、本地方法栈；线程共享的有堆和方法区。**<br>程序计数器：记录当前字节码行号，是唯一不会 OOM 的区域。虚拟机栈：每个方法调用一个栈帧（局部变量表、操作数栈等）。<br>堆：存对象实例，是 GC 的主要区域。方法区：存类信息、常量、静态变量。<br>JDK 7：字符串常量池、静态变量从永久代移到堆。JDK 8：永久代被元空间取代，元空间使用本地内存。<br>换成元空间的原因：永久代大小难以设定、容易 OOM；同时便于 HotSpot 和 JRockit 合并。 |
| **A** | 怎么判断对象可回收；GC Roots 有哪些 | 1/3 | 原理 | ①引用计数法为什么不用？②被判定为不可达的对象一定会被回收吗？ | **结论：HotSpot 用可达性分析——从 GC Roots 出发沿引用链搜索，搜不到的对象就可以回收。**<br>引用计数法实现简单，但解决不了循环引用，主流 JVM 不用。<br>GC Roots：虚拟机栈中局部变量引用的对象、方法区中静态变量和常量引用的对象、本地方法栈中 JNI 引用的对象、被 synchronized 持有的对象、JVM 内部引用（如系统类加载器）。<br>不可达之后还有一次 finalize() 自救机会（只会执行一次，JDK 9 起 finalize 已被标记废弃）。 |
| **A** | 常见垃圾收集器；JDK 8 和 JDK 9+ 默认用什么 | 2/3 | 原理 | ①吞吐量优先和停顿时间优先怎么选？ | **结论：JDK 8 默认 Parallel Scavenge + Parallel Old（吞吐量优先），JDK 9 起默认 G1。**<br>新生代：Serial（单线程）、ParNew（Serial 的多线程版，配合 CMS 使用）、Parallel Scavenge（关注吞吐量）。<br>老年代：Serial Old、Parallel Old、CMS（并发标记清除，关注低停顿；JDK 9 废弃，JDK 14 移除）。<br>整堆：G1（Region 化，可设定停顿目标）；ZGC（JDK 15 正式可用，停顿控制在毫秒级，JDK 21 起支持分代）。<br>离线计算看吞吐量选 Parallel；Web 接口看停顿选 G1 / ZGC。 |
| **A** | 类加载过程 | 2/3 | 原理 | ①准备阶段和初始化阶段给静态变量赋值有什么区别？ | **结论：加载 → 连接（验证、准备、解析）→ 初始化，之后是使用和卸载。**<br>加载：通过全限定名获取二进制字节流，在方法区生成类结构，在堆里生成 Class 对象。<br>验证：检查字节码格式和安全性。准备：给静态变量分配内存并赋零值（`static final` 常量此时直接赋真实值）。<br>解析：把符号引用替换为直接引用。<br>初始化：执行 `<clinit>()`，即静态变量赋值语句和静态代码块，JVM 保证多线程下只执行一次。 |
| **A** | 双亲委派模型；为什么需要；怎么打破 | 2/3 | 原理 | ①Tomcat 为什么要打破双亲委派？②JDBC 的 SPI 是怎么绕过的？ | **结论：类加载器收到加载请求时先交给父加载器，父加载器加载不了才自己加载。**<br>层级（JDK 8）：Bootstrap → Extension → Application → 自定义加载器；JDK 9 起 Extension 改为 Platform ClassLoader。<br>好处：避免类重复加载；保护核心类库，自己写的 java.lang.String 不会替换掉 JDK 的。<br>打破方式：自定义类加载器重写 loadClass（只想改加载来源而不打破，重写 findClass 即可）；线程上下文类加载器（JDBC SPI）；Tomcat 给每个 Web 应用一个 WebappClassLoader，优先自己加载，实现应用隔离。 |
| **A** | 强、软、弱、虚四种引用 | 3/3 | 定义 | ①ThreadLocalMap 的 key 为什么用弱引用？ | **结论：四种引用强度依次减弱，决定 GC 时对象能不能被回收。**<br>强引用：普通的 new，只要有强引用就不回收，宁可 OOM。<br>软引用 SoftReference：内存不足时才回收，适合做缓存。<br>弱引用 WeakReference：下一次 GC 就回收，如 ThreadLocalMap 的 key、WeakHashMap。<br>虚引用 PhantomReference：不影响回收，get 永远返回 null，配合引用队列感知对象被回收（如释放堆外内存）。 |
| **A** | OOM 和内存泄漏怎么区分、怎么排查 | 3/3 | 方案 | ①内存泄漏和内存溢出有什么区别？ | **结论：先保留现场拿到堆转储文件，再用工具找出占用最大的对象和它的引用链。**<br>预先配置 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=...`，OOM 时自动生成 hprof 文件。<br>手动：`jmap -dump:live,format=b,file=heap.hprof <pid>`；`jstat -gcutil <pid> 1000` 看 GC 频率和各区占用。<br>分析：用 MAT 或 VisualVM 打开，看 Dominator Tree / Leak Suspects，顺着到 GC Roots 的引用链找到泄漏代码。<br>常见原因：集合只增不删、静态集合做缓存、ThreadLocal 没有 remove、连接没关闭、一次查询加载了大量数据。 |
| **B** | G1 的特点；CMS 和 G1 的区别 | 3/3 | 原理 | ①G1 的 Mixed GC 是什么？②CMS 的浮动垃圾是什么？ | **结论：CMS 是老年代的并发标记-清除收集器，追求低停顿但有碎片；G1 把堆划成 Region，整体看是标记-整理、局部看是复制，停顿时间可预测。**<br>CMS 四步：初始标记（STW）→ 并发标记 → 重新标记（STW）→ 并发清除；缺点是碎片、浮动垃圾、对 CPU 敏感，出现 concurrent mode failure 时退化成 Serial Old。<br>G1：堆分成等大的 Region，每个 Region 动态扮演 Eden / Survivor / Old / Humongous；按回收价值排序，优先回收垃圾最多的 Region（Garbage First），尽量满足 `-XX:MaxGCPauseMillis` 目标。<br>G1 有 Young GC 和 Mixed GC（回收新生代 + 部分老年代 Region），Full GC 只是兜底。 |
| **B** | 线上 CPU 飙高怎么定位到线程 | 2/3 | 方案 | ①怎么判断是 GC 导致的？ | **结论：先找到占 CPU 高的进程，再找到线程，最后用 jstack 定位到代码行。**<br>`top` 找进程 PID → `top -Hp <pid>` 找占用高的线程 ID → `printf '%x' <tid>` 转成十六进制。<br>`jstack <pid> \| grep -A 30 <十六进制tid>` 看该线程的栈，定位死循环、正则回溯、频繁计算等代码。<br>如果高占用的是 GC 线程，用 `jstat -gcutil` 确认是不是在频繁 Full GC，再按内存问题排查。<br>也可以用 Arthas 的 `thread -n 3` 直接列出最忙的 3 个线程。 |
| **B** | 栈溢出和堆溢出怎么产生 | 1/3 | 本质原因 | 如何定位？ | 结论：栈溢出常由递归过深或栈帧过大导致；堆溢出由对象持续存活或堆太小导致。用异常日志、堆转储、线程栈和 GC 日志定位。 |
| **B** | 怎么降低 STW；安全点和安全区域 | 2/3 | 方案 | 哪些阶段仍必须暂停？如何验证停顿改善？ | 结论：通过并发标记、分区回收、合理堆大小和降低单次回收工作量减少停顿。<br>GC 根扫描、部分对象转移和重定位等阶段仍需暂停。<br>用 GC 日志、JFR 和监控对比停顿时间、频率、分配速率，而不是只看一次 Full GC。 |
| **B** | 对象的创建过程 | 1/3 | 原理 | ①指针碰撞和空闲列表分别在什么情况下用？②并发分配内存怎么保证安全？ | **结论：类加载检查 → 分配内存 → 初始化零值 → 设置对象头 → 执行构造方法 `<init>`。**<br>分配内存：堆内存规整（复制 / 整理类收集器）用指针碰撞；不规整（CMS）用空闲列表。<br>并发安全：CAS + 失败重试；或 TLAB（每个线程在 Eden 预先分到一小块私有缓冲区）。<br>初始化零值保证字段不赋值也能直接用；对象头写入类元数据指针、哈希码、GC 年龄等。<br>最后执行 `<init>`：按代码给字段赋值，执行实例代码块和构造方法。 |
| **B** | 对象在内存中的布局 | 1/3 | 原理 | ①一个空 Object 占多少字节？②开启指针压缩后 Klass Pointer 占多少？ | **结论：对象由对象头、实例数据、对齐填充三部分组成。**<br>对象头：Mark Word（哈希码、GC 年龄、锁信息）+ Klass Pointer（指向类元数据）；数组对象额外有 4 字节的数组长度。<br>实例数据：各个字段的内容，相同宽度的字段排在一起。<br>对齐填充：对象大小必须是 8 字节的整数倍。<br>64 位 JVM 默认开启指针压缩，空 Object 占 16 字节：Mark Word 8 + Klass Pointer 4 + 填充 4。 |
| **B** | Metaspace 和永久代的区别 | 1/3 | 版本差异 | JDK 8 为什么移除永久代？ | 结论：JDK 8 起类元数据主要放在本地内存的 Metaspace，JDK 7 及以前使用永久代。<br>Metaspace 默认可动态扩展，但仍受 `MaxMetaspaceSize` 等参数约束。<br>类加载器泄漏、动态生成大量类会导致 Metaspace OOM。 |
| **B** | TLAB 是什么 | 1/3 | 原理 | TLAB 用完怎么办？大对象如何分配？ | 结论：TLAB 是线程本地分配缓冲区，让线程在私有区域快速分配小对象。<br>正常分配无需每次竞争共享堆指针；TLAB 用尽后申请新块或走共享分配路径。<br>过大的对象直接进入老年代或使用专门的大对象分配路径，具体规则取决于收集器实现。 |
| **B** | 逃逸分析和 JIT | 2/3 | 原理 | 标量替换和锁消除有什么关系？ | 结论：逃逸分析判断对象是否逃出当前线程或方法作用域。<br>若对象不逃逸，JIT 可做栈上替代、标量替换或消除不必要锁。<br>它是运行时优化，效果受 JDK、编译热度和代码形态影响，不能当作固定语义保证。 |
| **B** | 常用 JVM 参数 | 1/3 | 定义 | ①-Xms 和 -Xmx 为什么常设成一样？ | **结论：主要是堆大小、新生代比例、元空间、GC 选择、GC 日志几类。**<br>堆：`-Xms` 初始堆、`-Xmx` 最大堆（常设相同，避免运行时扩缩容）；`-Xmn` 新生代大小；`-Xss` 线程栈大小。<br>比例：`-XX:NewRatio`（老年代 / 新生代，默认 2）、`-XX:SurvivorRatio`（Eden / 一个 Survivor，默认 8）。<br>元空间：`-XX:MetaspaceSize`、`-XX:MaxMetaspaceSize`；GC：`-XX:+UseG1GC`、`-XX:MaxGCPauseMillis`。<br>GC 日志：JDK 8 用 `-XX:+PrintGCDetails -Xloggc:路径`，JDK 9+ 统一为 `-Xlog:gc*`。 |

| **A** | this 的绑定规则；call / apply / bind | 3/3 | 原理 | ①箭头函数的 this 能被 call 改变吗？ | **结论：this 在函数调用时确定，看"怎么调用"而不是"在哪定义"；箭头函数没有自己的 this，用的是外层作用域的 this。**<br>优先级：new 绑定 > 显式绑定（call / apply / bind）> 隐式绑定（`obj.fn()` 指向 obj）> 默认绑定（非严格模式指向 window，严格模式为 undefined）。<br>call 和 apply 都立即执行：call 的参数逐个传，apply 的参数用数组传。<br>bind 不立即执行，返回一个 this 被永久绑定的新函数，还能预置部分参数。<br>箭头函数的 this 不能被 call / apply / bind 改变。 |
| **A** | 原型和原型链 | 3/3 | 原理 | ①`Object.prototype.__proto__` 是什么？②new 一个对象做了哪几步？ | **结论：每个对象都有内部属性 `[[Prototype]]`（即 `__proto__`）指向它构造函数的 prototype；访问属性找不到时沿这条链往上找，直到 null，这条链就是原型链。**<br>关系：`实例.__proto__ === 构造函数.prototype`，`构造函数.prototype.constructor === 构造函数`。<br>终点：`Object.prototype.__proto__ === null`。<br>作用：实现继承和方法共享，所有实例共用 prototype 上的方法。<br>new 的过程：创建空对象 → 把它的 `__proto__` 指向构造函数的 prototype → 以它为 this 执行构造函数 → 构造函数返回对象就用返回值，否则返回这个新对象。 |
| **A** | Promise 的状态、链式调用、all / allSettled / race / any | 3/3 | 原理 | ①Promise.all 和 Promise.allSettled 有什么区别？ | **结论：Promise 是异步操作结果的容器，有 pending、fulfilled、rejected 三种状态，状态一旦改变就不可逆；async / await 是基于 Promise 的语法糖。**<br>解决回调地狱：then 链式调用，catch 统一捕获错误。<br>静态方法：all（全部成功才成功，一个失败就失败）、allSettled（等全部结束，返回每个结果）、race（取最先结束的）、any（取最先成功的）。<br>async 函数总是返回 Promise；await 暂停函数执行，等待 Promise 的结果，错误用 try-catch 捕获。 |
| **A** | async / await 的本质和异常处理 | 2/3 | 方案 | 不加 `await` 会发生什么？并行任务怎么写？ | 结论：`async` 函数始终返回 Promise，`await` 的拒绝应由 `try/catch` 或上层 Promise 链处理。<br>不加 `await` 会留下未处理或延后的 Promise，不会同步得到结果。<br>独立任务用 `Promise.all` 并行，依赖任务再按顺序 `await`。 |
| **A** | 防抖和节流 | 3/3 | 方案 | ①搜索框联想和滚动加载分别用哪个？ | **结论：两者都靠闭包保存定时器或时间戳；防抖是"停止触发 n 毫秒后才执行一次"，节流是"n 毫秒内最多执行一次"。**<br>防抖：每次触发先 clearTimeout 旧定时器，再重新 setTimeout；用于搜索框输入联想、窗口 resize 结束后再计算。<br>节流：记录上次执行时间，当前时间减去上次时间超过间隔才执行（时间戳版），或用定时器加标志位；用于滚动加载、按钮防连点、mousemove。<br>实现要点：用 `fn.apply(this, args)` 保留原来的 this 和参数。 |
| **A** | == 和 === 的区别 | 2/3 | 定义 | ①`null == undefined` 的结果？②`NaN === NaN` 的结果？ | **结论：=== 是严格相等，类型和值都相同才为 true；== 会先做类型转换再比较。**<br>== 的转换规则：null == undefined 为 true；字符串和数字比较时字符串转数字；布尔值先转数字；对象和原始值比较时，对象调用 valueOf / toString 转成原始值。<br>NaN 和任何值都不相等，包括它自己，判断用 `Number.isNaN()`；`Object.is()` 能区分 +0 和 -0，并认为 NaN 等于 NaN。<br>开发中统一用 ===。 |
| **B** | 数据类型及判断；原始类型和引用类型 | 2/3 | 原理 | ①`typeof null` 为什么是 `'object'`？ | **结论：8 种类型：7 种基本类型（Number、String、Boolean、Undefined、Null、Symbol、BigInt）+ 引用类型 Object。**<br>typeof：能判断基本类型（null 除外，返回 `'object'`）和 function；对象、数组都返回 `'object'`。<br>instanceof：沿原型链判断，适合引用类型，不能判断基本类型，跨 iframe 会失效。<br>最准确：`Object.prototype.toString.call(x)`，返回 `[object Array]` 这类字符串；数组还可以用 `Array.isArray`。<br>基本类型按值访问；引用类型的变量里存的是对象的引用。 |
| **B** | CommonJS 和 ES Module 的区别 | 2/3 | 原理 | 浏览器和 Node.js 的默认支持如何？ | 结论：ESM 使用静态 `import/export`，CommonJS 使用运行时 `require/module.exports`。<br>ESM 更利于静态分析、摇树优化和异步模块加载；CommonJS 在传统 Node.js 生态中更常见。<br>Node.js 的 ESM 行为受 `package.json`、扩展名和运行参数影响。 |
| **B** | 事件冒泡、捕获和事件委托 | 2/3 | 原理 | ①stopPropagation 和 preventDefault 有什么区别？ | **结论：事件传播分捕获（从 window 到目标）→ 目标 → 冒泡（从目标回到 window）三个阶段；事件委托是利用冒泡，把子元素的事件统一绑在父元素上。**<br>addEventListener 的第三个参数为 true 时在捕获阶段触发，默认 false 在冒泡阶段触发。<br>事件委托：在父元素上监听，用 `event.target` 判断是哪个子元素触发；好处是监听器少、动态新增的子元素自动生效。<br>stopPropagation 阻止事件继续传播；preventDefault 阻止默认行为（如链接跳转、表单提交）。 |
| **B** | 箭头函数和普通函数的区别 | 1/3 | 定义 | ①对象的方法能用箭头函数写吗？ | **结论：箭头函数没有自己的 this、arguments、prototype，不能作为构造函数。**<br>this 继承定义时外层作用域的 this，且不能被 call / apply / bind 改变。<br>没有 arguments，用剩余参数 `...args` 代替。<br>不能 new，也不能做 Generator 函数。<br>对象方法用箭头函数时，this 不会指向这个对象，所以对象方法、需要动态 this 的回调要用普通函数。 |
| **B** | 跨域及解决方案 | 1/3 | 方案 | ①CORS 的预检请求什么时候触发？②开发环境的代理为什么能绕过跨域？ | **结论：浏览器的同源策略限制脚本读取不同源（协议、域名、端口任一不同）的响应；最常用的解决方案是后端配置 CORS。**<br>CORS：服务端返回 Access-Control-Allow-Origin 等响应头；非简单请求（如 PUT、Content-Type 为 application/json、带自定义请求头）会先发 OPTIONS 预检。<br>代理：开发环境用 webpack / Vite 的 devServer proxy，生产用 Nginx 反向代理；服务器之间的请求不受同源策略限制。<br>JSONP：利用 script 标签不受同源限制，只支持 GET，已基本淘汰。<br>简单请求跨域时，请求其实已经到达服务端，是浏览器拦截了响应。 |
| **B** | Cookie、localStorage、sessionStorage | 1/3 | 定义 | ①Cookie 的 HttpOnly、Secure、SameSite 分别防什么？ | **结论：Cookie 会随请求自动发给服务端、容量约 4KB；localStorage 和 sessionStorage 只存在浏览器端、容量约 5MB。**<br>生命周期：Cookie 由 Expires / Max-Age 决定，不设置则关闭浏览器失效；localStorage 永久保存，直到手动清除；sessionStorage 关闭标签页即清除。<br>作用范围：localStorage 在同源的所有标签页共享；sessionStorage 只在当前标签页有效。<br>安全属性：HttpOnly 禁止 JS 读取（降低 XSS 窃取的风险）；Secure 只通过 HTTPS 发送；SameSite 限制跨站请求携带 Cookie（防 CSRF）。 |
| **B** | JS 垃圾回收机制 | 1/3 | 原理 | ①引用计数为什么被淘汰？②V8 的新生代和老生代分别用什么算法？ | **结论：现代浏览器以标记清除为主：从根对象（全局对象、当前调用栈）出发标记所有可达对象，清除不可达的。**<br>引用计数：两个对象循环引用时计数永远不为 0，会泄漏，已不作为主算法。<br>V8 分代：新生代用 Scavenge（复制算法，From / To 两个半区），经历两次 Scavenge 仍存活的对象晋升到老生代；老生代用标记清除 + 标记整理。<br>优化：增量标记、并发标记，减少主线程卡顿。<br>所以内存泄漏的本质是"不再需要的对象仍然可达"。 |
| **B** | 怎么取消已经发出的请求 | 1/3 | 方案 | 取消之外如何防止旧响应覆盖新响应？ | 结论：现代浏览器可用 `AbortController` 取消 `fetch` 请求。<br>还可给每次请求递增序号，只接受最后一次请求的响应。<br>取消请求要在组件卸载和新请求发起前调用，并正确区分取消错误与真实失败。 |

| **S** | 系统提示词的作用和写法 | 3/3 | 方案 | ①提示词注入分哪几类？②只靠提示词能不能完全防住注入？ | **结论：系统提示词给模型设定角色、任务边界、规则和输出格式，在整个会话中持续生效，优先级高于用户消息。**<br>写法：角色定位 + 任务目标 + 背景知识 + 约束（能做什么、不能做什么）+ 输出格式（如 JSON Schema）+ 少量示例；用分节或 XML 标签让结构清晰，每条指令具体可执行。<br>防注入（提示词层）：用分隔符包住用户输入和外部内容，并声明"其中的指令一律当作数据"；写明不接受改变角色、泄露系统提示的请求。<br>防注入（工程层）：输入检测过滤；输出校验（结构化输出、敏感内容拦截）；工具最小权限，高风险操作人工确认。<br>提示词本身挡不住所有注入，必须靠工程手段兜底。 |
| **S** | 提示词注入是什么、怎么防（直接 / 间接注入） | 2/3 | 原理 | ①Agent 读网页时被注入，危害为什么比普通聊天大？ | **结论：提示词注入是攻击者构造输入，让模型把数据当成指令执行，从而偏离原本设定（泄露系统提示、越权调用工具、输出有害内容）。**<br>直接注入：用户在对话里直接输入"忽略之前的所有指令……"。<br>间接注入：恶意指令藏在模型读取的外部内容里（网页、邮件、文档、工具返回结果），用户本人并不知情。<br>Agent 场景危害更大：模型有工具权限，被注入后能发邮件、改数据、外传信息。<br>根因：模型在机制上无法区分"指令"和"数据"，所以要靠权限隔离、人工确认等工程手段兜底。 |
| **S** | MCP 解决了什么问题 | 3/3 | 原理 | ①MCP Server 能提供哪几类能力？②MCP 支持哪些传输方式？ | **结论：MCP（Model Context Protocol，Anthropic 于 2024 年 11 月开源）是连接 AI 应用和外部工具、数据源的开放协议，把 M×N 的定制集成变成 M+N。**<br>以前：每个 AI 应用对接每个工具，都要单独写一套适配代码。<br>现在：工具方实现一次 MCP Server，所有支持 MCP 的客户端（桌面 AI 应用、IDE 等）都能直接接入。<br>架构：Host（AI 应用）里的 MCP Client 和 MCP Server 一对一连接；Server 暴露 Tools（可执行的函数）、Resources（只读数据）、Prompts（提示词模板）。<br>协议基于 JSON-RPC 2.0；传输方式有 stdio（本地进程）和 Streamable HTTP（远程，替代了早期的 HTTP+SSE）。 |
| **S** | MCP 工具描述和模型调用格式不兼容怎么办 | 2/3 | 方案 | ①不支持 Function Calling 的模型怎么用工具？②适配逻辑放在哪一层？ | **结论：在 MCP Client（或模型适配层）做格式转换——MCP 侧统一用 JSON Schema 描述工具，Client 把它转成目标模型要求的工具格式，再把模型发出的调用转回 MCP 请求。**<br>不兼容的根源：各厂商的 Function Calling 格式不同，如 OpenAI 的 tools / tool_calls、Anthropic 的 tool_use、Gemini 的 functionDeclarations。<br>转换：`tools/list` 拿到的 name、description、inputSchema → 映射成模型的 tools 参数；模型返回的调用 → 组装成 `tools/call` 请求；执行结果再按模型格式作为工具结果回传。<br>Schema 降级：目标模型不支持的 JSON Schema 关键字（如部分模型不支持 oneOf、$ref）在转换时展开或简化。<br>模型不支持原生 Function Calling：把工具描述写进提示词，约定 JSON 输出格式，解析后做 Schema 校验，失败带着错误信息重试；LangChain、LiteLLM 等框架提供现成的多模型适配。 |
| **S** | Function Calling 怎么让模型调用外部 API；模型扮演什么角色 | 3/3 | 原理 | ①模型会直接执行函数吗？②一次回答要调用多个函数怎么办？ | **结论：模型只负责"决定调哪个函数、生成参数"，真正执行 API 的是应用代码；模型是决策者和参数生成者，不是执行者。**<br>① 开发者把函数名、描述、参数的 JSON Schema 随请求一起发给模型。<br>② 模型判断需要调用时，返回结构化的调用意图（函数名 + JSON 参数），而不是普通文本。<br>③ 应用解析后执行真实的 API（鉴权、超时、错误处理都在应用侧），把结果作为工具消息回传给模型。<br>④ 模型根据结果生成最终回答，或继续发起下一次调用（多轮调用、并行调用）。 |
| **S** | 问题有歧义、同时匹配多个工具时模型怎么决策；工具边界怎么避免重叠 | 3/3 | 原理 | ①怎么让工具选择更稳定？②tool_choice 参数有什么用？ | **结论：模型根据工具名称、描述、参数说明和用户意图的语义匹配程度来选，本质是基于上下文的概率生成，不是规则匹配；结果有三种：选一个、并行调用多个、先向用户澄清。**<br>决策依据：工具描述写得越清楚（适用场景、不适用场景、和相似工具的区别），选得越准。<br>工程手段：系统提示里规定"意图不明确或缺少必填参数时先追问，不许编造参数"；工具之间职责不重叠。<br>tool_choice 控制：auto（模型自己决定）、必须调用（OpenAI 为 required，Anthropic 为 any）、指定某个工具、none（不调用）。<br>工具很多时，先做意图分类 / 路由，只把相关的子集暴露给模型。 |
| **A** | MCP 和 Function Calling 的关系 | 1/3 | 原理 | ①有了 MCP 还需要 Function Calling 吗？ | **结论：Function Calling 是模型的能力（输出结构化的调用意图），MCP 是工具接入的协议标准（工具怎么被发现、描述、调用、返回结果）；两者互补，不是替代关系。**<br>Function Calling 解决"模型怎么表达要调用工具"，格式由各模型厂商定义。<br>MCP 解决"工具怎么用统一方式接入应用"，和具体模型无关。<br>配合方式：MCP Client 从 Server 拿到工具列表 → 转成模型的 Function Calling 格式 → 模型决定调用 → Client 发 `tools/call` 给 Server 执行。 |
| **A** | 模型生成错误参数、不符合 JSON Schema 怎么处理 | 2/3 | 方案 | ①错误信息要不要回传给模型？ | **结论：在"生成前约束、执行前校验、失败后反馈"三处把关，不能直接信任模型生成的参数。**<br>生成前：JSON Schema 写清类型、枚举值、必填项、格式和示例；开启严格结构化输出（如 OpenAI 的 strict 模式）。<br>执行前：应用侧做 Schema 校验和业务校验（ID 是否存在、当前用户有没有权限）。<br>失败后：把具体的错误信息作为工具结果回传，让模型自我修正，并限制重试次数。<br>缺少必填信息时让模型追问用户；高风险操作执行前人工确认。 |
| **A** | 大模型幻觉是什么、怎么缓解 | 3/3 | 方案 | ①大模型为什么会产生幻觉？ | **结论：幻觉是模型生成看似合理、但与事实不符或没有依据的内容；根源是模型按概率生成下一个 token，目标是"通顺"而不是"真实"。**<br>原因：训练数据有错误或过时；有知识截止日期；问题超出知识范围时仍会硬给答案；解码有随机性。<br>缓解：RAG 检索真实资料作为依据，并要求标注引用；提示词里允许模型回答"不知道"；降低 temperature。<br>校验：调用工具查实时数据；输出后做事实核验，或用另一个模型交叉检查；关键场景人工审核。 |
| **A** | RAG 是什么、完整流程 | 2/3 | 原理 | ①文档切块大小怎么定？②检索不准怎么优化？ | **结论：RAG（检索增强生成）先从外部知识库检索相关内容，再和问题一起交给模型生成答案，解决知识过时、私有知识和幻觉问题。**<br>离线：文档加载 → 切块（按段落或固定长度，相邻块有重叠）→ Embedding 向量化 → 存入向量数据库。<br>在线：问题向量化 → 相似度检索 Top-K → 重排序（Rerank）→ 拼进提示词 → 模型生成答案并标注来源。<br>优化：混合检索（向量 + BM25 关键词）、查询改写、调整切块大小、元数据过滤、Rerank 模型。<br>对比微调：RAG 更新知识只要改知识库，成本低、可溯源。 |
| **A** | temperature 和 top_p 的作用 | 3/3 | 原理 | ①写代码和写文案分别怎么设？ | **结论：两者都控制输出的随机性：temperature 调整概率分布的平滑程度，top-p 限定参与采样的候选 token 范围。**<br>Temperature：越低分布越尖锐、输出越确定（接近 0 时基本每次都选概率最高的）；越高越随机、越有创造性。<br>Top-p（核采样）：只在累计概率达到 p 的最小候选集合里采样，p 越小候选越少。<br>一般只调其中一个。代码生成、信息抽取、结构化输出用低温度；创意写作用较高温度。 |
| **A** | Token、上下文窗口、最大输出 | 3/3 | 定义 | ①同样的内容，中文和英文的 token 数为什么不一样？ | **结论：Token 是模型处理文本的最小单位，由分词器（如 BPE）切分得到；上下文窗口是模型一次能处理的输入 + 输出 token 总数上限。**<br>常见英文单词约 1 个 token；一个汉字占 1 到 2 个 token 不等，取决于具体模型的分词器。<br>计费、速度、窗口上限都按 token 计算。<br>超出窗口的内容会被截断或直接报错，所以长对话需要摘要、检索等上下文管理手段。 |
| **A** | 怎么让模型稳定输出结构化 JSON | 2/3 | 方案 | JSON 解析失败怎么办？ | 结论：优先使用模型提供商的 JSON mode 或 structured output，并同时提供严格 Schema。<br>程序侧必须解析、校验字段、类型和枚举，不能只依赖提示词。<br>失败时做有限修复或重试，超过上限就返回可诊断错误。 |
| **A** | 常用提示词技巧：Few-shot、思维链 | 1/3 | 原理 | ①Few-shot 的示例怎么选？ | **结论：核心是把任务说清楚、给出示例、引导推理、约束输出格式。**<br>Zero-shot / Few-shot：不给示例直接做 / 给几组"输入 → 输出"示例让模型模仿格式和风格；示例要覆盖典型情况且格式统一。<br>思维链（CoT）：让模型先写出推理步骤再给答案，提升数学、逻辑等多步问题的准确率；推理模型已把这个过程内置。<br>其他：角色设定、把复杂任务拆成多步串联（Prompt Chaining）、用分隔符区分指令和数据、指定输出格式、写明反例和边界条件。 |
| **B** | Embedding 和向量数据库 | 3/3 | 原理 | ①向量相似度怎么计算？ | **结论：Embedding 把文本映射成高维向量，语义相近的文本向量距离也近；向量数据库专门存储向量并做高效的相似度检索。**<br>相似度：余弦相似度、点积、欧氏距离。<br>检索：数据量大时用近似最近邻（ANN）索引，如 HNSW、IVF，用少量精度换速度。<br>常见选型：Milvus、Chroma、FAISS（库）、pgvector（PostgreSQL 扩展）、Elasticsearch 的向量检索。<br>用途：RAG 检索、语义搜索、推荐、Agent 长期记忆。 |
| **B** | 向量检索和关键词检索怎么选 | 1/3 | 方案 | 为什么常用混合检索？ | 结论：向量检索擅长语义相似，关键词检索擅长精确实体和编号。混合检索结合两者，再用重排统一排序，适合企业知识库。 |
| **B** | 提示词工程、RAG、微调分别适合什么场景 | 2/3 | 方案 | ①微调能让模型学会新知识吗？ | **结论：先提示词，再 RAG，最后才考虑微调——成本和门槛依次升高。**<br>提示词工程：几乎零成本，适合调整输出格式、风格、任务说明。<br>RAG：适合需要外部知识、私有数据、知识频繁更新、要求能溯源的场景。<br>微调：适合固定输出风格、特定领域的任务格式、让小模型学会某类任务；不适合频繁变化的知识，成本高，还有遗忘已有能力的风险。<br>实际项目里常组合使用。 |
| **B** | 流式输出怎么实现 | 2/3 | 原理 | ①前端怎么接收流式数据？②SSE 和 WebSocket 有什么区别？ | **结论：模型逐个 token 生成，服务端每生成一段就推给客户端，常用 SSE（Server-Sent Events）实现，目的是缩短首字等待时间。**<br>SSE：基于 HTTP 长连接，响应头 `Content-Type: text/event-stream`，服务端按 `data: ...` 加空行的格式持续推送，单向（服务端 → 客户端）。<br>前端：EventSource 只支持 GET；调大模型接口一般用 fetch + `response.body.getReader()` 逐块读取并解析，可以发 POST。<br>后端（Spring）：返回 SseEmitter，或 WebFlux 的 `Flux<ServerSentEvent>`。<br>WebSocket 是全双工，适合双向实时交互；只需要单向推送时用 SSE 更简单。 |
| **B** | Transformer 和自注意力的基本原理 | 1/3 | 原理 | ①为什么要用多头注意力？②位置编码有什么用？ | **结论：Transformer 用自注意力让序列中每个 token 直接和其他所有 token 计算相关性，可以并行计算，解决了 RNN 只能串行、长距离依赖弱的问题。**<br>自注意力：每个 token 生成 Q、K、V 三个向量，Q 和所有 K 做点积再除以 √d，经 softmax 得到权重，对 V 加权求和。<br>多头注意力：多组 Q / K / V 并行计算，从不同子空间捕捉不同的关系。<br>位置编码：注意力本身不感知顺序，要额外加入位置信息。<br>GPT 类大模型只用 Decoder 部分，用因果掩码保证每个 token 只能看到前面的内容，自回归地逐个生成。 |
| **B** | MCP 的 Client 和 Server 怎么通信 | 1/3 | 原理 | ①Server 新增了工具，客户端怎么感知？ | **结论：基于 JSON-RPC 2.0，流程是初始化握手 → 能力协商 → 发现能力 → 调用。**<br>初始化：Client 发 initialize（协议版本、自身能力）→ Server 返回自己的能力 → Client 发 initialized 通知。<br>发现：`tools/list`、`resources/list`、`prompts/list` 获取可用能力及其描述、参数 Schema。<br>调用：`tools/call` 传入工具名和参数，Server 执行后返回结果（文本、图片等内容块；失败时用 isError 标记）。<br>变更通知：Server 的工具列表变化时发 `notifications/tools/list_changed`，Client 重新拉取列表。 |
| **B** | 工具调用失败怎么处理 | 2/3 | 方案 | 哪些错误不能重试？如何做幂等？ | 结论：按错误类型区分重试、换工具、澄清和终止。<br>网络超时、临时限流可指数退避重试；参数错误和权限错误应修正或拒绝。<br>有副作用的调用要带幂等键并记录执行状态，避免重试造成重复操作。 |
| **B** | 大模型应用怎么保护隐私和密钥 | 1/3 | 方案 | API Key 能放前端吗？日志怎么脱敏？ | 结论：密钥只放服务端，通过短期凭证和最小权限访问外部服务。<br>敏感字段进入模型前做脱敏、最小化和用途限制，日志与追踪数据同步脱敏。<br>工具层按用户身份和资源权限校验，模型输出不能绕过鉴权。 |
| **B** | 怎么选模型、控制调用成本 | 1/3 | 方案 | 什么时候用小模型或缓存？ | 结论：按准确率、延迟、上下文长度、工具能力和单位成本做任务路由。<br>分类、改写和简单抽取可使用小模型，复杂推理再升级。<br>用缓存、批处理、上下文压缩和预算上限控制成本，并持续做质量回归。 |

| 优先级 | 题目 | 共识 | 要懂到哪一层 | 可能的追问 | 答案要点 |

| **S** | XSS 是什么，分几种 | 3/3 | 原理 | ①三种类型各举一个例子？②DOM 型和反射型的区别在哪？ | **结论：XSS（跨站脚本攻击）是攻击者把恶意脚本注入到网页中，在其他用户的浏览器里以该站点的身份执行；分存储型、反射型、DOM 型三种。**<br>存储型：脚本被存进数据库（评论、昵称），所有访问该页面的人都会中招，危害最大。<br>反射型：脚本放在 URL 参数里，服务端原样拼进响应返回，需要诱导用户点击恶意链接。<br>DOM 型：前端 JS 把 URL、输入框等不可信数据直接写进 innerHTML、document.write、eval，全程不经过服务端。<br>危害：窃取 Cookie / Token、冒充用户操作、篡改页面、钓鱼。 |
| **S** | 富文本保留部分标签时怎么防 XSS；为什么白名单比黑名单可靠 | 3/3 | 本质原因 | `img`、链接属性如何过滤？前端过滤够不够？ | 结论：使用成熟库按白名单保留允许标签、属性和协议，服务端再过滤一次。<br>链接只允许 `http`、`https` 等明确协议，移除事件属性和危险 URL。<br>白名单默认拒绝未声明内容；黑名单无法穷举新标签、编码变形、大小写和事件属性绕过。 |
| **S** | XSS 通用防御：输出编码、CSP、HttpOnly 能否完全防住 | 3/3 | 方案 | ①Vue 的 v-html 为什么危险？<br>①禁止内联脚本后，必须用的内联脚本怎么办？<br>①Token 存 localStorage 和存 Cookie 哪个更安全？ | ▸ **防御 XSS 的通用手段有哪些？**<br>**结论：核心是"输出编码"——不可信数据输出到页面时按所在上下文转义，再叠加 CSP、HttpOnly 等纵深防御。**<br>输出编码：HTML 内容中转义 `< > & " '`；属性、JS、URL 上下文用各自的编码规则。<br>框架默认转义：Vue 的 `{{ }}`、React 的 JSX 都会自动转义；慎用 v-html、dangerouslySetInnerHTML、innerHTML。<br>纵深防御：Cookie 设置 HttpOnly；配置 CSP 限制脚本来源；输入校验（长度、格式）。<br>富文本场景用白名单过滤。<br>▸ **CSP 是什么？怎么防 XSS？**<br>**结论：CSP（内容安全策略）通过响应头告诉浏览器哪些来源的脚本、样式、图片可以加载执行，注入的脚本即使出现在页面里也不会运行。**<br>配置：响应头 `Content-Security-Policy: script-src 'self' https://cdn.example.com`，或用 meta 标签。<br>启用 script-src 后默认禁止内联脚本和 eval，直接挡住大部分注入的 `<script>` 和 onerror 事件。<br>必须用内联脚本时，用 nonce（每次请求生成的随机值）或 hash 放行指定的脚本。<br>上线前可先用 Content-Security-Policy-Report-Only 只上报不拦截，观察后再正式启用。<br>▸ **Cookie 设置了 HttpOnly，能完全防住 XSS 吗？**<br>**结论：不能。HttpOnly 只阻止 JS 读取 Cookie，防的是"XSS 之后偷 Cookie"，阻止不了脚本被注入和执行。**<br>脚本照样能在页面里以用户身份发请求（浏览器会自动带上 Cookie）、读取页面上的数据、篡改页面钓鱼、记录键盘输入。<br>所以 HttpOnly 只是降低危害的手段，防 XSS 还是要靠输出编码、白名单过滤和 CSP。 |
| **S** | SQL 注入是什么，怎么防 | 3/3 | 方案 | ①预编译为什么能防注入？②ORDER BY 动态排序怎么防？ | **结论：SQL 注入是用户输入被拼接进 SQL 语句并被当成代码执行；根本防御是参数化查询（预编译）。**<br>例：后端拼接 `"select * from user where name = '" + name + "'"`，输入 `' or '1'='1` 能绕过登录，输入 `'; drop table user; -- ` 能删表。<br>防御：PreparedStatement 参数化查询；MyBatis 用 #{} 不用 ${}；用 ORM 框架的参数绑定。<br>必须拼接的位置（表名、排序字段）用白名单校验；输入做类型和格式校验。<br>纵深防御：数据库账号最小权限；不把数据库报错信息返回给前端；部署 WAF。 |
| **A** | 预编译为什么能防注入；ORDER BY 动态排序、LIKE 怎么写 | 1/3 | 本质原因 | ①占位符能代替表名吗？<br>①ORDER BY 为什么不能用 #{}？ | ▸ **预编译为什么能防 SQL 注入？**<br>**结论：本质是"代码和数据分离"——SQL 的结构先编译固定，参数之后只作为值传入，不会再被当成 SQL 语法解析。**<br>过程：带 `?` 的 SQL 模板先交给数据库解析、编译成执行计划，此时语法结构已经确定。<br>执行时传入的参数只填充占位符，即使内容是 `' or 1=1`，也只是一个普通的字符串值。<br>MySQL 驱动默认（`useServerPrepStmts=false`）是在客户端对参数转义后再拼接发送，效果同样是参数只被当作值处理。<br>限制：占位符只能代替值，不能代替表名、列名、ORDER BY 字段、SQL 关键字，这些位置要用白名单。<br>▸ **ORDER BY 动态排序、LIKE 模糊查询怎么写才能防注入？**<br>**结论：ORDER BY 字段走白名单映射，LIKE 用 #{} 配合拼接函数，不让用户输入直接进入 SQL 结构。**<br>ORDER BY：#{} 会给值加上引号，变成按常量排序、不起作用，只能用 ${}；所以前端只传排序标识，后端用 Map 或枚举映射成固定列名，不在白名单内就用默认排序。<br>LIKE：写 `like concat('%', #{kw}, '%')`，或在 Java 里拼好 `"%" + kw + "%"` 再用 #{} 传入；不要写 `'%${kw}%'`。<br>IN 查询：用 `<foreach>` 生成多个 #{}，不要拼接字符串。 |
| **A** | CSRF 是什么、怎么防；和 XSS 的区别 | 3/3 | 原理 | ①SameSite 的 Strict 和 Lax 有什么区别？②Token 放在请求头里为什么能防 CSRF？<br>①网站有 XSS 漏洞时，CSRF Token 还有用吗？ | ▸ **CSRF 是什么？怎么防？**<br>**结论：CSRF（跨站请求伪造）是攻击者诱导已登录的用户访问恶意页面，利用浏览器自动携带 Cookie 的特性，以用户身份发起请求。**<br>例：恶意页面里放 `<img src="https://bank.example/transfer?to=hacker&amount=1000">`，用户打开页面就发出了转账请求。<br>防御：CSRF Token（服务端下发随机值，请求时放在表单或请求头里校验，攻击者拿不到）；Cookie 设置 SameSite=Lax / Strict；校验 Referer / Origin 请求头；关键操作二次验证。<br>JWT 放在 Authorization 请求头而不是 Cookie 里时，浏览器不会自动携带，天然不受 CSRF 影响。<br>Chrome 80 起，没有声明 SameSite 的 Cookie 默认按 Lax 处理。<br>▸ **XSS 和 CSRF 有什么区别？**<br>**结论：XSS 是在目标站点里执行攻击者的脚本，CSRF 是借用户的登录态从别的站点发请求；XSS 能读到页面数据，CSRF 拿不到响应，只能"盲发"请求。**<br>发生位置：XSS 在受害网站内部执行；CSRF 从第三方站点发起。<br>依赖条件：XSS 依赖网站存在注入漏洞；CSRF 依赖浏览器自动带 Cookie，且服务端只靠 Cookie 认证。<br>防御：XSS 靠输出编码、白名单过滤、CSP；CSRF 靠 Token、SameSite、校验来源。<br>有 XSS 时 CSRF Token 会失效，因为脚本在同源页面里能直接读到 Token。 |
| **A** | 密码（和身份证号）怎么存储 | 3/3 | 方案 | ①为什么不能用 MD5？②盐需要保密吗？ | **结论：用加盐的慢哈希算法存储，如 BCrypt、Argon2、PBKDF2；绝不能明文或用可逆加密存储。**<br>单纯的 MD5 / SHA：计算太快，能被彩虹表和 GPU 暴力破解。<br>加盐：每个用户一个随机盐，相同密码的哈希值也不同，彩虹表失效；盐可以和哈希值存在一起，不需要保密。<br>慢哈希：BCrypt 有可调的工作因子，故意让单次计算变慢，提高暴力破解的成本；Spring Security 的 BCryptPasswordEncoder 可以直接用。<br>传输过程用 HTTPS 保护。 |

| **B** | crontab 定时任务 | 2/3 | 定义 | ①定时任务没有执行，怎么排查？ | **结论：`crontab -e` 编辑，格式是"分 时 日 月 周 命令"。**<br>例：`0 2 * * * /data/backup.sh >> /data/backup.log 2>&1` 每天凌晨 2 点执行；`*/5 * * * *` 表示每 5 分钟执行一次。<br>`crontab -l` 查看当前用户的定时任务。<br>没执行的常见原因：cron 的环境变量很少，命令和脚本要写绝对路径；脚本没有执行权限；查看 /var/log/cron 或 syslog 定位。 |
| **B** | 程序后台运行、退出终端不被杀 | 1/3 | 方案 | ①`2>&1` 是什么意思？ | **结论：`nohup java -jar app.jar > app.log 2>&1 &`：nohup 忽略挂断信号，`&` 放到后台运行。**<br>`> app.log` 把标准输出重定向到文件（覆盖），`>>` 是追加；`2>&1` 把标准错误（2）重定向到标准输出（1）所指的位置。<br>`jobs` 查看后台任务，`fg` 调回前台。<br>生产环境更推荐用 systemd 或 Docker 管理进程，支持开机自启和崩溃自动重启。 |
| **B** | 怎么查找文件 | 1/3 | 方案 | ①怎么找出 7 天前的日志并删掉？ | **结论：按条件实时查找用 find，按文件名快速查找用 locate。**<br>`find /data/logs -name '*.log' -size +100M`：按名称和大小查找；`-mtime +7` 表示修改时间超过 7 天；`-type f` 只找普通文件。<br>清理旧日志：`find /data/logs -name '*.log' -mtime +7 -exec rm -f {} \;`（先不带 -exec 跑一遍，确认结果再删）。<br>locate 查的是索引库，速度快，但要先 updatedb 更新；`which java` 查命令所在路径。 |
| **B** | 管道、重定向、xargs | 1/3 | 原理 | `2>`、`2>&1` 分别表示什么？ | 结论：管道把前一个命令标准输出交给后一个命令，重定向改变输入或输出去向。<br>`>` 覆盖文件，`>>` 追加，`2>` 重定向标准错误，`2>&1` 合并到标准输出。<br>`xargs` 把标准输入转换为命令参数，使用时要处理空格和特殊字符。 |
| **B** | systemd 和 journalctl | 1/3 | 方案 | 如何查看服务最近一次失败原因？ | 结论：`systemctl` 管理服务状态、启动、停止和开机启动，`journalctl` 查询 systemd 日志。<br>常用命令是 `systemctl status app`、`journalctl -u app -f` 和按时间过滤。<br>服务单元要配置用户、环境、重启策略和资源限制。 |
| **B** | 环境变量和进程继承 | 1/3 | 原理 | 为什么修改 shell 环境不影响已运行进程？ | 结论：子进程启动时复制父进程环境变量。已运行进程不会自动同步后来修改，服务环境应通过启动配置、systemd 或容器显式注入。 |
| **B** | 零拷贝 | 1/3 | 原理 | `sendfile` 和 `mmap` 解决什么问题？ | 结论：零拷贝减少数据在用户态和内核态之间的重复复制。<br>Linux 的 `sendfile` 可在内核内把文件数据发送到 socket，`mmap` 可映射文件减少显式复制。<br>它减少 CPU 和内存带宽开销，但不等于完全没有数据搬运。 |

| **S** | 主从延迟的原因；单线程回放大事务时延迟的本质原因 | 3/3 | 本质原因 | ①MySQL 的并行复制是怎么演进的？②业务上怎么规避延迟带来的读不一致？ | **结论：主库多线程并发写，从库回放能力跟不上就会延迟；单线程回放大事务时，本质是"主库并发执行的工作被压成从库串行执行"，而且大事务必须完整执行完才能提交。**<br>复制流程：主库提交时写 binlog → 从库 IO 线程拉取并写入 relay log → 从库 SQL 线程回放。<br>常见原因：从库配置低；从库承担大量查询、抢占资源；大事务；主库写并发高而从库回放并行度低（MySQL 5.6 之前只有一个 SQL 线程）；网络延迟。<br>大事务的本质：binlog 在事务提交时才整体写入并发出，从库收到时主库已经执行了 T 秒，从库还要再花约 T 秒回放，延迟至少是 T；单线程下它还会堵住后面所有事务，延迟持续累积。<br>解决：拆分大事务（如分批删除）；开启并行复制（5.6 按库并行、5.7 基于组提交、8.0 基于 WRITESET）；强一致的读走主库。 |
| **S** | 为什么 InnoDB 用 B+ 树而不用 B 树 | 3/3 | 原理 | ①叶子节点之间的双向链表有什么用？②3 层 B+ 树能存多少数据？ | **结论：B+ 树更矮（磁盘 IO 少）、范围查询更快、查询性能更稳定。**<br>更矮：B+ 树的非叶子节点只存键和指针、不存数据，一页（16KB）能放更多键，扇出大，3 层就能存两千万级数据，一次查询只要 2 到 3 次磁盘 IO。<br>范围查询：数据全在叶子节点，叶子之间用双向链表相连，定位到起点后顺序遍历即可；B 树要在树上来回做中序遍历。<br>稳定：所有查询都要走到叶子节点，路径长度相同；B 树的数据分散在各层，查询耗时不稳定。<br>补充：主键索引的叶子节点存的是整行数据，这就是聚簇索引。 |
| **S** | 聚簇索引和二级索引；回表和覆盖索引 | 3/3 | 原理 | ①表没有定义主键时，聚簇索引用什么？②二级索引的叶子节点为什么存主键而不是行地址？ | **结论：聚簇索引的叶子节点存整行数据，InnoDB 的表数据就按主键组织；二级索引的叶子节点存的是主键值。**<br>回表：通过二级索引查到主键，再到聚簇索引里查整行，多一次 B+ 树查找。<br>覆盖索引：查询的列都在二级索引里（如联合索引 (name, age) 上执行 `select name, age from user where name = ?`），不需要回表。<br>没有主键时，InnoDB 用第一个非空唯一索引；还没有就生成隐藏的 6 字节 row_id。<br>二级索引存主键而不存地址：行数据移动（页分裂）时不用更新二级索引。 |
| **A** | 主从复制原理；binlog 格式；延迟怎么监控和治理 | 2/3 | 原理 | ①异步复制和半同步复制有什么区别？ | **结论：主库把数据变更写入 binlog，从库拉取后重放，实现数据同步。**<br>三个线程：主库的 binlog dump 线程负责发送；从库的 IO 线程接收并写入 relay log；从库的 SQL 线程读取 relay log 回放。<br>binlog 格式：STATEMENT（记录 SQL 原文，日志小，但 now()、uuid() 等函数会导致主从不一致）；ROW（记录每行变更前后的值，最安全，日志大，MySQL 5.7.7 起为默认）；MIXED（默认用 STATEMENT，不安全时自动切 ROW）。<br>默认是异步复制，主库提交时不等从库；半同步复制要求至少一个从库收到 binlog 并写入 relay log 后主库才返回，减少主库宕机时的数据丢失。 |
| **A** | 读写分离下刚写入就读不到怎么办 | 1/3 | 方案 | ①怎么监控主从延迟？ | **结论：根因是主从延迟，从库还没回放完；解决思路是让对一致性要求高的读走主库。**<br>强制走主库：写完马上要读的场景（如下单后查订单详情）指定读主库，ShardingSphere 等中间件支持用 Hint 强制路由。<br>会话级：同一会话在写操作之后的一段时间内，读请求都走主库。<br>等待方案：判断从库延迟（`show slave status` 的 Seconds_Behind_Master；8.0.22 起为 `show replica status` 的 Seconds_Behind_Source），或等 GTID 回放到位后再读从库。<br>业务层：写完直接用接口返回的结果展示，或提示"处理中"。 |
| **A** | 事务 ACID 和隔离级别；脏读、不可重复读、幻读 | 3/3 | 原理 | ①为什么说一致性是目的，其他三个是手段？<br>①InnoDB 的 RR 能完全解决幻读吗？②RC 和 RR 在并发性能上有什么差别？ | ▸ **事务的 ACID 是什么？InnoDB 分别靠什么实现？**<br>**结论：原子性靠 undo log，持久性靠 redo log，隔离性靠锁和 MVCC，一致性是前三者共同保证的目标。**<br>原子性（A）：要么全部成功，要么全部回滚；undo log 记录反向操作，用于回滚。<br>一致性（C）：事务前后数据都满足约束和业务规则。<br>隔离性（I）：并发事务互不干扰；读靠 MVCC，写靠行锁。<br>持久性（D）：提交后数据不丢；redo log 采用 WAL（先写日志再写数据页），宕机后用 redo log 恢复。<br>▸ **事务的隔离级别有哪些？分别解决了什么问题？**<br>**结论：读未提交、读已提交（RC）、可重复读（RR）、串行化，依次解决脏读、不可重复读、幻读；InnoDB 默认是 RR。**<br>读未提交：能读到别人还没提交的数据（脏读）。RC：只读已提交的数据，但同一事务两次读的结果会不同（不可重复读）。<br>RR：同一事务多次读结果一致；InnoDB 在 RR 下，快照读靠 MVCC、当前读靠 Next-Key Lock，解决了大部分幻读。<br>串行化：读写都加锁，性能最差。<br>RR 不能完全避免幻读：事务先做快照读，再 update 了别的事务新插入的行，之后的快照读就能看到这一行。 |
| **A** | MVCC 原理 | 2/3 | 原理 | ①RC 和 RR 下 ReadView 的生成时机有什么不同？ | **结论：MVCC 通过"隐藏列 + undo log 版本链 + ReadView"实现读不加锁，让读写可以并发。**<br>隐藏列：每行有 trx_id（最后修改它的事务 ID）和 roll_pointer（指向 undo log 里的上一个版本），串成版本链。<br>ReadView：记录生成那一刻的活跃事务 ID 列表、最小活跃事务 ID、下一个要分配的事务 ID、创建者事务 ID。<br>可见性：沿版本链找第一个满足条件的版本——trx_id 是自己，或小于最小活跃 ID，或小于下一个分配 ID 且不在活跃列表里。<br>RC 每次 select 都重新生成 ReadView；RR 只在第一次 select 时生成并一直复用，所以能重复读。 |
| **A** | 最左前缀原则和联合索引 | 3/3 | 原理 | ①`where b = 1 and a = 1` 能用上 (a, b) 索引吗？②`a > 1 and b = 2` 里的 b 能用上索引吗？ | **结论：联合索引 (a, b, c) 先按 a 排序，a 相同再按 b、再按 c；查询必须从最左边的列开始连续匹配，才能用上索引。**<br>能用：`a`、`a, b`、`a, b, c`；不能用：只有 `b`，或只有 `b, c`。<br>条件书写顺序无关：`where b = 1 and a = 1` 会被优化器调整，照样能用。<br>范围查询（`>`、`<`、between）之后的列不能用于索引定位；MySQL 5.6 起的索引下推可以在索引里用这些列先过滤，减少回表。<br>建索引时，把区分度高、最常用的等值条件列放在左边。 |
| **A** | 索引失效的情况 | 3/3 | 原理 | ①怎么确认索引有没有生效？ | **结论：本质都是"无法利用 B+ 树的有序性来定位"，或者优化器判断走全表扫描更快。**<br>对索引列做函数或计算：`where year(create_time) = 2024`、`where id + 1 = 10`。<br>隐式类型转换：字符串类型的列用数字比较，如 `where phone = 13800000000`。<br>左模糊 `like '%abc'`；联合索引不满足最左前缀；OR 条件中有一列没有索引。<br>优化器判断回表成本高于全表扫描（如结果占了表的大部分）；用 explain 的 type、key 字段确认。 |
| **A** | redo log、undo log、binlog；两阶段提交 | 3/3 | 原理 | ①只用 binlog 能做崩溃恢复吗？ | **结论：redo log 是 InnoDB 的物理日志，保证崩溃恢复；undo log 用于回滚和 MVCC；binlog 是 Server 层的逻辑日志，用于主从复制和数据恢复。**<br>redo log：记录"哪个页的哪个位置改成了什么"，固定大小、循环写。binlog：记录 SQL 或行变更，追加写，所有存储引擎都有。<br>两阶段提交：redo log prepare → 写 binlog → redo log commit。<br>目的：保证 redo log 和 binlog 一致；否则崩溃后主库按 redo log 恢复、从库按 binlog 复制，主从数据会不一致。<br>崩溃恢复时：redo log 处于 prepare 且 binlog 完整就提交，binlog 不完整就回滚。 |
| **A** | 慢查询怎么排查；EXPLAIN 看哪些字段 | 3/3 | 方案 | ①type 字段从好到差的顺序是什么？ | **结论：开启慢查询日志找到慢 SQL → 用 explain 看执行计划 → 针对性地加索引或改写 SQL。**<br>开启：`slow_query_log = ON`，用 `long_query_time` 设置阈值（如 1 秒）。<br>explain 重点：type（system > const > eq_ref > ref > range > index > ALL，至少要到 range）、key（实际用到的索引）、rows（预估扫描行数）、Extra（出现 Using filesort、Using temporary 要优化，Using index 表示用了覆盖索引）。<br>优化：补上合适的索引；避免 `select *`；改写导致索引失效的写法；大表分页优化；拆分复杂的 join。 |
| **B** | 索引为什么不用哈希、二叉树、红黑树或跳表 | 1/3 | 原理 | ①InnoDB 的自适应哈希索引是什么？ | **结论：数据库索引要同时满足"磁盘 IO 次数少"和"支持范围查询"，只有 B+ 树两点都满足。**<br>哈希：等值查询 O(1)，但不支持范围查询、排序和最左前缀匹配。<br>二叉搜索树：顺序插入时会退化成链表。红黑树 / AVL：虽然平衡，但每个节点只有两个子节点，百万数据树高 20 层左右，每层一次磁盘 IO。<br>跳表：层数高，节点分散，不适合按页读取；Redis 是纯内存数据库，所以用跳表合适。<br>B+ 树一个节点就是一页，扇出上千，3 层就够用。 |
| **B** | InnoDB 行锁；什么时候锁表；RR 下怎么防幻读 | 2/3 | 原理 | ①什么情况下行锁的效果等同于锁全表？ | **结论：行锁有记录锁、间隙锁、临键锁（Next-Key Lock = 记录锁 + 间隙锁）；RR 下当前读用临键锁同时锁住记录和间隙，阻止其他事务插入。**<br>记录锁：锁单条索引记录。间隙锁：锁两条记录之间的间隙，只在 RR 下存在，作用是防插入。<br>加锁的对象是索引：where 条件没走索引时会扫描全表，给扫到的所有记录加锁，效果等同锁表。<br>唯一索引上的等值查询命中记录时，临键锁退化为记录锁。<br>`select ... for update`、update、delete 是当前读，要加锁；普通 select 是快照读，不加锁。 |
| **B** | 深分页为什么慢、怎么优化 | 2/3 | 原理 | ①游标分页有什么限制？ | **结论：MySQL 要先扫描并丢弃前 100 万行（每行还要回表），才能返回后面的 10 行。**<br>优化一（延迟关联）：先在覆盖索引上查出主键 `select id from t order by id limit 1000000, 10`，再用这些主键 join 回原表取整行，大幅减少回表。<br>优化二（游标 / 书签）：记住上一页最后一个 id，用 `where id > #{lastId} order by id limit 10`，直接从索引定位。<br>游标分页不能跳页，适合"加载更多"、滚动翻页。 |
| **B** | 一亿条流水只查最近一天怎么优化 | 1/3 | 方案 | 除了索引和分区还可做什么？ | 结论：先按时间范围建立高选择性索引，再减少返回列并使用覆盖索引。<br>数据量和保留周期稳定时可按时间分区、冷热分层或归档历史数据。<br>还要控制分页、查询并发和报表读写隔离，不能只堆硬件。 |
| **B** | 一条 SELECT / INSERT 怎么执行 | 1/3 | 原理 | 解析、优化和执行分别做什么？ | 结论：请求经过连接、解析、优化、执行和返回结果等阶段。<br>优化器根据统计信息选择索引、连接顺序和执行计划；执行器再访问存储引擎。<br>`INSERT` 还涉及约束检查、锁、undo、redo 和 binlog。 |
| **B** | COUNT(*)、COUNT(1)、COUNT(列) | 1/3 | 原理 | `COUNT(列)` 为什么不统计 NULL？ | 结论：`COUNT(*)` 统计行数，`COUNT(1)` 在常见 InnoDB 场景语义等价，`COUNT(列)` 只统计非 NULL 值。<br>是否走索引取决于执行计划、可见性和查询条件，不应死记固定速度结论。<br>大表精确计数要关注扫描成本和业务是否接受近似值。 |
| **B** | 分库分表和分区表 | 2/3 | 方案 | 分片键怎么选？跨分片查询怎么办？ | 结论：分区仍由一个数据库实例管理，分库分表把数据和压力拆到多个节点。<br>分片键应兼顾查询路由、数据均衡和扩容稳定性。<br>跨分片聚合、事务和排序会增加应用层复杂度，必须结合业务权衡。 |
| **B** | InnoDB 和 MyISAM 的区别 | 1/3 | 定义 | ①MyISAM 的 `count(*)` 为什么快？ | **结论：InnoDB 支持事务、行锁、外键和崩溃恢复，是 MySQL 5.5 起的默认引擎；MyISAM 这些都不支持。**<br>锁：InnoDB 是行锁；MyISAM 只有表锁，并发写能力差。<br>索引：InnoDB 是聚簇索引，数据和主键索引存在一起；MyISAM 是非聚簇索引，索引文件和数据文件分开。<br>`count(*)`：MyISAM 存了总行数，直接返回；InnoDB 因为 MVCC，不同事务看到的行数不同，要实时统计。<br>崩溃恢复：InnoDB 有 redo log；MyISAM 崩溃后表容易损坏。 |
| **B** | 3 层 B+ 树能存多少行 | 1/3 | 原理 | ①主键用 UUID 和用自增 ID，对 B+ 树有什么影响？ | **结论：主键是 bigint、单行 1KB 时，3 层约能存 2000 万行。**<br>计算：一页 16KB；非叶子节点每项 = 主键 8B + 页指针 6B = 14B，一页约 16384 / 14 ≈ 1170 个指针。<br>叶子节点每行 1KB，一页存 16 行。<br>3 层：1170 × 1170 × 16 ≈ 2190 万行。<br>主键用自增 ID，新数据追加在最后一页，插入效率高；UUID 无序，会导致页分裂和碎片，而且主键更长，二级索引也跟着变大。 |
| **B** | B+ 树索引为什么不适合大量随机写 | 1/3 | 本质原因 | 页分裂如何产生？ | 结论：随机插入可能导致页分裂、碎片和更多磁盘写入。通过合理主键、批量写入和控制索引数量降低维护成本。 |

## 九、Agent

| 优先级 | 题目 | 共识 | 要懂到哪一层 | 可能的追问 | 答案要点 |
|---|---|---|---|---|---|
| **S** | 长期记忆存哪些；记忆冲突怎么办 | 3/3 | 方案 | 记忆要不要带时间和来源？哪些内容不应存？ | 结论：长期记忆只存稳定、可复用且经用户同意的事实、偏好和任务约束。<br>每条记忆带来源、时间、置信度和作用域；冲突时按可信度和新鲜度处理，无法判定就询问用户。<br>密码、Token 和不必要的敏感信息不进入长期记忆。 |
| **S** | 临时偏好要不要存进长期记忆 | 3/3 | 方案 | ①怎么判断一个偏好是临时的还是长期的？ | **结论：不存进长期记忆，只放在当前会话的短期记忆（上下文）里。**<br>原因：临时偏好（"这次回答简短点""今天用英文"）只对当前任务有效，写进长期记忆会在之后的会话里被错误套用，污染记忆。<br>判断标准：用户是否明确说了"以后都这样"；是否在多次会话中反复出现；是否和稳定的身份、习惯相关。<br>处理：反复出现的临时偏好可以升级为长期偏好；拿不准时直接问用户"要不要记住这个偏好"。 |
| **S** | Agent 的上下文窗口怎么管理 | 3/3 | 方案 | ①摘要压缩会丢信息怎么办？②什么是 lost in the middle？ | **结论：按 token 预算分层组织上下文，只放当前步骤需要的信息，其余靠摘要压缩和按需检索。**<br>问题：窗口有上限；内容越长成本越高、速度越慢；放在中间位置的信息容易被模型忽略（lost in the middle）。<br>手段：滑动窗口保留最近 N 轮；早期对话做摘要压缩；长期记忆和知识库按需检索（RAG）；工具返回的大结果只保留关键字段，原文存到外部、只给引用。<br>分层：系统提示 + 记忆摘要 + 近期对话 + 当前任务，按预算分配 token，重要信息放在开头或结尾。<br>子任务交给子 Agent 在独立的上下文里执行，只把结论传回来。 |
| **S** | Agent 无限循环怎么设计终止条件 | 3/3 | 方案 | ①任务完成怎么判定？②终止后要返回什么？ | **结论：硬上限兜底 + 完成判定 + 无进展检测，三层同时生效。**<br>硬上限：最大迭代步数、token 或费用预算、总执行时长、工具连续失败次数。<br>完成判定：模型给出最终答案（不再调用工具），或调用显式的 finish 工具；关键任务再用校验器或评审模型确认目标是否达成。<br>无进展检测：连续 N 步状态没有变化、重复相同的工具调用、同一个错误反复出现时，停止或触发重新规划。<br>终止后返回已完成的进展、终止原因和下一步建议，必要时转人工处理。 |
| **S** | 工具参数每轮细微差别、本质无效尝试，怎么判定 | 3/3 | 本质原因 | ①相似度阈值怎么定？②判定为无效尝试之后怎么办？ | **结论：不能只看参数是否完全相同，要看这一步有没有带来新信息、有没有推进任务。**<br>参数层：参数归一化后再比较（去空格、统一大小写、键排序、数值取整），或计算参数的编辑距离 / 向量相似度，超过阈值视为同一次尝试。<br>结果层：连续多次返回相同或高度相似的结果（同样的空结果、同样的错误码），说明换参数没有效果。<br>进展层：最近 N 步内，任务状态、已收集的信息、目标完成度都没有变化。<br>触发后：滑动窗口内计数超过阈值 → 让模型反思并更换策略或工具；仍然无效就终止，请用户补充信息。 |
| **A** | 长期记忆和当前上下文冲突；记忆的版本、TTL、撤销 | 2/3 | 方案 | 新旧事实同时存在时如何覆盖？ | 结论：记忆记录应带版本、时间、来源、置信度、作用域和过期时间。<br>新事实只有在来源可信且作用域一致时覆盖旧事实，否则并存并标记冲突。<br>用户删除或撤回授权后要从检索索引和缓存中同步移除。 |
| **A** | 短期记忆和长期记忆的区别和实现 | 1/3 | 原理 | ①什么时候把短期记忆转成长期记忆？ | **结论：短期记忆是当前会话的上下文，会话结束就消失；长期记忆跨会话持久保存，需要时检索出来放进上下文。**<br>短期：对话历史、当前任务的中间结果，直接放在上下文窗口里，靠滑动窗口和摘要控制长度。<br>长期：存在数据库或向量库里；写入时机是对话中实时提取，或会话结束后批量提取；读取时按当前问题做语义检索，把 Top-K 注入提示词。<br>转换：会话结束时由模型从对话中提取值得保留的事实和偏好，经过冲突检测后写入长期记忆。 |
| **A** | 对话摘要压缩怎么避免丢失关键信息 | 2/3 | 方案 | ①摘要由谁来做？ | **结论：区分"必须原样保留"和"可以压缩"的信息，压缩时保留能追溯到原文的引用。**<br>必须保留：用户的明确要求和约束、已经做出的决策、关键数据（ID、数字、文件路径），抽成结构化状态单独维护，不参与压缩。<br>可以压缩：过程性的讨论、已完成步骤的细节。<br>可追溯：原文存到外部存储，摘要里留引用，需要时再检索回来。<br>分级压缩：越早的内容压缩得越狠，最近几轮保留原文。 |
| **A** | 工具调用失败：超时、重试、幂等、换策略 | 3/3 | 方案 | ①哪些错误适合重试，哪些不适合？ | **结论：按错误类型分别处理：临时错误重试，参数错误让模型修正，不可恢复的错误换方案或上报。**<br>临时错误（超时、限流 429、5xx）：指数退避重试，设置最大次数。<br>参数错误（4xx、校验失败）：把具体的错误信息作为工具结果返回给模型，让它修正参数。<br>权限不足、资源不存在：不重试，换工具或换路径，或者告知用户。<br>全程记录调用日志，失败次数计入终止条件。 |
| **A** | 什么是 Agent，由哪些部分组成 | 1/3 | 定义 | ①Agent 和普通的大模型问答有什么区别？ | **结论：Agent 是以大模型为大脑、能自主规划并调用工具来完成目标的系统，常见组成是"LLM + 规划 + 记忆 + 工具"。**<br>LLM：理解任务、推理和决策。<br>规划：把目标拆成子任务，并根据执行结果调整计划。<br>记忆：短期记忆（上下文）+ 长期记忆（外部存储）。<br>工具：搜索、代码执行、API、数据库等，让模型能获取信息、对外部世界产生作用。 |
| **A** | ReAct 模式 | 2/3 | 原理 | ①ReAct 和 Plan-and-Execute 有什么区别？ | **结论：ReAct（Reasoning + Acting）让模型交替进行"思考 → 行动 → 观察"，根据每一步的观察结果决定下一步。**<br>Thought：分析当前情况，决定下一步做什么。Action：调用某个工具。Observation：拿到工具返回的结果。<br>不断循环，直到模型判断可以给出最终答案。<br>优点：推理过程可见；能根据中间结果动态调整，减少凭空编造。<br>缺点：每一步都要调用模型，步骤多时慢、成本高，也容易陷入循环，需要终止条件。 |
| **A** | Agent 和 Workflow 的区别、怎么选 | 2/3 | 方案 | ①Dify、Coze 里的工作流属于哪一种？ | **结论：Workflow 的执行路径由开发者预先编排好，Agent 的执行路径由模型在运行时自主决定。**<br>Workflow：步骤固定、结果可预测、易调试、成本可控，适合流程明确的任务（如审批、固定格式的报告生成）。<br>Agent：灵活，能处理开放性问题，但结果不稳定、成本高、难调试。<br>选择：能用工作流解决的优先用工作流；路径无法提前确定时才用 Agent；实际项目常组合使用，在工作流的某个节点里放一个 Agent。 |
| **A** | 工具权限和高风险操作怎么控制 | 3/3 | 方案 | ①加了人工确认，会不会让 Agent 失去意义？ | **结论：最小权限 + 人工确认 + 隔离环境 + 可审计，不把安全寄托在模型的自觉上。**<br>最小权限：只给完成任务必需的工具和权限，读写分离，写操作限定范围。<br>人工确认（Human-in-the-loop）：不可逆的操作执行前，把具体内容展示给用户确认。<br>隔离：代码执行放进沙箱 / 容器；防提示词注入，外部内容不能触发高风险操作。<br>审计：记录每次工具调用的参数和结果，支持追溯和回滚。 |
| **A** | 怎么评估 Agent 效果；可观测性记录什么 | 3/3 | 方案 | ①没有标准答案的任务怎么评？ | **结论：从结果、过程、成本三个维度，用固定的测试集持续评估。**<br>结果：任务成功率、答案准确率；有标准答案的自动比对，开放性任务用 LLM-as-Judge 加人工抽检。<br>过程：工具调用是否正确、用了多少步、有没有无效循环、有没有越权操作。<br>成本：平均 token 消耗、耗时、费用。<br>每次改提示词或换模型后跑一遍回归测试集，防止效果退化。 |
| **B** | 多 Agent 协作模式 | 3/3 | 原理 | ①多 Agent 比单 Agent 好在哪？代价是什么？ | **结论：常见的有主从（Supervisor）模式、流水线模式、对等协作 / 辩论模式。**<br>主从：主 Agent 拆分任务、分派给专职的子 Agent，再汇总结果；最常用。<br>流水线：各 Agent 按固定顺序处理，前一个的输出是后一个的输入（如需求 → 编码 → 测试）。<br>辩论 / 评审：多个 Agent 各自给方案或互相审查，提升结果质量。<br>好处是上下文隔离、职责专一；代价是通信开销大、token 成本明显增加、协调出错时难排查。 |
| **B** | 任务规划、执行和重新规划 | 2/3 | 原理 | ①计划执行到一半发现走不通，怎么办？ | **结论：常见模式有 ReAct（边想边做）、Plan-and-Execute（先规划再执行）、Reflexion（执行后反思改进）。**<br>Plan-and-Execute：先由规划器生成完整的步骤列表，执行器逐步执行，出问题时重新规划；适合步骤多的复杂任务。<br>Reflexion / 自我反思：执行完后让模型评估结果、总结失败原因，带着反思重新尝试。<br>任务拆解：把大目标拆成可验证的子任务，每个子任务都有明确的完成标准。 |
| **B** | 怎么检索最相关的记忆 | 1/3 | 原理 | 关键词、向量和时间如何混合排序？ | 结论：先按用户、任务和权限过滤，再结合关键词、向量相似度、时间新鲜度和置信度排序。<br>检索结果要带来源和用途，避免把相似但无关的记忆直接当事实。<br>没有足够证据时返回未知并请求补充，而不是强行拼接。 |
| **B** | 什么场景需要 Human-in-the-Loop | 1/3 | 方案 | 人工确认放在工具调用前还是后？ | 结论：涉及金钱、删除、对外发布、权限变更和高不确定性决策时引入人工确认。<br>可先让 Agent 生成计划或预览，再在真正副作用操作前确认。<br>人工确认应展示目标、参数、影响范围和过期时间，并记录审计结果。 |
| **B** | 怎么防工具层的提示词注入 | 1/3 | 方案 | 外部网页内容和工具返回值应当被当成什么？ | 结论：外部内容和工具返回值都视为不可信数据，不能直接改变系统规则或权限。<br>采用内容分隔、输出清洗、工具参数白名单、权限校验和结果沙箱。<br>系统提示词中的防注入说明只能辅助，关键控制必须在代码和服务端。 |
| **B** | Agent 状态怎么持久化 | 1/3 | 方案 | 如何支持断点续跑？ | 结论：保存任务 ID、阶段、输入摘要、工具调用、结果和版本信息。每步写入可恢复状态，重启后从最后确认的幂等节点继续。 |
| **B** | 工具很多时怎么让 Agent 选对工具 | 1/3 | 方案 | ①工具描述怎么写？ | **结论：不要把所有工具一次性塞给模型，先缩小范围，再让模型选。**<br>路由：先做意图分类，按类别只暴露相关的工具子集；或者用向量检索，按问题召回 Top-K 个工具描述。<br>分层：把相关的工具交给专门的子 Agent，主 Agent 只负责选子 Agent。<br>描述质量：名称语义清晰；描述写明用途、适用和不适用的场景、参数含义和示例；相似的工具写清楚区别。 |
