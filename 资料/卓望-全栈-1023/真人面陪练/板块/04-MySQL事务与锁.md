# ④ MySQL 事务与锁

> 出处：N11、N13（原子性和持久性）、N2（锁表）、N1（AI 面：主从延迟）、N7（运维面：主从延迟指标）。编号见 `../面经原帖.md`。

## 追问链（真题）

1. InnoDB 怎么实现原子性和持久性 / update 怎么保证原子性和持久性（N11、N13）
2. MySQL 什么时候会锁表（N2）
3. 主从延迟的原因（N1、N7）

## 大纲

1. **ACID 各靠什么实现**：原子性靠 undo log（出错时按它回滚）；持久性靠 redo log（先写日志、顺序写，崩溃后按它恢复）；隔离性靠锁 + MVCC；一致性是前三者共同追求的目标
2. **一条 update 的过程**：加行锁 → 写 undo log → 改 Buffer Pool 里的数据页 → 写 redo log（prepare）→ 写 binlog → redo log 提交。中间这一段是两阶段提交，保证 redo log 和 binlog 一致
3. **隔离级别**：读未提交、读已提交、可重复读（InnoDB 默认）、串行化；分别对应脏读、不可重复读、幻读三个问题；MVCC 靠 ReadView 加 undo 版本链实现
4. **什么时候会锁表**：
   - 行锁加在索引上 → 更新条件没走索引，会锁住大量行，效果接近锁表
   - 执行 DDL 时要拿元数据锁（MDL）
   - 显式执行 `lock tables`
   - 可重复读级别下有间隙锁、临键锁，用来防幻读
5. **死锁**：两个事务加锁顺序不一致，互相等待；InnoDB 检测到后会回滚其中一个
6. **主从延迟**：主库写 binlog → 从库 IO 线程拉取到 relay log → 从库 SQL 线程回放
   - 原因：大事务、从库回放并行度不够、从库机器差或负载高、网络
   - 处理：拆分大事务、开启并行复制、关键的读请求走主库

## 一句话骨架

原子性靠 undo log，持久性靠 redo log，两者和 binlog 用两阶段提交对齐；行锁加在索引上，所以没走索引的更新会锁一大片；主从延迟出在从库回放跟不上。

## 易错点

- 把 undo log 和 redo log 的作用说反
- 以为 InnoDB 只有行锁，答不出「什么时候锁表」
