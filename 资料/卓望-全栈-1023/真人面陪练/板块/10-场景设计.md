## 大纲

1. **订单通知失败**：先分清主次。订单是核心事务，通知是旁路功能 → 不回滚订单（用户已经下单成功了）→ 通知要保证可靠送达：本地消息表或事务消息、失败重试加退避、最后人工兜底；通知应该放在事务提交之后发（`@TransactionalEventListener(phase = AFTER_COMMIT)`），避免事务还没提交就发出了通知
2. **定时任务**：
   - 延迟的原因：上一次还没跑完、调度线程被阻塞、多个实例同时在跑
   - 防重复：分布式锁（Redis `SET NX` 加过期时间）；XXL-JOB 由调度中心统一调度，路由策略保证只派给一个执行器，再配阻塞处理策略（单机串行或丢弃后续调度）
   - 防漏：不要按「当前时间往前推 5 分钟」捞数据，而是按状态字段捞「未处理」的数据，处理完再改状态；处理逻辑做成幂等（唯一键或状态机）
3. **设计模式**：
   - 单例：Spring 的 Bean、配置类、连接池
   - 工厂：根据类型创建对象，比如 BeanFactory
   - 策略：多种支付方式或通知方式，用来消除 if-else；在 Spring 里注入 `Map<类型, 策略>`，按类型取出对应的策略
   - 模板方法：固定流程的骨架，具体步骤留给子类实现，比如 JdbcTemplate
   - 代理：AOP
   - 观察者：Spring 的事件机制
   - 回答时最好能结合「我的项目里哪里用了」
4. **微服务划分**：按业务能力或领域划分（DDD 的限界上下文），做到高内聚、低耦合，每个服务有自己的数据，边界和团队对齐；gateway 是统一入口，负责路由、鉴权、限流、日志
5. **秒杀**：前端限流（按钮置灰）→ 网关限流 → 在 Redis 里预扣库存（用 Lua 脚本保证原子性）→ 用 MQ 异步下单削峰 → 数据库用乐观锁兜底防超卖 → 用唯一索引防重复下单 → 热点商品隔离
6. **请求全过程**：前端发出 GET 请求 → DNS、TCP、HTTP → 网关或 Nginx → Controller 校验参数 → Service → Mapper 查库（可以先查缓存）→ 返回 VO 组成的 JSON → 前端拿到数据更新响应式状态 → 页面渲染。上传文章还要加上：校验、XSS 过滤 → 存正文 → 生成摘要（截取或调用 AI）→ 回显
7. **对接外部接口**：先拿到对方的接口文档和测试环境 → 申请凭证（AppKey / Secret，或 OAuth）→ 按约定的协议签名、处理超时和重试、做好幂等 → 记录调用日志
8. **MQ 对比**：Kafka 吞吐量高，适合日志和大数据流；RocketMQ 适合业务消息，事务消息、延时消息、重试和死信队列更完善

## 一句话骨架

场景题先分清「核心链路」和「旁路」，再说怎么保证不重复（锁、幂等）、不丢失（状态捞取、重试、消息表）、扛得住（限流、异步、削峰）。

## 易错点

- 订单通知失败答成「整个事务回滚」
- 设计模式只会背名字，说不出业务场景

## 自测

- 用三句话答「订单成功、通知失败要不要回滚」
- 说一个你项目里可以用策略模式改造的地方
