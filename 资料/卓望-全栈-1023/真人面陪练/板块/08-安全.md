# ⑧ 安全

> 出处：N5（敏感字段、password、VO）、N6（密码和身份证存储、加盐）、N13（为什么不明文、为什么加盐）、N4 / N12（SQL 注入）、N2 / N4（MyBatis `#` 和 `$`）、N11（文件上传）、N2（AES）、N1（AI 面：XSS）。编号见 `../面经原帖.md`。

## 追问链（真题）

1. 密码和身份证号怎么存储（N6）→ 为什么不能明文存密码 → 为什么要加盐（N13）
2. 加盐哈希后，登录时怎么校验（N6）
3. 身份证号和密码能用同一套方案吗（N6）
4. 实体里有前端不显示的字段，有没有安全风险 → 如果是 password 呢 → VO 怎么处理敏感字段（N5）
5. 什么是 SQL 注入，怎么避免（N4、N12）→ MyBatis 里 `#` 和 `$` 的区别（N2、N4）
6. 文件上传有哪些安全问题（N11）
7. AES 相关（N2）
8. XSS 是什么，分几种（N1，AI 面）

## 大纲

1. **根问题**：数据库万一泄露，怎么把损失降到最小 → 先问这份数据要不要还原出原文
2. **密码**（只需要比对，不需要还原 → 用单向哈希）：
   - 加盐的目的：防彩虹表（别人预先算好了常见密码的哈希值），并且让相同的密码算出不同的哈希
   - 每个用户随机生成一个盐，和哈希值一起存
   - 登录校验：取出这个用户的盐，和输入的密码一起重新算哈希，再比对
   - 推荐用 BCrypt：盐内置在结果里，而且是慢哈希，计算成本可调
3. **身份证号**（业务上要展示和核验原文 → 只能用可逆加密）：用 AES 加密后存储；密钥放在 KMS 或配置中心，不写进代码；需要按身份证号查询时，额外存一列哈希值做等值匹配；展示时脱敏
4. **敏感字段**：前端不显示不等于后端没返回，按 F12 就能看到 → 返回给前端用 VO / DTO，只放需要的字段；再用 `@JsonIgnore` 兜底
5. **SQL 注入**：把用户输入直接拼进 SQL，改变了 SQL 的语义 → 用预编译和参数化（PreparedStatement）；MyBatis 的 `#` 是预编译占位符 `?`，`$` 是直接替换字符串；`$` 只用于表名、排序字段这类场景，而且要做白名单校验
6. **XSS**：分存储型、反射型、DOM 型 → 防御：输出时转义、设置 CSP、Cookie 加 HttpOnly
7. **文件上传**：用白名单校验扩展名、MIME 类型和文件头（魔数）；限制大小；文件重命名；存储目录不给执行权限，或者直接用对象存储；防路径穿越；必要时做病毒扫描
8. **AES**：对称加密，分组长度 128 位，密钥 128 / 192 / 256 位；模式里 ECB 不安全，推荐 GCM（自带完整性校验）

## 一句话骨架

先问数据要不要还原：密码只需比对，用加盐慢哈希；身份证要还原，用 AES 加密、密钥单独管理；返回给前端只走 VO；SQL 一律参数化，`$` 只用在白名单场景。

## 易错点

- 身份证号也用哈希存（那样就展示不出来了）
- 以为前端不显示的字段就没有风险
