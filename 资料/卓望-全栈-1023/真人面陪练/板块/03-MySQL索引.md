# ③ MySQL 索引

> 出处：N4、N2、N11、N13、N6。编号见 `../面经原帖.md`。

## 追问链（真题）

1. 用过 MySQL 吗 → 为什么用 B+ 树，不用 B 树（N4）
2. 聚簇索引和非聚簇索引（N4）
3. 联合索引；ABC 联合索引，只查 B、C 能查出来吗（N4）
4. 索引为什么会失效（N2、N11）
5. 用了索引还是慢，怎么办（N13）
6. 一亿条流水，查最近一天的，怎么优化 → 除了索引、覆盖索引、分区分表，还有什么思路（N6）
7. MySQL 分区和分表的区别（N13）

## 大纲

1. **根问题**：数据在磁盘上，查询慢就慢在磁盘 IO 次数多 → 索引的所有设计都是为了少读几次磁盘
2. **B+ 树和 B 树**（这是根问题带来的结果）：
   - 非叶子节点只存键 → 一页能放更多键 → 树更矮，三层就能存千万级数据
   - 数据全在叶子节点，叶子之间用链表串起来 → 范围查询顺着链表扫
   - 每次查询都走到叶子，耗时稳定
3. **聚簇索引和二级索引**：InnoDB 主键索引的叶子存整行数据；二级索引的叶子存主键值，查到以后还要拿主键回主键索引查一次（回表）；查询的列全在索引里时不用回表（覆盖索引）
4. **联合索引 (a, b, c)**：先按 a 排序，a 相同再按 b 排，以此类推 → 最左前缀原则
   - 只查 b、c：**结果能查出来**，但用不上这个索引的有序查找，一般是全表扫描
   - 如果要查的列都在索引里，可能走索引全扫描
   - MySQL 8.0.13 以后有索引跳跃扫描（skip scan），某些条件下能用上
5. **索引失效**：对索引列用函数或做计算；隐式类型转换（比如 varchar 列传数字）；`like '%xx'` 左模糊；不满足最左前缀；`OR` 里有没索引的列；联合索引中范围条件后面的列；优化器判断全表扫描更快
6. **用了索引还慢**：先 `explain` 看 `type`、`key`、`rows`、`Extra`（有没有 `Using filesort`、`Using temporary`）→ 回表太多就改成覆盖索引 → 深分页用游标或延迟关联 → 单表太大就分区或分表 → 历史数据归档
7. **一亿条流水查最近一天**：时间字段建索引 + 按时间分区（查询时只扫相关分区）+ 只查需要的列；其他思路：归档历史数据、预先算好的汇总表、交给 ES 或数仓、读写分离、缓存
8. **分区和分表**：分区是存储引擎层把一张逻辑表拆成多个物理文件，对应用透明，仍然在一个库里；分表是应用层或中间件拆成多张表（可以跨库），需要路由，能突破单机瓶颈

## 一句话骨架

索引的一切都为了减少磁盘 IO：B+ 树矮且叶子成链；二级索引要回表、覆盖索引能省掉回表；联合索引按最左前缀；慢了先 `explain`，再看回表、分页、数据量。

## 易错点

- 「ABC 查 B、C 能查出来吗」：别直接答「查不出来」，要说结果能查出来，只是用不上索引的有序查找
- 分区和分表混成一回事

## 自测

- 从「磁盘 IO」出发，推出 B+ 树的三个特点
- 写一条会因为隐式类型转换导致索引失效的 SQL
