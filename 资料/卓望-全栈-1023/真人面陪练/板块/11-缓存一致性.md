# ⑪ 缓存一致性

> 出处：N6（先更新库再删缓存、延迟双删）、N13（数据一致性以哪个为准）。编号见 `../面经原帖.md`。

## 追问链（真题）

1. 先更新数据库再删缓存，能保证最终一致吗（N6）
2. 延迟双删的流程（N6）
3. 数据一致性以哪个为准（N13）

## 大纲

1. **以数据库为准**，缓存只是副本
2. **为什么删缓存，而不是更新缓存**：并发写的时候，更新缓存的顺序可能和更新数据库的顺序不一致；而且写多读少时，更新缓存是白费功夫
3. **先更新库，再删缓存**：大多数情况下没问题
   - 仍有一个不一致的窗口：读请求缓存没命中，读到旧值 → 写请求更新库并删缓存 → 读请求把旧值写回缓存。要发生这种情况，读请求得比写请求还慢，所以概率低
   - 删缓存失败也会不一致 → 失败重试，或者投 MQ 重试，或者订阅 binlog（Canal）去删
4. **先删缓存，再更新库**：问题更大（刚删完，读请求就把旧值回填了）→ 所以有延迟双删：删缓存 → 更新库 → 等一段时间（要大于一次「读库 + 回填」的耗时）→ 再删一次
5. **兜底**：缓存都设置过期时间
6. **要求强一致**：用分布式锁，或者干脆不缓存

## 一句话骨架

以数据库为准，写操作删缓存而不是更新缓存；先更新库再删缓存只剩一个小概率窗口，删除失败靠重试或 binlog 补删，最后用过期时间兜底。

## 易错点

- 说「先更新库再删缓存」能保证强一致

## 自测

- 用时间线画出「先更新库再删缓存」仍然不一致的那个窗口
