## 一、工具与协议：Function Calling、MCP、Skill、Workflow

| 概念 | 一句话 | 容易混的地方 |
|---|---|---|
| Function Calling | 模型按 JSON Schema 输出「要调哪个函数、传什么参数」，由程序去执行，再把结果交回模型 | 模型自己不执行任何东西，执行的是外面的程序 |
| MCP | 一套标准协议，把外部能力（工具、资源、提示词）用统一格式暴露给任何支持它的 AI 客户端 | 和普通 API 的区别：API 是给程序调的，各家格式不同；MCP 是给模型调的，自带工具描述，接一次所有客户端都能用 |
| Skill | 一个文件夹：说明文档 + 脚本 + 资源。模型平时只看到名字和描述，判断需要时才加载全文（渐进披露） | 和工具的区别：工具是「一个动作」，Skill 是「一套做事方法」，里面可以调用多个工具；Skill 进的是上下文，MCP 工具是被调用的 |
| Workflow | 流程由人写死：第 1 步做什么、第 2 步做什么，模型只负责其中某些节点 | 和 Agentic 的区别见第二节 |

**真题和答法**

- **为什么把 Workflow 改成 Skill？两者各有什么优缺点？**（F、G）
  - Workflow：可控、可预测、好调试、成本稳定；缺点是死板，遇到流程外的情况就处理不了，每加一个分支都要改代码
  - Skill：灵活，模型能按情况组合步骤，改说明文档就能迭代；缺点是不稳定，模型可能不按文档走，评测成本高
  - 选择：步骤确定、合规要求高 → Workflow；开放、多变的任务 → Skill / Agent；常见做法是两者混合，Workflow 管大流程，个别节点交给 Agent
- **怎样判断一个 Skill 好不好？怎么验证它按预期运行？**（G）
  - 三个维度：触发准（该用的时候用了，不该用的时候没用）、执行稳（同一输入多次结果一致）、结果对（对照标准答案）
  - 验证：准备评测用例集，正例和反例都要有，批量跑，看触发率和正确率
- **Skills 怎么组织、识别和召回？相似提示词怎么保证准确率？**（A2）
  - 模型靠 Skill 的「名字 + 描述」决定加载哪个，所以描述要写清「什么时候用、什么时候不用」，最好带反例
  - 相似的 Skill 要在描述里写明边界；用一组相似问法做评测，统计误触发率，再改描述
- **Skill 和 MCP 有哪些安全规范？**（E）
  - 最小权限：只开放必要的工具，写操作要二次确认；鉴权放在服务端，不靠 prompt
  - 输入校验，防注入；敏感数据不返回给模型；全部调用留日志
- **我的实践**：YonWork MCP 插件，素材库里的关键词是「说明放进 MCP」「答错分两层」——**具体做法待确认**，二面前一定要能讲清楚

## 二、Agent

| 概念 | 一句话 | 容易混的地方 |
|---|---|---|
| Agent | 大模型 + 循环：自己决定下一步 → 调工具 → 看结果 → 再决定，直到完成 | 和 Chat 的区别：Chat 一问一答，Agent 会自己多步执行 |
| ReAct | 「想（Thought）→ 做（Action）→ 看结果（Observation）」交替循环 | ReAct 是 Agent 最基础的一种循环模式，不等于 Agent 本身 |
| Workflow vs Agentic | Workflow 是人定流程；Agentic 是模型定流程 | 两者不是二选一，可以嵌套 |
| Multi-Agent / Subagent | 主 Agent 把子任务分给子 Agent，每个子 Agent 有独立的上下文，做完只把结论交回 | 主要价值是**隔离上下文**和并行，不是「人多力量大」 |
| Harness | 模型外面那层工程：工具定义、循环控制、上下文管理、权限、日志。Claude Code、Codex 就是 harness | 换模型不换 harness，效果也会变；Agent 之间的差异主要在 harness |

**真题和答法**

- **在大模型基础上构建 Agent，比原始大模型多做了哪些事？**（D）
  - 规划（拆任务）、工具调用（读写外部世界）、记忆（跨轮保存状态）、反馈循环（根据结果调整）、终止条件
  - 加上工程保障：权限控制、出错重试、日志和可观测性
- **AI 怎样判断已经完成，并停下来？**（G）
  - 模型不再调用工具、直接给出最终回答；或者显式调用一个「完成」工具
  - 更可靠的做法是外部验收：测试通过、满足预先写好的验收标准
  - 兜底：最大步数、token 预算、超时
- **Agent 适配只是模型适配吗？不同 Agent 真正的差异在哪？**（G）
  - 不只是模型。差异主要在 harness：工具集和工具描述、system prompt、上下文怎么压缩、权限模型、循环策略
- **Multi-Agent 怎么协同？subagentA 的结果怎么传给 B？几万字也放进 context 吗？**（B 一、B 三）
  - 不放全文。子 Agent 只交回摘要或结构化结论；大的产出写成文件，只传路径，下游需要时再读
  - 有依赖的串行执行，没依赖的并行
- **编排支持条件、循环、退出、replan 吗？**（B 三）
  - 用图来编排（例如 LangGraph）：节点 + 条件边就能表达分支和循环；replan 就是一个「结果不满意就回到规划节点」的条件边
- **意图路由用规则、小模型还是主模型？**（F）
  - 先规则（快、便宜、可解释）→ 规则覆盖不了的交给小模型分类 → 复杂、模糊的才交给主模型
  - 依据是延迟、成本、准确率三者的权衡；用评测集比较各方案的准确率
- **用户欺骗 Agent，诱导它把风险等级标成 low，怎么办？**（B 三）
  - 风险判定不能只靠模型：关键字段用规则或独立模型复核；高风险操作强制人工确认；用户输入和系统指令隔开，不让用户输入覆盖规则
- **LangChain、LangGraph 是什么？优缺点？用过吗？**（F）
  - LangChain：组件库（prompt 模板、链、工具、检索）；LangGraph：用图编排 Agent，有节点、State、条件边，支持循环、持久化、人工介入
  - 优点是搭得快；缺点是抽象层多、版本变动快、出问题难调试
  - **用没用过，按实际情况答**（待确认）
- **我的实践**：我的多模型协作就是一套人工编排的 Multi-Agent——「主脑」负责拆解、决策和验收，「干活的」负责检索和实现；任务书固定写背景、任务、边界、验收标准；交回的结果要求带路径和行号，由主脑抽查（出处：`D:\work\AGENTS.md`）

## 三、上下文、记忆、Prompt

| 概念 | 一句话 |
|---|---|
| 上下文工程 | 决定每一轮往窗口里放什么：规则、工具描述、检索结果、历史、摘要。比写好一句 prompt 更重要 |
| 上下文压缩 | 快超限时把旧对话压成摘要，保留结论和未完成的事项，丢掉过程 |
| 会话隔离 | 每个会话有独立的状态，不同对话不共享同一个消息池 |
| 记忆分层 | 工作记忆（当前上下文）→ 短期记忆（本会话摘要）→ 长期记忆（向量库、用户画像） |

**真题和答法**

- **一次输入超过上下文限制，怎么处理？**（B 一）
  - 截断或滑动窗口（最简单，会丢信息）；摘要压缩；RAG 按需检索，不全部塞进去；分块处理再汇总（map-reduce）；交给子 Agent 分担
- **摘要放 System 还是 User？**（B 一）
  - System 放稳定的规则和角色；会变的会话摘要一般作为一条消息放在历史开头
  - 理由：System 内容稳定才能利用 prompt 缓存；把摘要混进 System，规则和临时信息分不清
- **上下文压缩时怎么保证数值精确？**（快手测开 10-08）
  - 数值不进压缩：压缩时只留字段名，数值由工具重新查出来再注入。模型复述数字容易出错
- **多个对话共享同一个消息池有什么问题？根源是什么？更好的做法？**（二面博客第 15 问）
  - 问题：串话，A 对话的信息出现在 B 对话里，状态互相污染
  - 根源：状态是全局的，没有按会话划分
  - 做法：按 session id 隔离状态，每个会话有自己的消息列表和记忆
- **智能体记忆有哪些实现思路？记忆里有错误数据怎么处理？**（D、B 一）
  - 思路：会话结束后把一批消息交给模型抽取成要点，存入长期记忆；用的时候按相关性检索出来
  - 错误数据：每条记忆带来源和时间；冲突时以新的为准或者请用户确认；提供删除和更正的入口
- **prompt 调了很久效果仍然不好怎么办？**（H）
  - 先判断问题出在哪：缺信息、任务太大、指令互相冲突，还是模型能力不够
  - 对应的办法：补上下文、给示例（few-shot）、拆成小任务、要求结构化输出、换更强的模型；prompt 解决不了的，就改流程或者加工具
- **我的实践**：任务书要求「接收方看不到我们的对话，背景、路径、目标要写全」，这就是上下文工程（出处：`D:\work\AGENTS.md` 2.1 节）

## 四、评测与效果指标（7 篇，最稳的考点）

| 概念 | 一句话 |
|---|---|
| 离线评测 | 构造用例集 + 标准答案，批量跑，看准确率 |
| 线上指标 | 采纳率、转人工率、用户反馈、任务完成率 |
| LLM 当裁判 | 用一个模型按评分标准给输出打分；要用人工抽检校准它 |
| RAGAS | RAG 的评测框架：忠实度（回答是否基于检索内容）、答案相关性、上下文精确率和召回率 |

**真题和答法**

- **怎么证明优化有效？**（C、D）
  - 同一个评测集，优化前后各跑一次对比；上线后做 A/B；指标要提前定好，不能事后挑
- **标准答案怎么定？离线用例和线上真实情况一致吗？**（F）
  - 标准答案请领域专家或值班人员审核；用例从线上真实问题里抽样，再补上边界情况；定期用线上的 badcase 补充用例集
- **怎么降低评测成本？**（G）
  - 分层：先用便宜的规则检查格式和硬性约束，再用 LLM 裁判，最后人工只抽检
  - 每次改动只跑受影响的那部分用例
- **AI Coding 上线后发现一个没验证到的 badcase，怎么办？**（A1）
  - 先止血（回滚或修复）→ 把这个 case 加进测试集 → 回头查为什么漏了：是验收标准没写到，还是测试没覆盖到 → 改流程，不只改这一处代码
- **AI 代码生成率怎么统计？**（二面博客第 4 问）
  - 常见口径：AI 生成并被采纳的代码行数 ÷ 提交的总行数，靠工具埋点统计
  - 自己的口径要说实话：TeamMatch 是课程要求 AI 编码 95% 以上（出处：`一面-1022.md:27`）
- **我的实践**：一面 AI Coding 题就是完整的评测闭环——开工前先人工写好每条样本的预期结果、20 条边界样本、自己造 4 条新数据换着验收，另开一个对话做只读审查，专门检查有没有硬编码（出处：`面试记录\一面-1022.md:44-51`）

## 五、RAG 与向量库（了解即可）

- **流程**：文档切分 → 向量化 → 入库 → 检索 → 重排（rerank）→ 和问题一起交给模型生成
- **向量检索 vs BM25**：向量检索按语义找，同义词也能找到，但专有名词、编号这类精确匹配弱；BM25 按关键词找，精确但不懂同义。混合检索取长补短，两路结果用 RRF（按名次倒数加权）融合，再 rerank
- **切分策略**：固定长度加重叠；按标题等文档结构切；按语义切。非 Markdown 文档可以按段落、句子切，或者先转成结构化文本
- **检索取多少条**：用评测集调出来，不是拍脑袋。取多了噪声多、可能引发幻觉，取少了会漏掉答案
- **向量库索引**：FLAT 暴力搜索最准、最慢；IVF 先聚类，只在最近的几个簇里搜；HNSW 用分层图，又快又准，但占内存
- 项目里没做过 RAG 就直说，讲到原理为止

## 六、防幻觉、安全、越权

- **防幻觉**（D）：答案必须基于检索或工具拿到的数据，并给出出处；数字一律由工具取，不让模型自己编；要求结构化输出再做校验；允许模型回答「不知道」；用另一个模型交叉审查
- **模型可能不遵守 Skill 文档，高合规场景怎么保证不越权？**（G）
  - prompt 约束不可靠，要靠**架构**：权限在工具层和服务端校验；模型只能调白名单里的工具；高风险操作必须人工确认
- **保密内容放进上下文后怎么防止泄露？**（F）
  - 最好的办法是敏感内容根本不进上下文
  - 必须读的话，由一个隔离的子 Agent 读，只对外输出抽象后的结论（例如诊断规则），不输出原文
  - 输出过滤只能当最后一道兜底：主 Agent 自己约束输出和另设一个审查 Agent 相比，后者更独立，但两者都挡不住所有绕法
- **我的实践**：「独立对话做只读审查」就是用隔离的上下文做审查（出处：`一面-1022.md:48`）

## 八、LLM 基础

- **对神经网络的理解**（D）：多层「线性变换 + 非线性激活」的组合，用反向传播和梯度下降调整参数，去拟合数据
- **大模型**：Transformer 结构，核心是自注意力（每个词都看其他所有词，决定该关注谁）；训练目标是预测下一个 token；预训练之后再经过指令微调和对齐
