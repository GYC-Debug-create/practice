## 一、Java 集合

### 1. HashMap 底层、put 流程（来源：B 一、B 二、A2）
- JDK 8：数组 + 链表 + 红黑树。链表长度到 8 **且**数组长度 ≥ 64 才树化，否则先扩容；节点数降到 6 退回链表
- put：`hash = h ^ (h >>> 16)` 让高位参与运算 → 下标 `(n - 1) & hash` → 空桶直接放；key 相同就覆盖；否则尾插到链表或红黑树
- 元素个数超过 `容量 × 0.75` 就扩容为 2 倍
- 容量必须是 2 的幂：这样 `(n - 1) & hash` 才等于取模，而且扩容时能快速拆分

### 2. 扩容迁移、头插法为什么成环（来源：A2）
- JDK 8 迁移：看 `hash & oldCap`，结果是 0 就留在原下标，否则移到「原下标 + oldCap」，不用重新算 hash
- JDK 7 是**头插法**，迁移时链表顺序会反转。两个线程同时扩容，一个线程迁移到一半挂起，另一个已经把链表反转，前一个线程恢复后会让两个节点互相指向，形成环，之后 get 就死循环
- JDK 8 改成尾插，保持原顺序，不会成环，**但仍然线程不安全**

### 3. HashMap 线程安全吗？举例证明（来源：B 一、B 二）
- 不安全。例子一：两个线程同时 put 到同一个空桶，都判断为空，后写的覆盖先写的，丢数据
- 例子二：`++size` 不是原子操作，size 会算少
- 怎么证明：开 2 个线程，各 put 1 万个不同的 key，join 后打印 size，多跑几次会出现小于 20000
- 替代：`ConcurrentHashMap`；`Collections.synchronizedMap` 和 `Hashtable` 是整表加锁，性能差

### 4. ConcurrentHashMap 怎么实现（来源：A2）
- JDK 7：Segment 分段锁，每段一把 ReentrantLock
- JDK 8：Node 数组 + CAS + synchronized。空桶用 CAS 放；非空就 synchronized 锁住**桶的头节点**，锁粒度是一个桶
- 计数用 `baseCount` + `CounterCell` 数组分散竞争（和 LongAdder 思路一样）
- 扩容时多个线程按区间一起迁移，迁完的桶放 ForwardingNode，其他线程碰到就去帮忙
- key 和 value 都不允许 null：并发下 `get` 返回 null，分不清是没有这个 key 还是值本身为 null

### 5. Collection 实现；ArrayList vs LinkedList 顺序插 1000 万条（来源：B 二）
- List：ArrayList、LinkedList、CopyOnWriteArrayList；Set：HashSet、LinkedHashSet、TreeSet；Queue：ArrayDeque、PriorityQueue、BlockingQueue。Map 不属于 Collection
- 尾部顺序 add：**ArrayList 更快**。均摊 O(1)，内存连续、缓存命中好；扩容次数是 log 级，拷贝用 `System.arraycopy`
- LinkedList 的额外损耗：每个元素都 new 一个 Node（对象头 + prev / next 两个引用），内存是 ArrayList 的好几倍，GC 压力大，遍历时缓存不友好
- 少量数据两者差别不大；海量数据时差距被放大
- ArrayList 扩容：无参构造第一次 add 时容量变成 10，之后每次满了扩到 1.5 倍。知道数据量就 `new ArrayList<>(n)` 预分配

## 二、JVM

### 6. 垃圾回收：怎么判活、分代、收集器（来源：A1、A2）
- 判活：可达性分析，从 GC Roots 出发（栈里的引用、静态变量、常量、JNI 引用），找不到的就是垃圾
- 分代：新生代 = Eden + 2 个 Survivor（8:1:1），用复制算法，叫 Minor GC；对象熬过一定次数（默认 15）进老年代；老年代用标记-清除或标记-整理
- 收集器：JDK 8 默认 **Parallel**（吞吐优先）；CMS 低停顿，但有碎片，JDK 14 已移除；**G1 从 JDK 9 起默认**，把堆分成 Region，可以设停顿目标；ZGC 停顿在毫秒以下

### 7. 怎么降低 STW（补充，用友面经问过）
- 换低停顿收集器：G1 设 `-XX:MaxGCPauseMillis`，或者用 ZGC
- 调堆大小和新生代比例，减少对象过早进入老年代
- 代码层面少分配对象：避免循环里创建大对象，复用对象
- 先看 GC 日志找 Full GC 的原因：内存泄漏、元空间不够、晋升失败。不要调用 `System.gc()`

### 8. 对象创建过程（来源：A1）
1. 类加载检查：类没加载就先加载
2. 分配内存：堆规整用指针碰撞，不规整用空闲列表；并发分配靠 CAS 或者每个线程一块 TLAB
3. 把内存清零（所以成员变量有默认值）
4. 设置对象头：Mark Word（哈希码、GC 年龄、锁状态）+ 类型指针
5. 执行构造方法 `<init>`

### 9. 类加载、双亲委派（补充）
- 过程：加载 → 验证 → 准备（静态变量赋默认值）→ 解析 → 初始化（执行 static 块和静态变量的赋值）
- 双亲委派：先交给父加载器（启动类 → 平台 / 扩展 → 应用），父加载器加载不了才自己加载。目的是防止核心类被替换，比如自己写一个 `java.lang.String`

### 10. CPU 飙高怎么定位到线程（来源：A2）
1. `top` 找到 CPU 高的 Java 进程 PID
2. `top -Hp PID` 找到 CPU 高的线程 TID
3. `printf "%x" TID` 把 TID 转成十六进制
4. `jstack PID | grep -A 30 nid=0x十六进制` 看这个线程的调用栈
- 常见原因：死循环、频繁 GC（用 `jstat -gcutil` 看）、正则回溯。也可以用 Arthas 的 `thread -n 3` 一步看到

## 三、Java 并发

### 11. 线程池七大参数、执行流程（来源：A 二、A2）
- 七个参数：corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、handler
- 提交任务的流程：线程数 < core → 新建线程；否则放进队列；队列满了且线程数 < max → 新建非核心线程；还不行 → 拒绝策略
- 四种拒绝策略：Abort（默认，抛异常）、CallerRuns（由提交者自己执行）、Discard（丢掉）、DiscardOldest（丢掉最老的）
- 非核心线程空闲超过 keepAliveTime 会被回收

### 12. 线程池怎么配置；为什么不用 Executors（来源：A 二）
- CPU 密集型：线程数 ≈ 核数 + 1；IO 密集型：≈ 核数 × (1 + 等待时间 / 计算时间)，常取 2 × 核数起步，再压测调
- 用有界队列，自定义线程名（排查问题时一眼看出是哪个池），拒绝策略按业务选
- 不用 Executors：`newFixedThreadPool` 和 `newSingleThreadExecutor` 是无界队列，任务堆积会 OOM；`newCachedThreadPool` 的最大线程数是 `Integer.MAX_VALUE`，线程会爆
- **「遇到过哪些场景」**：TeamMatch 里有没有显式线程池，**未核对代码**。没用过就直说没用过，然后讲怎么配

### 13. 进程和线程的区别；数据通信、数据共享上的区别（来源：A 二）
- 进程是资源分配的单位，线程是 CPU 调度的单位；线程共享进程的堆、方法区、文件句柄，各自有栈、程序计数器、寄存器
- 切换开销：进程切换要换地址空间，比线程大
- 通信：进程之间要走 IPC（管道、消息队列、共享内存、信号量、信号、socket）；线程之间直接读写共享内存
- 共享：进程互相隔离，一个崩了不影响别的；线程共享内存，所以要同步（锁、volatile、阻塞队列），一个线程把进程搞崩，其他线程一起挂

### 14. volatile 的作用，能不能保证原子性（来源：A2）
- 两个作用：**可见性**（写完立即刷回主存，读的时候从主存读）；**禁止指令重排**（靠内存屏障）
- 典型用法：状态标志位；双重检查单例里的 instance 必须加 volatile，否则可能拿到还没初始化完的对象
- **不保证原子性**：`i++` 是读、改、写三步，两个线程会互相覆盖。要原子就用 `AtomicInteger`（CAS）或者加锁

### 15. ThreadLocal 原理，key / value 是什么，存在哪（来源：A2）
- 数据存在**每个 Thread 对象自己的 ThreadLocalMap** 里，不存在 ThreadLocal 里
- key 是 ThreadLocal 对象本身（**弱引用**），value 是存进去的值（强引用）
- 内存泄漏：key 被 GC 回收后，value 还被 Map 强引用着；线程池里的线程长期存活，value 一直不释放，还会把上一个请求的数据串到下一个请求
- 规矩：用完在 finally 里 `remove()`
- 场景：存当前登录用户；Spring 用它把数据库连接绑定到当前线程来管理事务

### 16. ReentrantLock、AQS、可重入、读写锁（来源：A2）
- AQS 的核心：一个 `volatile int state` + 一个双向等待队列。加锁就是用 CAS 把 state 从 0 改成 1，失败就进队列 park；释放时 state 减到 0 就唤醒下一个
- 可重入：记下持有锁的线程，同一个线程再次加锁时 state + 1，释放几次就减几次
- 公平和非公平：默认非公平，新来的线程先 CAS 抢一次，吞吐更高
- 读写锁：state 高 16 位是读锁计数、低 16 位是写锁重入数；读读共享，读写、写写互斥；写锁可以降级成读锁，读锁不能升级成写锁

### 17. synchronized vs ReentrantLock vs CAS（补充）
- synchronized：JVM 层实现，自动释放；有锁升级（无锁 → 轻量级 → 重量级；偏向锁在 JDK 15 起默认关闭）
- ReentrantLock：API 层实现，必须在 finally 里 unlock；支持可中断、`tryLock` 超时、公平锁、多个 Condition
- CAS：比较并交换，无锁乐观；有 ABA 问题（加版本号，用 `AtomicStampedReference`），竞争激烈时会一直自旋，浪费 CPU

## 四、MySQL

### 18. 一条 insert 怎么执行；事务提交时 redo / undo / binlog 的顺序（来源：A1）
1. Server 层：连接器 → 解析器 → 优化器 → 执行器，调用 InnoDB
2. InnoDB：要改的页不在 Buffer Pool 里就先读进来；**先写 undo log**（用于回滚和 MVCC）；改 Buffer Pool 里的页（变成脏页）；写 redo log buffer
3. 提交时走**两阶段提交**：redo log 写 prepare → 写 binlog → redo log 写 commit
4. 脏页之后由后台线程刷盘，不在提交时刷
- 为什么要两阶段：保证 redo 和 binlog 一致，否则崩溃恢复后的主库和靠 binlog 同步的从库数据会对不上。恢复时：redo 是 prepare 且 binlog 完整 → 提交；binlog 不完整 → 回滚

### 19. 三种日志的区别（补充，接上题）
| 日志 | 哪一层 | 记什么 | 作用 |
|---|---|---|---|
| redo log | InnoDB | 物理日志：某页改了什么；循环写 | 持久性，崩溃后恢复 |
| undo log | InnoDB | 逻辑日志：怎么撤回这次修改 | 原子性（回滚）+ MVCC 读旧版本 |
| binlog | Server | 逻辑日志：SQL 或者行的变化；追加写 | 主从复制、按时间点恢复 |
- 「双 1」配置：`innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`，每次提交都刷盘，最安全

### 20. 慢 SQL 怎么定位（来源：A1）
- 开慢查询日志：`slow_query_log=ON`，设 `long_query_time`；用 `mysqldumpslow` 或 `pt-query-digest` 汇总出最慢、最频繁的语句
- 用 `EXPLAIN` 看：`type`（ALL 是全表扫描）、`key`（实际用的索引）、`rows`（预估扫描行数）、`Extra`（Using filesort、Using temporary 要警惕）
- 优化手段：加或调整索引、避免索引失效、用覆盖索引减少回表、改写深分页、把大查询拆小

### 21. SQL 行转列，缺失科目填 0（来源：A2）
```sql
SELECT userid,
       SUM(CASE WHEN subject = '语文' THEN score ELSE 0 END) AS 语文,
       SUM(CASE WHEN subject = '数学' THEN score ELSE 0 END) AS 数学,
       SUM(CASE WHEN subject = '英语' THEN score ELSE 0 END) AS 英语
FROM score
GROUP BY userid;
```
- `ELSE 0` 让缺失的科目得 0；每人每科只有一行时，`SUM` 换成 `MAX` 也行
- 追问「科目不固定怎么办」：先查出所有科目，再动态拼 SQL，或者在应用层转

## 五、前端（部门是客户端 + 大前端；除第 22 题外都是**补充**）

### 22. 搜索框先发的请求后返回，怎么不让旧结果覆盖新结果（卓望 27 届全栈原题，电商搜索必备）
- 请求序号：每次发请求 `id = ++latestId`，回来时 `id !== latestId` 就丢掉
- 取消旧请求：`AbortController`，发新请求前 `controller.abort()` 掉上一个；fetch 和 axios 都支持传 `signal`
- 配合防抖减少请求次数
- React 里：在 `useEffect` 的清理函数里设 `ignore = true` 或者 abort；闭包读到旧 state 时，用 ref 或者函数式更新 `setX(prev => ...)`

### 23. 事件循环
- 先执行完同步代码 → 清空**所有**微任务（`Promise.then`、`queueMicrotask`）→ 取**一个**宏任务（`setTimeout`、IO、UI 事件）→ 可能渲染 → 再清空微任务……
- 常考输出顺序：`console.log` → `Promise.then` → `setTimeout`
- `await` 后面的代码相当于放进了 `.then`

### 24. 闭包、this、Promise
- 闭包：函数加上它定义时所在的作用域。用途：私有变量、防抖节流；坑：引用一直不释放导致内存泄漏，用 `var` 的循环里所有回调拿到同一个 i
- this 由调用方式决定：`obj.fn()` 指向 obj，直接调用指向 undefined（严格模式），`new` 指向新对象，`call` / `apply` / `bind` 手动指定；箭头函数没有自己的 this，用外层的
- Promise 三种状态，一旦变化就不再改变；`all`（有一个失败就整体失败）、`allSettled`（等全部结束）、`race`（谁先结束用谁）、`any`（谁先成功用谁）

### 25. 防抖和节流
- 防抖：停止触发 n 毫秒后才执行一次，用于搜索框输入
- 节流：n 毫秒内最多执行一次，用于滚动、resize、按钮连点
- 实现都靠闭包保存定时器或者上次执行的时间

### 26. Vue 基础
- MVVM：View ↔ ViewModel ↔ Model，数据变化自动更新视图，表单输入自动回写数据
- 响应式：Vue 2 用 `Object.defineProperty`，检测不到新增属性和数组下标修改；Vue 3 用 `Proxy`，没有这些问题
- 组件通信：父传子用 props，子传父用 emit，跨层级用 provide / inject，全局状态用 Pinia
- `computed` 有缓存，依赖不变就不重新算；`watch` 用于数据变化后执行副作用
- `v-if` 真正创建和销毁元素，`v-show` 只切换 `display`；列表的 `key` 帮助 diff 复用节点，不要用数组下标当 key

### 27. 从输入 URL 到页面显示；重排和重绘
- DNS 解析 → TCP 连接（HTTPS 还要 TLS 握手）→ 发 HTTP 请求 → 解析 HTML 建 DOM、解析 CSS 建 CSSOM → 合成渲染树 → 布局 → 绘制 → 合成图层
- 重排：几何属性变了（宽高、位置），要重新布局，开销大；重绘：只改外观（颜色），不用重新布局
- 减少重排：批量改样式（改 class）、动画用 `transform` / `opacity`（只走合成层）、不要在循环里读 `offsetHeight` 这类会强制布局的属性

### 28. HTTP 缓存、跨域
- 强缓存：`Cache-Control: max-age`（优先）或 `Expires`，命中就不发请求
- 协商缓存：`ETag` / `If-None-Match`，`Last-Modified` / `If-Modified-Since`，资源没变就返回 304
- 跨域：同源 = 协议、域名、端口都相同。解决办法：后端返回 CORS 头；开发环境用 dev server 代理；Nginx 反向代理
- 用友实习的联调经验能挂在这里（前端怎么转发请求）：**具体用的什么代理方式请你确认**

### 29. 首屏和长列表性能（电商页面）
- 指标：LCP（最大内容出现时间）、INP（交互响应）、CLS（布局偏移）
- 首屏：图片懒加载（`IntersectionObserver`）、路由级代码分割、CDN、压缩、骨架屏、关键资源 `preload`
- 长列表：虚拟滚动，只渲染可视区域的那几十条
- 图片：按屏幕尺寸给不同大小的图，用 WebP

### 30. 电商场景的坑
- 金额：用「分」作单位的整数，不用浮点数（`0.1 + 0.2 !== 0.3`）
- 大整数 ID：超过 2^53 的订单 ID，JSON 解析会丢精度，后端以字符串返回
- 防重复下单：前端点击后禁用按钮，**后端必须做幂等**（这部分已在 TeamMatch-八股第 5 题）
- 倒计时：用服务端时间校准，不信本机时间

## 六、场景题

### 31. 大文件里一堆无序数，全放内存会 OOM，怎么排序（来源：A 二）
1. 外部排序：分块读，每块大小能放进内存 → 块内排序后写成临时文件
2. k 路归并：每个临时文件开一个读指针，用小顶堆每次取最小值输出
3. 文件太多就分多轮归并；读写都用缓冲
- 如果数字范围有限，用计数排序或位图，一遍就够

### 32. uv、pv 怎么算，埋点怎么做（来源：H）
- pv = 页面被浏览的次数；uv = 去重后的用户数（按用户 ID，未登录按设备 ID）
- 埋点：前端在曝光、点击时上报事件（事件名、用户标识、时间、页面、参数）；用 `navigator.sendBeacon` 防止页面关闭时丢数据；批量合并上报
- 服务端：日志进 Kafka → 实时或离线计算
- uv 去重：数据少用 Set；数据多用 Redis HyperLogLog（12KB，误差约 0.81%）；用户 ID 是连续整数时可以用 Bitmap
- **项目里没有埋点**的话就直说，按原理答

### 33. 设计用户头像上传模块，前后端分开讲（来源：D）
- 前端：选文件 → 校验类型和大小 → 裁剪、压缩（canvas）→ 预览 → 上传（FormData，或者拿后端签名直传对象存储）→ 进度条、失败重试
- 后端：鉴权；校验 MIME 和文件头魔数（不信扩展名）；限制大小；用 UUID 重命名，防止路径穿越；存对象存储 + CDN，数据库只存 URL
- 其他要点：生成多种尺寸的缩略图、内容审核、清理旧头像；存储目录不给执行权限

### 34. 短信平台只能扛 100 QPS，生产 1 万 QPS，怎么限流，怎么和 MQ 结合（来源：C）
- 用 MQ 削峰：生产者把消息写进 MQ，消费者按 100 QPS 的速度消费
- 消费端用令牌桶控速；多实例时要做全局限流（Redis 令牌桶），否则每台机器各限 100，加起来就超了
- 拿不到令牌：不 ack，等一会儿重试或者投到延迟队列，**不能丢**
- 监控积压量，积压到阈值就告警或者扩短信通道；消费端要幂等，防止重复发短信

### 35. 下游服务挂了、大量报错，对你的业务有什么影响；监控和指标怎么设计（来源：D）
- 影响：请求卡在等下游超时 → 线程池、连接池被占满 → 自己也挂，层层传上去就是雪崩
- 应对：设置超时、熔断（Sentinel、Resilience4j）、降级（返回兜底数据）、用独立线程池隔离；重试要限次数、加退避，并且接口幂等
- 指标：请求量、错误率、延迟 P99（RED 三件套）+ CPU、内存、GC、连接池；按阈值告警
