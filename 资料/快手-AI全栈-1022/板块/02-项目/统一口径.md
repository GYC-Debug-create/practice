## 四、关键设计决策的因果链（架构层，面试时按这条线讲）

```
课程约束：过程分占 60%（开发过程 30% + 质量保证 30%），周期 16 周，4 人，单实例部署
   → 设计原则：P0 不引入 MQ、定时任务、分布式锁，复杂度压到最低
   → 一致性手段只用数据库自带的：事务、唯一索引、条件更新、行锁
   → 业务上的约束（谁能评谁、什么状态能申诉）用“入口约束”前置，减少并发路径
   → 账本设计：流水表是事实源，user.credit_score 是缓存，任何分数变化先有一条流水
```

每个点的“实际做法 / 备选 / 什么条件下换”：

| 设计点 | 实际做法 | 备选 A | 备选 B | 什么条件下换 |
|---|---|---|---|---|
| 防重复评价 | 联合唯一索引兜底 + 预检查 | 应用层锁 | Redis 锁 | 多实例且需要跨服务互斥时，锁只做性能保护，正确性仍留给唯一索引 |
| 多表同进同退 | 单库同事务 | 异步消息 + 补偿 | 本地消息表 | 跨服务、跨库时 |
| 复核并发 | 条件更新（状态机单字段） | 乐观锁版本号 | 悲观锁 | 一个对象被多个流程改且冲突少时用乐观锁；要先读多处状态再写时用悲观锁 |
| 申诉恢复并发 | 行锁 + 状态判断 + 幂等检查 + 唯一索引兜底 | 条件更新 | 分布式锁 | 状态判断只依赖一个字段时改条件更新 |
| 信誉分更新 | SQL 原子自增 | 读出来再写回 | 乐观锁 | 封顶规则要严格保证时，对用户行加锁 |
| 异常评价 | 评价人评完全部队友后整体判断，命中则批量挂起，管理员复核 | 单条判断 | 事后离线扫描 | 规则要实时拦截时 |
| 申诉与复核冲突 | 入口约束：待复核的评价不开放申诉 | 加锁互斥 | 状态机合并 | 入口约束难以保证时 |
| 列表分页 | 单用户流水用内存分页（项目未配分页插件，开发时有意选择） | 物理分页 | 游标 | 数据量大时 |

## 五、纠错：以下两处按真实情况讲，不要照简历原句

| 简历原句 | 统一口径 |
|---|---|
| “复核和申诉恢复先 SELECT FOR UPDATE 锁定评价行” | “**申诉恢复**用行锁；**复核**用条件更新。复核和申诉靠入口约束不同时碰同一条评价。” |
| 状态里的“恢复计分” | “评价有四个状态：正常、待复核、判为无效、保留但不计分。恢复是在信誉流水里追加一条反向流水，不是评价状态。” |

## 六、已知的不足（被问到就主动承认，并给改法）

| 不足 | 怎么说 |
|---|---|
| 信誉分封顶是“读累计 → 算 → 写”，没有加锁 | “P0 单实例，同一人同一项目被同时评价的窗口很小，我当时没加；审查里也提过建议加行锁。要补就对用户行加锁。” |
| 真并发没压测，测试是 Mockito 单测 | “唯一索引和事务的行为是 MySQL 保证的，单测验证了冲突后的处理和不落库；没有做真并发压测，这是后续要补的。” |
| 申诉恢复的幂等检查在默认隔离级别下的细节 | “我推演过：并发时会被唯一索引兜住，不会二次加分，但返回的是异常而不是‘已恢复’。没有实测。” |
| 没有监控、限流、刷新令牌（Pandora） | 如实说没做，给出做法 |

## 七、措辞

- 说“AI 辅助开发”，不说“vibe coding”。
- 说“框架层面借助 AI，设计和把关由我负责”，不说“技术不行”。
- 讲方案取舍时：“我们选了 A，因为约束是……；B 的优点是……缺点是……，条件变成……我会换成 B。”
- 不说“我们用了 B”，除非真的用过。
