# 项目讲述原则（所有项目题、所有公司都适用）

> 适用范围：TeamMatch、Pandora、用友实习，以及 AI Coding 题的复盘。所有口径文件、讲稿、模拟面试都按本文件来。

## 一、核心

**不讲**：「项目里是 X，但我知道 Y 更好」「当时没想到，现在会改成 Y」

**要讲**：「项目用 X，因为综合考量了 A 和 B。Y 也是一种做法，好处是……，但在我们的条件下代价是……」

也就是：把每一个设计都讲成**有意识的取舍**，原本的情况、其他方案都作为对照出现，不作为「遗憾」出现。

## 二、为什么

| | 事后诸葛亮式 | 决策式 |
|---|---|---|
| 面试官听到的 | 当时做得不好，事后才知道；出现两三次，会让人怀疑整个项目都是凑合的 | 知道有哪些方案、各自代价，按条件做了选择 |
| 考察点 | 只证明「现在懂了」 | 正好是二面考的「为什么这么做、换个方案行不行」 |
| 广度 | 要另外找机会展示 | 对照方案自然带出广度（Redis 锁、MQ、定时任务……） |

## 三、三种句式

1. **选择型**（最常用）：「这里用 X，主要考虑 A 和 B。对比过 Y，Y 的好处是……，但需要……，在我们 [规模 / 阶段 / 团队] 下不划算。」
2. **演进型**（条件变了才换）：「现在用 X 够用，因为 [条件]。如果 [条件变化，比如多实例部署、数据量到千万级]，会换成 Y，触发点是……」
3. **被问「有没有更好的做法」**：直接用演进型回答，**不说**「当时没想到」「当时没时间」

## 四、边界（不能越过）

- 「项目用 X」里的 X **必须是项目里真实存在的设计**。代码里没有的方案，只能放在「对比过的 Y」或「条件变化后会换成的 Y」里，**不能说成已经实现**
  - 原因：面试官虽然不会问具体源码，但会顺着问实现细节和效果（怎么做的、遇到过什么问题、效果怎么样）。说成已实现的东西答不出细节，会连带让整个项目失信。一面说过「失败后会重试」，代码里没有，就是例子
- 「对比过 Y」：当时确实没评估过的，用**演进型**句式，不说「当时评估过」
- 已知缺陷（例如某个分支返回体验不好）：不主动提；被问到时讲「正确性靠什么保证」+「这块我会怎么补」，用演进型

## 五、TeamMatch 示例

依据：`TeamMatch-八股.md`、`D:\work\求职\项目\TeamMatch\` 下的核对报告（只在本机）。

| 话题 | 决策式讲法 |
|---|---|
| 并发控制为什么用数据库，不用 Redis 锁 | 「并发控制全放在数据库层：唯一索引防重复、条件更新控制状态流转、申诉恢复加行锁。主要考虑两点：一是正确性要求高，约束放在数据最终落地的地方最可靠；二是单体服务，少一个组件就少一类故障。Redis 锁的好处是挡在数据库前面、减轻数据库压力，等多实例部署、并发上来以后，会把它加在前面做性能侧的互斥，数据库约束仍然保留做兜底。」 |
| 复核用条件更新，申诉恢复用 FOR UPDATE | 「复核只是一行记录的状态流转，一条 `UPDATE … WHERE status=待复核` 就能同时判断和修改，看影响行数就知道抢没抢到，不需要显式加锁；申诉恢复要先读评价状态、原流水是否生效、是否已经恢复过，读完再决定写不写，所以用 FOR UPDATE 把这几步锁在一起。」 |
| 信誉分冗余在用户表，另有流水表 | 「信誉分在用户表里存一份当前值，因为排行榜和个人页读得多，每次聚合流水代价高；每次变动同时写一条流水，两步在同一个事务里，流水是对账和追溯的依据。」 |
| 没有消息队列 | 「评价提交后的处理是同步做的，因为规模小、链路短，同步更好排查。用户量上来以后，会把通知和榜单刷新拆到 MQ 异步，消费端按业务唯一键去重。」 |
| 没有定时任务 | 「互评窗口到期没用定时任务，而是查询时发现过期就改状态（懒检查）。好处是不需要调度组件，多实例也不会重复执行；代价是状态更新不够及时。需要实时统计的时候，会加定时任务和分布式调度锁。」 |

## 六、怎么用

- 写口径文件时：每个设计点都按「项目用 X，因为 A 和 B；对照 Y」来写；真实设计带出处（文件 + 行号），对照方案标【对照，未实现】
- 模拟面试时：出现「但我知道」「当时没想到」「其实应该」这类说法，当场指出并改写

## 七、补充规则（2026-10-26，用户明确要求）

### 7.1 真实没考虑到的小问题：大方承认

- 课程项目没有上线实测，产品设计上有考虑不周的地方很正常，**不硬包装成取舍**
- 决策式只用在真实做过取舍的设计点上，不要每个缺口都硬套
- 承认时带三样：**自己怎么发现的 + 两种做法各自的代价 + 要补会怎么补**
- 例：「一个人能不能同时参加多个项目，P0 没定下来。限制成一个，满足不了多项目并行的真实需求；不限制，就能靠不结束项目、不结束互评绕开限制。要补的话……」
- 第四节的边界不变：没做过的不能说成做过

### 7.2 源文件是讲故事的素材

- 面试官不看源文件。文档、代码、记录是**组织语言和资料的素材**，判断标准只有一个：**对讲故事有没有帮助**
- 不逐条追问「这是不是你写的」；读到有用的素材，直接说它能怎么用进故事
- 只有一种情况要标归属：**明确是别人做的**，讲成「组员做的，我拿来用在……」，不说成自己做的（例：校园墙组队帖数据是组员爬的，我用来论证需求）
- 行号出处仍然写进口径文件，方便自己回查；讲的时候不念出处
