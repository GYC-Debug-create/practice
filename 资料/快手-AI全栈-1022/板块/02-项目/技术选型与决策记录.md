## 一、选型的方法（面试时的总述，30 秒）

> “技术选型我是这样做的：先把约束定清楚——课程实训、16 周、4 个人、单实例部署，而且课程要看开发过程和测试证据。然后让 AI 对每个决策点列出备选方案、优缺点和实现难度，我按‘能否在周期内做稳、能否被验证、出了问题能否回退’来选。选定后写进详细设计，变成全员冻结的规则。AI 出的方案我还会再让另一轮审查：比如推荐算法的方案，审查时发现了编译错误、接口路径写错、引用了不存在的数据访问类、还有查询次数的问题，修正之后才进入实现。”

三条判断标准（统一口径）：**① 能做稳；② 能验证；③ 能回退。**【口述，已确认】
- 能做稳：在周期、人手、单实例的约束内，实现得住、跑得稳。
- 能验证：能用测试和审查证明它对。
- 能回退：出了问题能退回，不引入新的运维负担。

### D. 推荐算法（你亲自设计并让 AI 实现的一块，决策有成文记录）

`推荐方案` 的“设计决策说明”表（原文意思）：

| 决策 | 原因（文档原文） |
|---|---|
| 技能相似度硬门槛 0.15 | 太低无意义，太高会误拦“匹配少但愿意学”的人 |
| 信誉硬门槛 80 | 跑路过的人不进推荐 |
| 排除队长自己 | 队长不需要被推荐给自己 |
| 技术分不分技能维度 | 四维评价里的技术分是整体能力，不是分 Java / Python 的打分 |
| 先验权重 5 | 3 到 5 次互评后真人评价接管；不设为 100，因为互评权重约等于信誉分/100 |
| 合作可信度只用信誉分 | 技术分已经在“技术可信度”的先验里出现，不重复计算 |
| 最终分用乘法 | 每个维度是闸门，不是加分项 |
| 批量预取 5 张表 | 一次推荐只发 5 条查询，不随候选人数增长 |

**AI 方案的审查**（`方案审查`，这是“我验收 AI 产出”的直接证据）：
- 结论：原方案**不能直接照抄实现**，编译失败点集中在推荐服务和互评数据访问层。
- 发现的问题：动态 SQL 的循环没有包在脚本标签里；引用了不存在的数据访问类和方法；技术画像按错误的主键批量查；**接口路径写错**——项目已配置统一前缀，再写一遍会变成重复前缀；用了和 M4 不同包的同名类，有混用风险。
- 同时审查了**对其他模块的影响**（只读不写）和**查询次数**（修正后循环内没有查询）。

## 三、面试里的回答模板

**“你为什么选 X 不选 Y？”**
> “我当时让 AI 把 X、Y 都列出来，比较优缺点和实现难度。结合我们的约束——单实例、16 周、要能验证——X 更合适，因为……；Y 的优点是……，但在我们的场景里代价是……。如果后面访问量/部署方式变成……，我会换成 Y。”

**“这个是你写的还是 AI 写的？”**
> “代码是 AI 生成的，分阶段做，每个阶段我先写清规格，再验证。规格和选型是我定的，写进了详细设计；验证用审查和单测。比如推荐算法的方案，AI 第一版有编译错误和路径错误，是审查之后才修正进入实现的。”

**“如果让你现场实现呢？”**
> “我会用同样的方式：先把要求和约束写清楚，让 AI 分步实现，每步用测试和审查验证；我的重点在规格、边界和验证。”
