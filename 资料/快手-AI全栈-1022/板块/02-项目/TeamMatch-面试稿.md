## 二、简历 5 个技术点（每点：口语稿 1 分钟内 + 四层证据）

### 技术点 1　防重复互评：唯一索引兜底

**【念】** 一个学生对一个队友，在一个项目里只能评一次。我在评价表上建了联合唯一索引，项目、评价人、被评价人三列。提交前先查一遍，查到就直接拒绝；但两个请求同时通过这一查，就会同时插入，这时数据库只放行一个，另一个抛唯一键冲突。我捕获这个异常，返回「已评价」的业务错误码，用户看到提示，不是 500，也不会多写流水、多加分。备选我评估过应用层加锁和 Redis 锁：前者多实例就失效，后者多一个依赖，还要处理锁过期；而且这个约束本来就是数据本身的性质，放数据库最可靠。验证上，单测模拟插入抛冲突，断言返回已评价且流水和分数都不写。真并发我没压测过。

| 层 | 内容 |
|---|---|
| 做了什么 | 联合唯一索引 + 提交前预检查 + 捕获 `DuplicateKeyException` 映射 `ALREADY_EVALUATED` |
| 为什么 | 备选 ① 先查再插：两个请求同时通过检查都会插入，只能提前拦不能兜底；② 应用层锁：多实例失效；③ Redis `SET NX`：多一个依赖，锁过期、抛异常不知道有没有加上。设计文档 8.3 节明确写「用数据库唯一约束兜底幂等性和重复提交」 |

### 技术点 2　写路径一致：同一事务

**【念】** 一次互评生效，要写三类数据：评价记录、信誉分流水、用户总分。我把它们放进同一个事务，任何一步插入行数不对就抛异常，整体回滚。复核通过更完整：评价状态、流水生效标志、用户总分三处一起改。为什么不异步：信誉分是用户看得见的账本，不能出现有流水没加分，或者加了分没流水。异步方案是最终一致，要处理重试、重复消费和补偿，P0 单库，同一个事务最简单。有一个坑我专门注意过：事务只对异常回滚，返回失败对象不回滚，所以申诉那条链路里，恢复服务返回失败时，调用方要主动转成异常。验证上单测覆盖了流水插入失败和总分更新失败两种，但这是 Mockito 层验证抛异常，没在真实 MySQL 上验证回滚。

| 层 | 内容 |
|---|---|
| 做了什么 | `submit` 整个方法一个 `@Transactional`：插评价、标签、流水、增量更新总分 |
| 为什么 | 备选：先写评价再异步算分（MQ / 定时任务），最终一致，要重试 + 幂等消费 + 补偿；设计上 P0 明确不引入，且总分是缓存、流水是事实源 |

### 技术点 3　并发与幂等（别念简历原句）

**【念】** 申诉恢复这条链路，我在事务里先用 `SELECT FOR UPDATE` 锁住那条评价行，再判断：评价已被判无效就拒绝；原评价的流水没生效就按「跳过」成功返回；已经有恢复流水就返回「已恢复」；都不是，才追加一条反向流水并回写总分。选悲观锁是因为这里要先读好几处状态再决定写不写，读和写之间不能让别人进来；乐观锁要加版本列还要重试，而这里冲突的处理就是跳过，不需要重试。重复请求靠四层拦：申诉状态不是待处理就拒绝，行锁加两次幂等检查，流水表唯一索引兜底。要说明：复核那条链路我没用 `FOR UPDATE`，用的是条件更新，下一点讲；简历上这两条写在一起，实际手段不同。

| 层 | 内容 |
|---|---|
| 做了什么 | 申诉恢复：`FOR UPDATE` 锁评价行 → 判评价状态 → 判原流水是否生效（未生效返回跳过）→ 判是否已有恢复流水（有则返回已恢复）→ 插入反向流水 + 回写总分 |
| 为什么 | 「读 → 判断 → 写」且读多处状态，用悲观锁；备选乐观锁（加 version 列，冲突要重试，这里冲突直接跳过，用不上）、Redis 分布式锁（P0 单实例不需要，账本一致性也不想依赖 Redis 可用）。设计文档 8.7 D-11 / D-13 已定 |
| 坏了怎么办 | 同一申诉被重复提交：① 申诉状态非 `pending` 直接拒绝；② 行锁 + 幂等检查；③ 流水唯一索引 `(source_type, source_id, user_id, change_type)` 兜底，不会二次加分。**已知细节（读代码推演，没实测）**：MySQL 默认可重复读，第二个事务在行锁上等待后，普通 `SELECT` 读的是事务开始时的快照，看不到对方刚提交的恢复流水，会走到插入，被唯一索引拦住抛异常。结果是不会二次加分，但返回的是异常而不是「已恢复」。要改成真幂等：捕获 `DuplicateKeyException` 当已恢复 |
| 怎么证明 | 单测：已存在恢复流水 → `alreadyRestored`；原流水未生效 → `skipped`。**真并发未压测，快照推演未实测** |

**【念】** 管理员处理申诉时，状态判断本身是先读后写，拦不住同时到达。所以我在恢复这一步做了保护：恢复事务里先对评价行 `SELECT FOR UPDATE`，两个请求在这里排队，排到的再检查原流水有没有生效、有没有恢复过。已经恢复过就不再加，最后还有流水表唯一索引兜底。所以不管几个管理员同时通过，分只会恢复一次。

### 技术点 4　状态流转与条件更新；测试

**【念】** 评价有四个状态：正常、待复核、判为无效、保留但不计分。注意「恢复」不是评价状态，是在流水表里追加一条反向流水。只有待复核的评价能被管理员处理。复核时我用一条条件更新：状态等于待复核才更新，影响行数不是 1，说明已被别人处理过，抛冲突异常，整个事务回滚。两个管理员同时点通过，一个更新到一行，另一个零行，不会重复加分；流水侧还有一道守卫，只更新未生效的流水。这个方案比乐观锁和悲观锁都轻，状态机单字段，一条语句既判断又修改，不需要版本列也不需要额外加锁。复核和申诉不会碰同一条评价，靠的是入口约束：待复核的评价不开放申诉。测试上，三个核心 Service 共七十一个单测，提交是我的账号；没有真并发测试。

|---|---|
| 做了什么 | 四个状态 `normal / pending_review / voided / kept_no_credit`；`UPDATE evaluation SET status=? WHERE id=? AND status='pending_review'`，行数 ≠ 1 抛 `STATUS_CONFLICT` 回滚 |
| 为什么 | 备选乐观锁版本号（要加列、每次更新带版本）、悲观锁（多一次加锁读，持锁更久）。条件更新用的是 `UPDATE` 的当前读，不受快照影响，比先 `SELECT` 判断再 `UPDATE` 安全。同一模式设计文档在退出投票也用（`...V2.1_最新_2026-05-27.md:876-885`） |

## 三、技术栈与取舍【念】

**30 秒总述。** 学生端微信小程序，管理端 Vue 3 加 Element Plus，后端 Spring Boot 加 MyBatis-Plus 加 MySQL，阿里云 ECS 单实例部署，Redis 只存邮箱验证码，图片放 OSS。选型我用三条标准：能做稳、能验证、能回退。让 AI 列出备选和优缺点，我按这三条拍板，写进详细设计，变成全员冻结的规则。

**四个关键决策**（每个一句：选了什么 / 备选 / 为什么）

| # | 选了什么 | 备选 | 为什么 |
|---|---|---|---|
| 1 | 数据库行锁 + 事务（申诉恢复） | Redis 分布式锁 | 单实例；账本一致性不该依赖 Redis 可用；Redis 锁要处理服务挂了锁不释放、TTL 太长、抛异常不知道有没有加上。多实例且跨服务互斥时才会加锁做性能保护，正确性仍留给唯一索引 |
| 2 | 唯一索引兜底 + 预检查 | 应用层先查再插 | 先查再插挡不住并发，只能提前拦；唯一约束是数据的性质，放数据库最可靠 |
| 3 | 条件更新（复核） | 乐观锁版本号 | 状态机单字段，一条语句判断加修改，不需要版本列；一个对象被多个流程改、冲突少时才换乐观锁；要先读多处状态再写，就换成行锁（申诉恢复就是这种） |
| 4 | 主动不做 MQ、定时任务、分布式锁、软删除、外键 | 引入这些 | 16 周 4 人单实例；过期状态用「被访问时检查」代替定时任务；通知用实时统计未读数代替消息系统；设计文档 P0 不做清单明确写了 |

### 4.5 真题「AI 生成的复杂长 SQL，怎么检查、验证能不能直接上线」

**【念】** 我不直接上线。分四步。第一，拿设计文档和表结构对一遍，字段、表名、关联条件对不对，AI 经常引用不存在的字段或类，推荐算法那份方案审查时就发现过动态 SQL 写错和引用了不存在的数据访问类。第二，在测试库用几组准备好的数据跑，包括边界：空结果、重复数据、极端值，输入输出对设计文档的预期。第三，看执行计划，确认走索引、没有全表扫描，看循环里有没有逐条查库。第四，写操作先看影响行数，并确认并发下不会重复生效；我们的复核就是条件更新，影响行数必须是 1，不是 1 回滚。合入前再由另一个 AI 只读审查，我自己看改动对比后提交。我们的真实经历里，查询次数也审过：修正后循环内没有查询。

【查】推荐算法方案审查：`PKG\03_详细设计\推荐方案\recommendation-plan-audit.md`（编译错误、接口路径写错、引用不存在的类、查询次数）；`技术选型与决策记录.md` D 节。**这一段的前提**：推荐算法那轮审查是你让另一个 AI 审的还是你自己审的，资料里仍是【待补】，面试里只说「方案审查之后才进入实现」，不说是谁审。
