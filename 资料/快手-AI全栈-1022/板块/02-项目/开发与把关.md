## 一、一句话（面试第一句）

> “我不写代码，我做的是**把业务规则拆成可验证的阶段，指挥 AI 一个阶段一个阶段地做，每个阶段用业务场景的输入输出来验收**。”

## 二、我的流程（口述 + 仓库证据）

```
① AI 按设计文档把任务划分成阶段         ← 阶段由 AI 提出【口述】
② 我判断这个划分是否合理               ← 我把关【口述】
③ 逐阶段和 AI 探讨业务场景             ← 先对齐“这一步要解决什么业务问题、有哪些场景”【口述】
④ AI 一次只做一个文件，做完停下来，用自然语言解释这个文件为什么存在、对应哪条业务规则、哪里需要我决策；我确认后才继续【仓库·工作令 §5.1、§5.2、§9】
⑤ 验证：给定输入，看输出是否符合预期（含边界和失败场景）【口述】
⑥ 一个小闭环做完且本地测试通过，再交给另一个 AI 只读审查：对照设计文档、建表脚本、模块边界【仓库·工作令 §11】
⑦ 我看改动对比，自己执行提交，走评审流程【仓库·工作令 §9、§10、§12】
```

**对 AI 立的硬规矩**【仓库·工作令】
- 不允许一次生成全部文件，每次最多一个文件（§5.1）。
- 我不理解就必须先解释，不许继续写（§5.2）。
- 不许“顺手扩展”：写完判断不许顺手写提交，写完后端不许顺手写前端，不许改建表脚本（§5.3）。
- AI 不做任何 Git 写操作（§10）。
- 每个阶段完成标准里包含“用户能解释每条业务规则”“审查无必改项”“改动对比干净”（§12）。

## 三、M5 的阶段划分与每阶段的业务场景、输入输出

> 阶段名来自审查记录、提交记录和任务拆解。阶段由 AI 提出、我判断，这是你的口述；每阶段的具体输入输出来自测试计划。

| 阶段 | 要解决的业务问题 | 验证：给什么输入 → 期望什么输出 |
|---|---|---|
| **M5-1 互评资格**（1A 项目级入口 / 1B 待评价成员 / 1C 提交前兜底） | 用户进到项目里，要不要给他显示“去互评”？能评谁？提交时再兜一次底 | 是成员 + 项目已结束 + 窗口内 → 允许；不是成员 → 拒绝（NOT_PROJECT_MEMBER）；项目未结束 → 拒绝；窗口过期 → 拒绝；评自己 → 拒绝；评过了 → 拒绝（ALREADY_EVALUATED）。待评价列表不含自己、能区分评过与没评过 |
| **M5-2 提交内容校验** | 这条评价的内容合不合规 | 四维分都在 1 到 5；打 1 或 2 分没有负向标签 → 失败；评语不足 20 字 → 失败；打 5 分没有正向标签 → 失败；评语含违规词 → 失败 |
| **M5-3 信誉分映射与封顶** | 一条评价该给被评价人加多少分，一个项目里最多加减多少 | 均分 → 分值：1.0→-5，1.5→-3，2.0→-2，2.5→-1，3.0→0，3.5→+2，4.0→+3，4.5 与 5.0→+5（每个区间边界都测）。封顶：已有 +8，本次 +5 → 实际只加 +2；已有 -9，本次 -5 → 实际只扣 -1；无效（挂起）的流水不参与累计 |
| **M5-4 异常评价检测** | 怎么发现泄愤或互刷 | 评价人没评完全部队友 → 不检测；评完全部队友且整体均分 ≤2 → 全部进入待复核；评完且整体 =5 → 全部进入待复核；正常 → 不挂起。挂起后流水置为“不计分”，已加的分回退 |
| **M5-5 提交的事务编排** | 把前面几步串起来，一次提交要么全成要么全不成 | 正常提交 → 评价、标签、流水都写入，总分变化正确；重复提交 → 返回“已评价”，不多写流水不多加分；中途任何一步失败 → 评价、流水、总分都不留半截 |
| **M5-6 评价复核** | 管理员怎么处理被挂起的评价 | 通过：待复核→正常，流水生效，总分加回；作废：待复核→无效，不计分；保留不计分：待复核→保留，不计分。不是待复核状态 → 拒绝；重复通过 → 冲突，不重复加分 |
| **M5-7 申诉恢复** | 申诉通过后怎么恢复分数 | 原流水 -5 → 追加 +5 的恢复流水并回写总分；原流水不计分 → 跳过，视为成功；已恢复过 → 返回“已恢复”，不重复加分；评价已被作废 → 拒绝；中途失败 → 不留半截恢复 |
| **M5-8 查询类接口** | 用户怎么看自己的信誉分和流水 | 只查自己的；流水按时间倒序；挂起的流水也展示并标注“已挂起”；分页参数有边界 |
| **M5-9 管理端复核接口** | 管理员在后台怎么操作复核 | 非管理员 → 拒绝；无效或过期 token → 未授权；待复核列表正确；三个动作调用复核服务 |

**边界场景**（测试计划里单列）：互评窗口最后一刻与过期后一刻；均值刚好在区间边界；项目只有两名成员；多条评价同时触发封顶；复核与申诉涉及同一条评价。

## 五、面试话术

**“AI 写的代码你怎么保证对？”**
> “我分三层保证。第一，**规格层**：业务规则写进详细设计并冻结，AI 只能按它做。第二，**过程层**：AI 一次只做一个文件、做完停下来解释，我不理解不放行。第三，**验收层**：每个阶段用业务场景的输入输出验收，包括边界和失败场景；完成后再让另一个 AI 对照设计文档做只读审查。比如异常评价检测，AI 第一版把‘评完全部队友后整体判断’做成了‘单条判断’，测试全绿，是审查对照设计文档才发现口径错了，我们改回来，并用测试把正确口径固化。”

**“测试通过了就对吗？”**
> “不一定。测试可能把错误的预期固化进去，M5-4 就是例子。所以验收看两件事：测试通不通过，以及测试的预期是不是符合设计文档的业务规则。”

**“你不看代码怎么验证？”**
> “我验证的是行为：给定业务场景的输入，输出对不对。比如信誉分映射，我关心每个区间的边界值给出的分数对不对；封顶，我关心已有 +8 再加 +5 最终是不是只加 +2。代码怎么写是 AI 的事，对不对由业务规则来判。”

**“你怎么判断 AI 划分的阶段合理？”** 【补充，待你确认】
> “看三点：每个阶段是不是对应一个能独立说清的业务问题；阶段之间依赖顺序对不对（先资格、再内容、再算分、再异常、最后串成事务）；有没有越界做了别的模块的事。”

### 案例 A：提交 `743486f`（2026-06-16，联调后期，你的账号）— 最适合讲“跑功能发现现象”

**缺陷 D4：首页“待互评”红点数字不对**
- **现象（推演）**：
  - 项目**还在进行中**，用户首页就出现“待互评”红点。
  - 项目互评窗口**已过期**，红点还挂着；点进去提示窗口已关闭，红点却不消失。
  - 在项目 A 已经评完所有人，项目 B 的红点反而变少了。
- **定位到的原因**：旧逻辑把“用户所有 active 项目的其他成员数”减去“用户**全部项目**已提交的评价总数”。既没限定项目状态，也没限定互评窗口，还把不同项目的评价混在一起减。
- **怎么修**：先筛出“已结束且窗口未过期”的项目，再按“项目+被评价人”逐个比对谁没评，用差集统计待评数；查询批量取，不在循环里查数据库。
- **怎么验证**：进行中项目 → 红点为 0；已结束且窗口内、未评完 → 红点等于没评的人数；窗口过期 → 红点为 0；两个项目互不抵消。有单测（`MeControllerTest`，该提交新增 54 行）。

**缺陷 D1：已结项项目“二次提示”不符**
- **现象（推演）**：互评窗口过期后，用户**第一次**点进互评页，提示“互评窗口已关闭”（正确）；**第二次**再点，提示变成“项目尚未进入互评阶段”（错误，项目其实早就结束了）。
- **定位到的原因**：第一次访问时系统发现过期，把项目状态从“已结束”改成“互评关闭”（懒检查）；第二次访问时，旧代码只允许“已结束”状态，看到“互评关闭”就直接按“项目没结束”处理。
- **怎么修**：状态判断同时接受“已结束”和“互评关闭”；如果已经是“互评关闭”，直接返回“窗口已关闭”。
- **怎么验证**：窗口过期后连续访问两次，两次提示一致；有单测（`EvaluationEligibilityServiceTest`，该提交新增 18 行）。

### 七·更正：按旧代码精确定位后的结果（2026-10-19）

> 对照修复前的代码（`743486f` 的上一版）和两份小程序前端源码核对后，**上面第七节里“页面上看到”的说法要收紧到接口层**。

**D4（待互评数字不对）——后端原因已精确定位**
- 旧版 `MeController.getBadges` 的“待互评”计算（修复前 `:96-116`）：
  1. 取出用户所有 active 成员关系对应的项目（`:69-75`），**不看项目状态**；
  2. 把这些项目里的“其他 active 成员数”全部加起来（`:101-108`）；
  3. 减去用户**所有项目**里已提交的评价总数（`:111-113`）；
  4. 结果取不小于 0（`:115`）。
- 所以：进行中的项目、窗口已过期的项目都会被计入；不同项目的已评数互相抵消。
- **界面这一侧没有找到**：两份小程序源码里都没有调用 `/me/badges` 或读取 `pendingEvaluations` 的地方（搜索 badges、pendingEvaluations、红点、unread 无命中），只有组队中心有“待投票”数量。所以“红点出现在哪个页面”我无法从源码确认，只能确认**接口返回的数字**是错的。

**D1（二次提示不符）——后端原因已精确定位，但小程序不会显示两种不同文案**
- 旧版 `checkProjectEligibility`（修复前 `:60-74`）：第 3 步只放行“已结束”状态；第 4 步发现窗口过期时，把项目状态改成“互评关闭”并返回“互评窗口已关闭”。
- 第二次再查，项目状态已是“互评关闭”，卡在第 3 步，返回“项目尚未进入互评阶段”。
- **接口层现象**：同一个请求，第一次返回 `EVAL_WINDOW_CLOSED / 互评窗口已关闭`，第二次返回 `PROJECT_NOT_ENDED / 项目尚未进入互评阶段`。
- **小程序里看不到这两句不同的话**：互评页的资格校验失败时统一提示“资格校验失败”（`evaluation.js` 的 `checkEligibility`，请求函数 `team-service.js:485-495` 对非成功码直接拒绝）。所以你如果记得看到了两种不同的文字，应该来自**接口返回**（比如接口联调、Postman）或别的版本，不是这版小程序页面。

**对面试话术的影响**
- 讲“我跑功能时发现”，要说成“**联调和接口验证时发现**接口返回的数字和提示不对”，不要说成“小程序页面上看到红点”。
- 这依然是“跑起来发现现象 → 定位原因”：现象是接口响应，原因定位到上面的行。
