## 一、每个榜单的排名依据（实际实现）

| 榜单 | 排名依据 | 在哪里排序 | 数据口径 |
|---|---|---|---|
| **技术排行榜**（综合） | 综合技术分，降序 | **后端**（SQL 按技术分降序，分页） | Stars×10 + 提交数×2 + PR 数×5 + 仓库数×3 + 贡献数×1 |
| **Stars 星标榜** | 非 fork 仓库的 Star 总数 | 前端对已取回的列表排序 | 直接取自 GitHub / Gitee |
| **开源仓库榜** | 非 fork 的公开仓库数 | 前端排序 | 直接取自平台接口 |
| **代码贡献榜** | 提交数 | 前端排序 | **GitHub 是估算**：Star×20 + Fork×10；**Gitee 授权后是真实提交数**（逐仓库查）；Gitee 未授权也是估算（Star×20 + 仓库数×5） |

**每个人的“主力语言”怎么来**：只统计**非 fork 仓库**，每个仓库取平台给的“主语言”，按**出现的仓库个数**统计，取前 5。也就是说语言是“你有几个仓库用它”，**不是代码量，也没有按 Star 加权**。

**三个必须知道的事实（被追问就如实说）**
1. **提交数、PR 数、贡献数大多是估算值**（为了不要求用户授权，用的是无认证接口，限流 60 次/小时）。所以综合分实际上主要由 Star 和仓库数决定。技术画像说明里的论证：估算对所有人偏低的程度相似，相对排名影响不大。
2. **三个维度榜是前端排序**，只对前端取回的那一页（最多 100 条）排，不是全局真实排名。
3. **小程序榜单页会混入演示用的 Mock 数据**（代码注释写“Mock 数据永驻”）。不要说“榜单全是真实用户”，说“冷启动阶段用演示数据 + 真实绑定数据一起展示，真实用户绑定后进入榜单”。

## 二、核心问题：怎么根据不同语言，区分其具体的评分？

### 先给结论（面试第一句）
> “我们现在的**综合技术分不区分语言**，语言是画像里的标签。区分语言和技术栈，目前发生在**匹配层**：项目要什么技能，就看这个人在这些技能上的匹配度和可信度。如果要做成按语言单独评分，我的方案是……”

这样说是真话，而且面试官接下来问的正好是你准备好的方案。

### 现状：技术栈是怎么区分的（已实现）
- **技能字典**分编程语言 / 框架 / 工具 / 软技能四类；用户选自己的技能，项目选所需技能。
- **推荐**：技能匹配度（Jaccard）× 技术能力可信度 × 合作可信度。
- **技术能力可信度**：新用户用 GitHub 技术分当先验；有互评后，用互评里的“技术能力”维度分（按评价者信誉加权，低于 30 的评价丢弃），两者贝叶斯混合，先验相当于 5 条互评的分量。
- **现状的局限（主动说）**：互评里的技术维度是**一个整体分**，不分 Java / Python，代码注释写明“所有命中技能共享同一个权威分”。所以“这个人 Java 强不强”现在还回答不了。

### 为什么现状是这样（取舍，真实理由）
| 理由 | 依据 |
|---|---|
| **无认证接口限流 60 次/小时**。仓库列表一次请求就能拿到每个仓库的“主语言”；要拿每个仓库各语言的代码量，要**每个仓库再请求一次**，100 个仓库 = 100 次，一个用户就把额度用光 | 技术画像说明 §3.3 |
| 冷启动阶段要的是“能快速给结果、结果可解释”（“先给收益，再要求成本”） | 详细设计 §3.4 |
| P0 范围收紧，Gitee 双平台、批量爬取、定时更新都放到后续 | 详细设计 §0.3 |

### 如果要按语言区分评分，我的方案（演进方案，不是已实现）
**1. 数据层：把“语言”从一个标签变成一组指标**
- 授权后（OAuth）才能取每个仓库的各语言代码字节数、真实提交、PR。→ 每个语言得到：代码量占比、该语言的仓库数、该语言仓库的 Star 总和、近 12 个月提交活跃度。

**2. 评分：每个语言单独打一个分**
- 语言分 = `log(1 + 该语言仓库 Star 总和)` × 权重1 + `该语言仓库数` × 权重2 + `近期活跃度`（时间衰减）× 权重3。
- 取对数：压低靠少数爆款仓库刷出来的高分。时间衰减：三年前写过的和现在在写的不一样。

**3. 榜单：同一语言内排名，不跨语言比绝对值**
- Java 和 Rust 的 Star 量级本来就不同，直接比没有意义。做法是**按语言分组，在组内用百分位排名**（“该语言前 10%”）。

**4. 语言 ≠ 技术栈**
- 技术栈（框架、工具）要从仓库的 topics、依赖文件（如 `pom.xml`、`package.json`、`requirements.txt`）识别，再映射到已有的技能字典。
- 好处：字典已经分好 language / framework / tool 三类，直接复用。

**5. 和互评打通（项目里已经有预留）**
- **技能点赞是专门设计的**（你已确认）：互评时可以对具体技能点赞，详细设计里有这张明细表，互评页面也有“点赞技能”的入口（小程序提交时带了点赞的技能）。设计定位是 **P0 仅展示、不影响信誉分、不写入信誉流水**（详细设计 §6.9、`M5_DB.md`）。
- **现状要如实说**：表和实体已建，小程序也传了点赞的技能，但后端提交链路**还没有写入**，开发日志里记录为“不影响信誉分账本，后续由后续任务承接”（`IMPLEMENT_LOG.md:193-195`）。所以现在的准确说法是：**数据模型和前端入口设计好了，写入和使用排在下一迭代**。
- **为什么先不接**（可讲的理由，对应设计）：P0 把信誉账本的一致性放在第一位（唯一索引、事务、复核、申诉），点赞不影响信誉分，不在关键路径上，所以先保证账本，再接点赞。
- **接通后的用法（演进，属于 P1 设计）**：点赞按技能累积，每个技能有自己的互评信号，可信度按技能算，而不是所有技能共享同一个整体分；然后沿用现有的“先验 + 互评、按评价者信誉加权”的混合方式，只是从整体分变成按技能分。

**6. 反作弊**
- 已有：不统计 fork；互评按评价者信誉加权，低信誉评价者丢弃。
- 要加：Star 增长突变和同账号集中点赞识别；单仓库 Star 封顶；账号年龄门槛。

## 三、可能被追问的点

| 追问 | 答法 |
|---|---|
| 为什么 Star 权重最高 | Star 是社区对项目质量最直接、最容易获取的认可信号。承认缺点：容易被刷、和个人贡献不严格相关，所以真实提交和 PR 的数据（授权后）权重要提高，Star 要取对数 |
| 提交数是估算，榜单还有意义吗 | 冷启动要“能排出来、能解释”，估算对所有人偏差相似；它只是**先验**，有互评后由真实协作数据接管，评价者信誉还会加权。承认：代码贡献榜在 GitHub 上主要反映 Star 和 Fork |
| 刷 Star 怎么办 | 现状没有专门识别；说清楚缓解手段（对数、封顶、互评校正），以及要做的识别 |
| 为什么技术分不和信誉分合并 | 技术能力和协作信用是两个问题，合并会互相污染；组队时两个分数分别用于匹配（技术）和准入、加权（信誉） |
| 榜单实时吗 | 绑定时同步一次，之后没有定时刷新（P0 不引入定时任务）；同步失败建空画像占位，不阻断绑定。要刷新可以用户手动触发，或加定时任务 |
| 限流怎么处理 | 用无认证接口、每次绑定只请求用户信息和仓库列表两次；失败降级。要提升就申请 Token 或用户授权 |
| 一个人只写 Java，会不会被推荐到前端项目 | 不会：推荐先看技能匹配度，低于门槛直接过滤 |
| 新人没有仓库怎么办 | 没有画像时用兜底先验；互评积累后以互评为准 |
| 榜单里有 Mock 数据怎么解释 | 冷启动阶段让榜单不空；真实数据来自用户绑定。上线时可以关掉 |
