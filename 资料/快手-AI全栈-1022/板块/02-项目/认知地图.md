## ① 产品层

### 1.1 一句话

**TeamMatch 帮想做技术项目的学生在组队前回答两个问题：他技术怎么样？他合作靠不靠谱？**
- 技术怎么样 → 用公开的代码数据（GitHub / Gitee）生成**技术分**和榜单。
- 合作靠不靠谱 → 把过去每一次合作的表现沉淀成**信誉分**，并让它影响下一次组队。

核心用户：学生里有**技术开发组队需求**的人（做课程项目、比赛、开源）。【口述】

### 1.2 要解决的问题（V2.1 §1.1）【文档】

| 问题 | 谁受影响 |
|---|---|
| 组队效率低 | 想找队友的同学 |
| 选人盲目 | 队长不知道谁靠谱 |
| 协作过程缺少可信记录 | 甩锅、跑路没有代价，认真干活没有回报 |
| 项目经历难沉淀为可信档案 | 同学的项目经历只能靠自己说 |

### 1.3 三类角色、两个入口

| 角色 | 在哪用 | 能做什么 |
|---|---|---|
| 普通学生 | 微信小程序 | 看榜单、建档案、发布 / 搜索项目、申请 / 接受邀请、协作、互评、看信誉分、举报 / 申诉 |
| 队长（项目创建者自动成为队长） | 小程序 | 邀请 / 审批成员、切换项目状态、发起移除投票 |
| 管理员（单级，后端预置，不开放注册） | Web 管理端 | 复核异常评价、处理举报 / 申诉、执行处罚、管理板块 |

### 1.4 产品主线（V2.1 §0.4A 冻结）【文档】

```
冷启动引流 → 正式档案建立 → 发布/搜索项目 → 邀请/申请组队 → 协作执行
        → 项目结项 → 互评沉淀 → 信誉变化 → 影响下一次组队
                                              ▲                │
                                              └────────────────┘
```

**这是一个飞轮：信誉越有价值，大家越认真互评；互评越认真，信誉越可信。** 其余所有功能都是为这个飞轮服务的：前半段负责“把人带进来、把队组起来”，后半段负责“让评价可信”。

### 1.4.1 产品的两个核心分数（你的定位 + 仓库核对）

| | **技术分** | **信誉分** |
|---|---|---|
| 回答的问题 | 他技术怎么样 | 他合作靠不靠谱 |
| 数据来源 | 绑定 GitHub / Gitee，分析公开仓库：语言、仓库数、Star 等 | 过去组队记录：互评、退出、处罚、申诉 |
| 性质 | 客观，**还没合作过也有**（解决冷启动） | 行为数据，需要合作后才积累 |
| 主要用途 | 榜单；被搜索 / 被推荐时的技术依据 | 组队准入（推荐里有信誉门槛）、处罚依据 |
| 为什么分开 | 技术能力和协作信用是两件事，混在一起会互相污染：一个技术很强但爱跑路的人，不该因为技术分高而信誉看起来好（M3 说明 §6.3 明确“不混合计算”）【仓库】 | |

**技术分怎么来**【仓库：`M3_技术画像与排行榜说明.md` §3】
- 绑定账号后，平台读取该用户公开仓库（不含 fork），汇总 Star、仓库数、提交数、PR 数、主力语言 Top 5，按权重加总成综合技术分：Star 权重最高（社区认可），其次 PR（协作与开源贡献），再是仓库数、提交数。
- **局限（要主动承认）**：为了不让用户授权，用的是无认证接口，提交数、PR 数、贡献数是**估算值**（由 Star、Fork、仓库数推出），所以综合分实际上主要由 Star 和仓库数驱动。文档的理由是“估算对所有人低估程度相似，相对排名影响不大”。改进方向：OAuth 授权后取真实提交和 PR；按语言分别打分；对刷 Star 做异常识别。
- 榜单：按综合技术分降序；已认领的显示学校、昵称，未认领的也展示（促使认领）。小程序端可以按综合分 / Star / 仓库数 / 提交数切换排序（前端排序）。语言是画像的属性（Top 5）。

**你说榜单已实现，我核对到的和没核对到的**
- 找到了：小程序榜单页有**四种榜**——技术排行榜（综合分）、Stars 星标榜、开源仓库榜、代码贡献榜（`leaderboard.wxml:15`，按维度切换）；每个人的**主力语言 Top 5** 随画像展示；**技能字典**按“编程语言 / 框架 / 工具 / 软技能”分类，用于技术栈标签和匹配（`skills.wxml:26`）。
- **没找到**：按某一种语言单独成榜（比如“Java 榜”）的入口。后端 `/leaderboard` 只有分页参数，没有语言或技术栈参数（`TechProfileController.java:62-70`）；前端传的 `sort` 参数后端也没有接收，维度切换是前端排序（`leaderboard.js:139-143`）。我搜过关键词“语言榜 / 技术栈榜 / byLanguage / language=”，在后端、小程序、打包的另一份源码和设计文档里都没有命中。

**【待你确认】** Gitee：详细设计 V2.1 把 Gitee 放在 P1，但仓库里有 Gitee 授权和同步代码，技术画像说明也同时写了两个来源。实际交付范围以哪个为准？

**两个分数怎么一起用于“组队前筛选”**【仓库：推荐服务】
```
队长发布项目（带所需技能）
   → 阶段一 硬约束：信誉分达标（≥80）、账号正常、已建正式档案、排除自己/已在队/已被邀请的人、技能相似度太低的剔除
   → 阶段二 粗排：按技能匹配度（和项目所需技能的重合程度）排序
   → 阶段三 精排：最终分 = 技能匹配度 × 技术能力可信度 × 合作可信度
```
- **合作可信度** = 信誉分（封顶 1）。
- **技术能力可信度**：新用户没有互评，用 GitHub 技术分当**先验**；有了互评之后，用别人给他的“技术能力”评分，并**按评价者自己的信誉加权**（评价者信誉低于 30 的评价直接丢弃，防小号刷分）；两者做贝叶斯式混合——互评越多，GitHub 先验的影响越小，先验相当于 5 条互评的分量。
- 意义：**这就是互评（你负责的后端）和技术画像连在一起的地方**：互评不仅产出信誉分，还回头校正技术分。冷启动靠公开数据，稳定后靠真实协作。

### 1.5 冷启动：为什么平台一开始就要有“榜单”（V2.1 §1.2.1、§3）【文档】

```
排行榜引流 → 临时技术画像 → 学校邮箱认证 → 档案认领 → 进入正式榜单/搜索 → 发布或加入项目
```
- 问题：平台刚上线没人、没数据，“空城”。
- 做法：输入 GitHub 用户名，立刻生成**临时技术画像**（只分析公开仓库），“**先给收益，再要求填写成本**”；想上正式榜单、被搜到、接收邀请，必须认证邮箱建档案。
- 定位：冷启动**是主流程入口，不是营销附属**（V2.1 §0.4B）；画像只是轻量引流入口，**不落核心主库**。
- P0 取舍：只支持 GitHub 公开仓库，榜单允许离线脚本或手工维护；Gitee 双平台、批量爬取、定时更新移入 P1。

| 竞品 | 优势 | 劣势 | 我们的策略 |

## ② 业务规则层（六大板块）

> 每条规则带“为什么”。【文档】= 文档里写了意图；【补充】= 我补的逻辑，待你确认。

### 板块一：用户与认证 / 档案（§2）
| 规则 | 为什么 |
|---|---|
| 学生统一微信登录；管理员账号后端预置、不开放注册 | 【补充】学生要零门槛；管理员入口要收紧，避免被人自封管理员 |
| 学校邮箱验证（60 秒防刷、10 分钟有效、一个邮箱只能绑一个人） | 【补充】用邮箱把“真人 + 在校”绑定，信誉才有意义；防刷防多号 |
| 用户角色只能后端控制，前端不能自行决定 | 【补充】权限不能信任客户端 |
| 正式档案建立前，核心操作受限 | 【文档】冷启动“先给收益再要求成本”的另一半：想深度参与就得认证 |

### 板块二：冷启动 / 技术画像 / 档案认领（§3）
| 规则 | 为什么 |
|---|---|
| 临时画像只看公开仓库；不落核心主库 | 【文档】轻量引流，不承担正式数据责任；也避免未经同意采集 |
| 标签匹配推荐用 Jaccard 相似度，0 匹配不返回 | 【补充】技能标签是预置字典（集合），交并比最简单可解释；0 匹配推荐没有意义 |
| 技能标签 P0 只用预置字典，不允许自定义 | 【文档】已定稿；【补充】自定义会让匹配和搜索失控 |
| 中文搜索用 MySQL FULLTEXT + ngram，效果不佳时降级 LIKE | 【文档】已定稿；不引入搜索引擎，降低复杂度 |

### 板块三：项目管理（§4）
- **项目生命周期**：招募中 → 进行中 → 已结束（互评窗口开放）→ 互评关闭（只读）。【文档】
- 规则与理由：
  | 规则 | 为什么 |
  |---|---|
  | 只有队长能切换项目状态 | 【补充】权责清晰 |
  | 只有“招募中”允许邀请 / 申请；开始后剩余待处理请求全部失效 | 【补充】阵容在开始时固定，后面的退出、互评才有稳定的“应评价对象”集合 |
  | 项目结束后开启 **7 天**互评窗口 | 【文档】冻结；【补充】太短来不及评，太长会拖，也让信誉迟迟不更新 |
  | 互评关闭用“**懒检查**”（有人访问时才判断是否过期），不依赖定时任务 | 【文档】P0 不引入定时任务，降低运维和一致性复杂度 |
  | 项目不提供删除，状态只表达生命周期；核心表不做软删除 | 【文档】已定稿，保留历史、避免信誉流水指向不存在的项目 |
  | 结项凭证 P0 不做 | 【文档】已定稿，移入 P1 |

### 板块四：组队 / 成员 / 退出机制（§5）
这是**最容易被追问产品逻辑**的一块，核心是“**跑路的代价设计**”。

| 场景 | 扣分 | 设计意图 |
|---|---|---|
| 成员主动退出（self_exit）直接生效 | **-10** | 【文档】“重罚，堵死规避差评漏洞”：如果主动退出比被投票踢出更轻，就会有人在被评差评前自己先跑 |
| 队长发起移除投票，通过，“协商退出”档 | -5 | 【补充】给有正当原因的情况留余地 |
| 队长发起移除投票，通过，“恶意失联”档 | -10 | 【补充】和主动跑路同罪 |
| 投票未通过 | 0，不写流水 | 【文档】 |

- 投票规则：赞成票 > 反对票才通过，**平票算否决**（保守，不轻易踢人）；24 小时截止，用懒检查关闭；同一目标同一时间只能有一个进行中的投票；被投票人期间自己退出，走主动退出扣分，投票直接关闭。
- 招募阶段不允许队长直接移除成员：【补充】移除是有信誉代价的动作，必须在“进行中”并经投票，防止队长滥权。
- 退出机制拆成三层（触发方式 / 投票结果 / 成员状态），**不允许混用命名**（V2.1 §0.4C）：【文档】这是为了防止不同模块对同一件事各说各话。

### 板块五：互评 / 信誉分 / 异常 / 申诉（§6）——**本人负责的后端**

**互评怎么设计**
| 规则 | 为什么 |
|---|---|
| 只有同项目正式成员能互评，且必须在窗口内，不能评自己，一个对象只能评一次 | 【补充】评价必须来自真实协作关系；一人一票防刷 |
| 四维评分：沟通协作、任务完成、技术能力、责任心 | 【补充】单一总分太粗，也不利于解释；四维让评价可以“有理由” |
| 打 **1 或 2 分必须附负向标签和不少于 20 字的说明**；打 **5 分必须附正向标签** | 【补充】极端分最容易是情绪或互刷，要求给理由，提高作弊和报复成本 |
| 前台**匿名**展示，后台可追溯 | 【文档】匿名让人敢说真话；可追溯让平台能治理 |
| 不等待全员提交 | 【文档】P0 不卡进度，避免一个人不评拖住所有人 |

**信誉分怎么算**
- 初始 100 分；单条评价取四维均值，按八个区间映射为 -5 到 +5。【文档】
- **单项目封顶 ±10**：同一人在同一项目里互评带来的变化总和不超过 ±10。【文档】
  - 【补充】防止一个项目里被集中刷分或集中打压，一次合作不能决定一个人的全部信誉。
- **任何分数变化都必须先有一条流水**，不允许绕开流水直接改分。【文档】V2.1 §0.5
  - 【补充】流水是账本，可追溯、可审计、可对账；用户总分只是缓存。

**防作弊的完整链条（这块是产品与技术的结合点，面试官最爱问）**

| 作弊 / 异常手段 | 产品层机制 | 技术保障（④ 层展开） |
|---|---|---|
| 重复评价、刷评价 | 一个对象只能评一次 | 数据库唯一约束 |
| 评价人给所有队友全打低分 / 全打满分（泄愤、互刷） | 评价人评完**全部**队友后整体判断：均分 ≤2 或 =5，进入“平台复核中”，暂不计分 | 批量挂起评价 + 对已生效的流水做反向修正 |
| 集中打压 / 集中刷分 | 单项目封顶 ±10 | 封顶计算 |
| 评价不公平 | 被评价人可**申诉**；通过后追加一条**反向流水**恢复（不改原流水，因为“原始流水是已发生的事实”） | 行锁 + 幂等检查 |
| 异常评价挂起后怎么处理 | 管理员**复核**：通过（恢复计分）/ 作废（不展示不计分）/ 保留但不计分 | 状态流转用条件更新 |
| 复核与申诉两个入口同时处理同一条评价 | **入口约束**：待复核的评价不开放申诉，作废和保留不计分也不开放；只有正常计分的评价能申诉 | 设计上避开并发，而不是靠加锁硬扛 |

**为什么异常检测放在“评完全部队友之后”**【补充】：只评一个人时，全低分 / 全满分可能是合理的；只有看到这个人对**所有**队友的整体模式，才能判断是不是泄愤或互刷。（这也是代码审查里发现 AI 把规则做成“单条判断”并纠正的那一处，见 ⑤。）

### 板块六：后台治理（§7）
- 举报：P0 只对用户和项目开放，**不对评价开放**；评价的争议走“复核”和“申诉”，不走举报。【文档】
- 申诉：对收到的互评不满，或对管理员处罚不满。【文档】
- 处罚：扣信誉分，或限制功能 / 封禁。【文档】
- 举报、申诉、复核、处罚**都要留痕**。【文档】
- 单级管理员，不分层级。【文档】已定稿

## ③ 状态与数据层

### 3.1 状态机总览（每个都能讲“从哪到哪、谁能触发”）

| 对象 | 状态 | 谁触发 |
|---|---|---|
| 项目 | 招募中 → 进行中 → 已结束 → 互评关闭 | 队长；到期由懒检查关闭 |
| 成员 | 在队 → 已离队（附带“怎么离的”：主动 / 被投票移除） | 成员本人 / 投票结果 |
| 评价 | 正常计分、待复核、判为无效、保留但不计分 | 提交时正常；异常检测挂起；管理员复核 |
| 信誉流水 | 生效 / 挂起（不计分） | 随评价状态联动 |
| 申诉 | 待处理 → 通过 / 驳回 | 管理员 |
| 移除投票 | 进行中 → 已关闭（通过 / 否决 / 无结果） | 全员投完 / 队长手动关闭 / 超时懒检查 |

### 3.2 数据模型地图（17 张表，按业务分组；V2.1 §1.4、§8.6）

| 分组 | 表 | 一句话 |
|---|---|---|
| 用户与认证 | user、skill_tag、user_skill | 人、预置技能字典、人与技能的关系 |
| 项目与推荐 | project、project_skill、board | 项目、项目要的技能、项目所属板块 |
| 组队与退出 | team_request、team_member、exit_vote、exit_vote_record | 邀请 / 申请、正式成员、移除投票及每张票 |
| 互评与信誉 | evaluation、evaluation_tag、skill_endorse、credit_change | 评价、评价理由标签、技能点赞、**信誉流水（账本）** |
| 平台治理 | report、appeal、penalty | 举报、申诉、处罚 |

**数据设计的几条主线（每条都能讲取舍）**
1. **账本思想**：`credit_change` 是事实源，用户总分只是缓存；一切分数变化先有流水。→ 好处：可追溯、可对账、申诉恢复用“追加反向流水”而不是改历史。代价：多写一张表、需要保证两者同步（用事务）。
2. **用唯一约束表达业务规则**：一个人对一个队友在一个项目里只评一次；同一事件只申诉一次；同一来源同一类型的流水只一条。→ 规则落在数据库，不依赖应用层记得去检查。
3. **不做软删除、不做外键**（V2.1 §0.3；DDL 无外键）：简化实现。代价：引用完整性靠应用层保证。【补充：外键的取舍你当时怎么想的，待补】
4. **懒检查代替定时任务**：状态过期（互评窗口、投票截止）在被访问时才判断。→ 少一个运行组件；代价：数据在没人访问时是“旧状态”。

## ④ 技术保障层（与产品规则一一对应）

| 产品要求 | 技术手段 | 备选方案 | 为什么这样选 |
|---|---|---|---|
| 一个人对一个队友只评一次 | 联合唯一约束 + 提交前预检查 | 应用层锁、Redis 锁 | 规则本身是数据的性质，放数据库最可靠；单实例不需要额外组件 |
| 评价、流水、总分要同进同退 | 单库同一事务 | 异步消息 + 补偿 | 账本要强一致；P0 不引入 MQ |
| 复核不能被重复处理、不能重复加分 | 条件更新（状态不对就更新不到） | 版本号乐观锁、行锁 | 状态机单字段，一条 SQL 既判断又修改，最轻 |
| 申诉恢复不能多加分 | 行锁 + 状态判断 + 幂等检查 + 唯一约束兜底 | 条件更新、分布式锁 | 要先读评价状态、原流水、是否已恢复，再决定写不写 |
| 复核与申诉不冲突 | 入口约束（产品规则前置） | 加锁互斥 | 从源头避免并发路径 |
| 前端被重复点击 | 提交中禁用按钮 | — | 减少无效请求，不是保证 |
| 重复的业务失败要让前端能区分 | 统一业务错误码枚举 + 统一返回结构 | 全部返回 HTTP 错误码 | 前端按码给出准确提示，不统一退回“系统异常” |
| 组队前按“技术 + 信誉”筛选和排序 | 三阶段推荐：硬约束过滤 → 技能匹配粗排 → 精排（匹配度 × 技术可信度 × 合作可信度）；关联数据批量预取，查询次数不随候选人数增长 | 一个综合分、纯人工浏览 | 过滤放前面减少计算；两个分数各管一件事，乘法使任何一项很低都会拉低最终排名 |
| 技术分冷启动 | 公开仓库数据当先验，互评积累后贝叶斯混合接管 | 只用 GitHub 分、只用互评分 | 新用户没有互评也能被推荐；互评多了以真实协作为准 |
| 信誉分封顶的并发 | 目前读-算-写，**没有加锁** | 对用户行加锁 | P0 单实例、窗口小；已知不足 |
